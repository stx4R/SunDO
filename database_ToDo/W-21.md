## 1. 🔴 `authDomain` 변경 — P-0의 선행 조건

### 1.1 무엇을 왜 바꾸나

| | 이전 | **이후** |
| --- | --- | --- |
| 앱 출처 | `https://sundo-dev-8ef38.web.app` | 같음 |
| manifest `scope` | `/` | 같음 |
| `VITE_FIREBASE_AUTH_DOMAIN` | `sundo-dev-8ef38.firebaseapp.com` | 🔴 **`sundo-dev-8ef38.web.app`** |

**원인** — iOS 홈 화면 앱(standalone)은 **manifest `scope` 밖 내비게이션을 Safari로 내보낸다.**
`firebaseapp.com`은 scope 밖이라 `signInWithRedirect`가 앱을 벗어나고, OAuth가
**앱과 다른 브라우징 컨텍스트**에서 끝난다. 앱으로 돌아와도 `getRedirectResult()`가 `null`을
돌려주어 로그인 화면이 다시 뜬다 — **그것이 무한 루프다.**

🔬 실측(W-21) — 앱 출처에도 인증 헬퍼가 그대로 산다:

```
GET https://sundo-dev-8ef38.web.app/__/auth/handler   → 200 (Firebase 인증 헬퍼 원본)
GET https://sundo-dev-8ef38.web.app/__/auth/iframe    → 200
GET https://sundo-dev-8ef38.web.app/                  → 200, redirects=0
```

⇒ `authDomain`을 앱 출처로 맞추면 **전 과정이 동일 출처 · scope 안**이 되어 앱을 벗어나지 않는다.

⚠ **코드 diff는 0줄이다.** 값은 `.env.local`(커밋 대상 아님)에 있다.
커밋되는 것은 `.env.example`의 **주의 문단**뿐이다 — 다음 사람이 같은 함정에 빠지지 않도록.

### 1.2 🔴 콘솔 작업 (배포보다 먼저)

**① Google Cloud 콘솔 — 승인된 리디렉션 URI 추가** (필수)

1. <https://console.cloud.google.com/apis/credentials> → 프로젝트 **`sundo-dev-8ef38`** 선택
2. `OAuth 2.0 클라이언트 ID` 목록에서 **`Web client (auto created by Google Service)`** 클릭
3. **`승인된 리디렉션 URI`** 에 **추가**:

   ```
   https://sundo-dev-8ef38.web.app/__/auth/handler
   ```

4. 🔴 **기존 `https://sundo-dev-8ef38.firebaseapp.com/__/auth/handler`를 지우지 마라.**
   추가만 한다 — 되돌릴 일이 생겼을 때 그 줄이 살아 있어야 즉시 복구된다
5. `저장` → ⚠ **반영에 몇 분 걸릴 수 있다.** 저장 직후 실패하면 5분 뒤 다시 해 보라

**② Firebase 콘솔 — 승인된 도메인 확인** (대개 이미 되어 있다)

1. Firebase 콘솔 → `Authentication` → `Settings` → **`승인된 도메인`**
2. **`sundo-dev-8ef38.web.app`** 이 목록에 있는지 확인. 없으면 **추가**
3. ⚠ 없어도 대개 Hosting 사이트는 자동 등록돼 있다. **확인만 하고 다른 줄은 건드리지 마라**
   (`preview`·`live` 도메인 정리는 **W-22**다 — §18.2)

### 1.3 되돌리는 법

1. `.env.local`의 `VITE_FIREBASE_AUTH_DOMAIN`을 `sundo-dev-8ef38.firebaseapp.com`으로 되돌린다
2. `npm run build && npx firebase deploy --only hosting --project sundo-dev-8ef38`
3. 🔴 **콘솔은 되돌리지 않아도 된다.** ①은 추가만 했고 기존 URI가 그대로 남아 있다

⚠ **서비스 워커는 이 수정에 관여하지 않는다.** `public/sw.js` diff 0줄이라
W-20의 오프라인 계약(앱 셸 · 정책 3종 · 캐시 이름)은 **다시 검증할 필요가 없다.**

### 1.4 확인란

## 3. 🔴 검증용 2차 배포와 원복 (체크리스트 14~16번)

`database_ToDo/W-20.md` §4 그대로다. 배너는 **「새 워커가 감지될 때」**만 뜨므로,
`v0.14.0`을 설치한 기기에 **다른 바이트의 워커**를 한 번 더 올려야 잰다.
🔴 **커밋은 `SunDO v0.14.0` 1회 그대로다**(GT-03).

🔴 **W-20 §4의 절차(`sw.js`에 주석 한 줄)를 그대로 쓰면 16번을 잴 수 없다.**
`sw.js`만 바뀌면 `/assets/**` 해시가 그대로라 **화면이 바이트 단위로 동일해서
「최신인지」를 눈으로 구분할 수단이 없다.** 14·15번에는 충분하지만 16번에는 **마커가 필요하다.**

⇒ **`package.json` 버전을 임시로 올린다.** 한 번에 셋을 얻는다 —
① `sw.js`의 `VERSION`이 갈려 배너가 뜬다 ② **S10의 버전 표시가 눈에 보이는 증거**가 된다
③ 자산 해시까지 갈려 `assetCacheFirst`가 캐시 미스로 새 자산을 받는 것을 실제로 잰다.

```bash
# ① 정식 배포 (커밋과 같은 상태)
npm run build && npx firebase deploy --only hosting --project sundo-dev-8ef38

# ② 검증용 임시 배포 — package.json의 version을 한 칸 올린다 (예: 0.14.0 → 0.14.1)
npm run build && npx firebase deploy --only hosting --project sundo-dev-8ef38
#    → 앱을 다시 열면 업데이트 배너 (14) → 탭 (15)
#    → 🔴 배너를 무시하고 앱을 껐다 켠 뒤 S10의 버전 표시가 0.14.1이면 (16) 통과

# ③ 🔴 원복 — version을 되돌리고 즉시 재배포
#    🔴 `git checkout -- package.json`을 쓰지 마라 (§4.3)
npm run build && npx firebase deploy --only hosting --project sundo-dev-8ef38
git status --short   # ← 이 회차의 정상 변경만 남아야 한다
```

⚠ **② ~ ③ 사이에는 저장소와 배포본이 다르다.** 끝나면 **미루지 말고 ③을 하라.**
③이 실패하면 `npx firebase hosting:rollback --project sundo-dev-8ef38`으로 ①로 되돌린다.

### 3.1 🔴 원복이 제대로 됐는지 재는 법

배포본 `sw.js`의 **캐시 이름**을 본다 — `sundo-shell-v{버전}-{precache 목록 해시}`다.

```bash
curl -s "https://sundo-dev-8ef38.web.app/sw.js?cb=$(date +%s)" | grep -o "const VERSION = '[^']*'"
curl -s "https://sundo-dev-8ef38.web.app/sw.js?cb=$(date +%s)" | grep -o "sundo-shell-v[^\`]*"
```

🔬 W-21 실측: 검증 전 `8c3012bc` → 검증용 `fe580f3a` → 원복 후 **`8c3012bc`**.
**해시가 검증 전과 같다는 것이 곧 바이트 동일**이라는 증명이다.

### 3.2 🔴 `git checkout`으로 원복하지 마라 — W-21에서 실제로 당했다

`git checkout -- package.json`은 **아직 커밋되지 않은 그 회차의 정상 변경까지** HEAD로 돌린다.
W-21에서 `0.14.1` → `0.14.0`을 노렸는데 **`0.13.0`이 되어 그대로 배포됐다.**
**값을 직접 되돌려라.** W-20 §4가 `git checkout -- public/sw.js`를 쓴 것은 그 파일이
**그 회차에 이미 커밋될 상태였기 때문**이다 — 전제가 다르면 같은 명령이 다른 일을 한다.
