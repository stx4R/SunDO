## 1. 인덱스 실측 결과 — 6행 전문

st4R 환경(`sundo-dev-8ef38` · 부장 계정 · `records`·`students` 공란)에서 **앱이 초기화한 SDK 인스턴스**로 직접 측정한 값이다.

```
project=sundo-dev-8ef38  dateKey=2026-08-22  weekKey=2026-W34
OK        | W10-1 records  status+dateKey                          | count=0
OK        | W10-2 records  status+weekKey                          | count=0
OK        | W10-3 students academicYear+isActive+grade             | count=0
INDEX-REQ | W11-1 students academicYear+grade+classNo+isActive  orderBy number | failed-precondition
INDEX-REQ | W11-2 students academicYear+grade+classNo           orderBy number | failed-precondition
OK        | W11-3 students academicYear+isActive+grade+classNo  (count)        | count=0
```

| 사실 | 함의 |
| --- | --- |
| 등식만 있는 질의는 전부 통과 | 복합 인덱스 불필요. W-10 §2.4의 판단이 실측으로 확인됐다 |
| **`orderBy`가 붙는 순간 갈린다** | 등식 3~4개 + 다른 필드 정렬 → Firestore가 복합 인덱스를 요구한다 |
| W11-1과 W11-2가 **서로 다른 인덱스** | `isActive`를 서버 질의에 넣느냐가 인덱스 1개를 가른다. §3이 이것으로 결정됐다 |
| W11-3은 통과 | **S4의 반별 카운트는 인덱스 없이 돈다** |

🔴 **`count=0`을 「실패」로 읽지 마라.** 복합 인덱스가 없으면 Firestore는 **데이터가 0건이어도**
`failed-precondition`을 던진다. 값이 돌아왔다는 것은 집계가 실제로 수행됐다는 뜻이다.

### 1-1. 프로브를 다시 쓸 일이 생기면 (W-13 이후)

W-10이 만든 `public/__w10probe.js`는 **고장 나 있었다.** `projectId` 자리에 웹 API 키(`AIza…`)를
넣어 존재하지 않는 프로젝트 경로로 질의를 쐈고, 세 줄이 전부
`Permission denied on resource project AIza…`로 죽었다. **규칙 거부가 아니다** — 규칙 거부는
`Missing or insufficient permissions`다. **W-11이 저장소에서 삭제했다**(`public/`에 두면 번들에 섞여 배포된다).

다시 만든다면 요구는 넷이다.

| # | 요구 | 이유 |
| --- | --- | --- |
| 1 | **앱이 초기화한 SDK 인스턴스**를 그대로 쓴다. `lib/firebase`의 `db`를 import한다 | config를 다시 조립하면 위와 같은 사고가 난다 |
| 2 | 🔴 **firestore 함수도 앱과 같은 모듈 인스턴스에서 가져온다** | `/@id/firebase/firestore`로 import하면 **Vite가 별도 사본을 만들어** `collection(db, …)`이 `invalid-argument`를 뱉는다(실제로 겪었다). 해시가 매번 바뀌므로 경로를 하드코딩하지 말고 `performance.getEntriesByType('resource')`에서 실제 적재된 `firebase_firestore.js?v={해시}`를 찾아 그것을 import한다 |
| 3 | 머리글에 **`db.app.options.projectId`** 를 찍는다 | `sundo-dev-8ef38`이 아니면 그 실행은 무효다 |
| 4 | 실패를 **세 갈래**로 분류한다 — `INDEX-REQ`(`failed-precondition`) / `RULES`(`permission-denied`) / `OTHER` | 지난번은 셋을 전부 `FAIL`로 뭉갰다 |

## 3. `isActive`를 서버 질의에서 뺐다 — 근거와 남는 부채

### 3-1. 두 안과 실측

| 안 | 질의 | 필요한 인덱스 |
| --- | --- | --- |
| A — 서버에서 거른다 | `academicYear` + `grade` + `classNo` + **`isActive`** + orderBy `number` | **PRD §9.5에 없는 신규 인덱스**(W11-1) |
| **B — 클라이언트에서 거른다 (채택)** | `academicYear` + `grade` + `classNo` + orderBy `number` | **IX-08 그대로**(W11-2) |

**B로 갔다. 근거 셋.**

1. **IX-08이 정확히 이 조합이다.** 새 인덱스를 만들지 않고 PRD 설계를 그대로 쓴다. A로 가면 §9.5에 없는 인덱스가 하나 늘고 PRD 이탈이 생긴다.

3. **S4의 반별 카운트는 서버에서 `isActive`를 쓴다**(W11-3 = IX-09, 인덱스 없이 통과). 거르는 위치가 달라도 **결과는 같다** — 스텁에 활성 9 + 비활성 3을 넣어 **S4 카운트 9 == S5 행 수 9**를 실측으로 잠갔다(보고서 DoD 12).

### 4-1. 판정 근거 — catch-all 테스트

**PRD에 없는 임의 컬렉션(`zzruleprobe` · `nosuchcollection`)이 읽힌다.**
§9.6 본편은 컬렉션별 명시 `match`만 두고 catch-all이 없으므로 이 경로는 **거부돼야 한다.**
읽힌다는 것은 **W-04 §5의 `match /{document=**}` 임시 규칙이 살아 있다**는 뜻이고,
그렇다면 3건이 반영돼 있더라도 catch-all에 덮여 **무의미하다.**

> ⚠ `inviteCodes` list와 `auditLogs` 읽기가 통과하는 것은 **판별 근거가 되지 못한다.**
> 지금 계정이 `head`라 두 규칙 아래서 모두 허용된다. **catch-all 테스트만이 결정적이다.**

### 4-2. 왜 지금 급하지 않고, 언제 급해지나

**3건이 하나도 없어도 S2는 지금 동작한다** — 임시 규칙이 전부 허용하기 때문이다.
🔴 **W-15가 §9.6 본편을 배포하는 순간, 3건이 없으면 S2가 전부 막힌다.**
그때 발견하면 원인이 「이번에 배포한 §9.6」인지 「그전부터 없던 3건」인지 갈라내는 데 회차를 하나 더 쓴다.

**W-15 배포 직전 체크리스트에 3건을 반드시 넣어라.** 배포 직후에는
`database_ToDo/W-09.md` §4-2의 조작 3개를 그대로 돌린다.
