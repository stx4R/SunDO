## 2. 🔴 마이그레이션 — 이미 실행했다

### 2.1 무엇을 했나

`node scripts/migrate-duty-meals.mjs --commit` — 🔴 **dry-run으로 요약을 보고 사용자
확인을 받은 뒤** 실행했다. 대상 **2건**(`2026-W34`·`2026-W35`).

| 옛 필드 (🔴 **그대로 남아 있다**) | → 새 필드 (신설) |
| --- | --- |
| `assignments` `{mon:[uid],…}` | `assignmentsByMeal` `{mon:{lunch:[uid],dinner:[]},…}` |
| `assigneeNames` `{mon:[name],…}` | `assigneeNamesByMeal` `{mon:{lunch:[name],dinner:[]},…}` |
| `patrolTime` `"07:50"` | `patrolTimeByMeal` `{lunch:"07:50",dinner:null}` |
| `patrolPlace` `"중앙 현관"` | `patrolPlaceByMeal` `{lunch:"중앙 현관",dinner:null}` |

**왜 새 이름인가** — 넷 다 **타입이 바뀐다**(string → map · 배열 → map). 같은 이름으로
타입을 바꾸면 옛 앱이 `[object Object] · [object Object]`를 그리거나(`patrolLine`)
요일 행을 **조용히 비운다**(`toNameMap`의 `if (!Array.isArray(value)) continue`).
🔬 둘 다 코드에서 확인했다.

### 2.2 확인된 것

- ✅ 옛 필드 4개가 **전부 그대로** (`inspect-firestore.mjs`로 재확인)
- ✅ **멱등하다** — 다시 돌리면 「새 필드 4개가 이미 있다」로 건너뛴다
- ⚠ `inspect-firestore.mjs`가 새 필드를 **「여분」으로 표시**한다. 그 스크립트는 §9.3.6의
  10필드만 아는 W-16D 산출물이라 **정상이다** — 고치지 않았다(이 회차 범위 밖)

### 2.3 🔴 되돌리는 법

```bash
node scripts/migrate-duty-meals.mjs --revert            # dry-run
node scripts/migrate-duty-meals.mjs --revert --commit   # 실행
```

**새 필드 4개를 지운다. 옛 필드는 손대지 않았으므로 옛 앱이 그대로 돌아온다.**

⚠ 🔴 **앱을 배포한 뒤에 되돌리면** 새 앱이 새 필드를 못 찾는다 — 그때는 읽기 계층의
폴백(`promote()`)이 **옛 편성을 중식으로 승격**해 읽으므로 화면이 비지는 않는다.
다만 **부장이 앱에서 편성한 석식이 사라진다.** 되돌리기는 앱 롤백과 함께 하라.

### 2.4 🔴 배포 직후 부장이 해야 할 일

마이그레이션은 **기계적이다** — `07:50`(등교 지도 시각)이 그대로 **중식 시간** 자리로
옮겨졌고 석식은 비어 있다. 스크립트가 값을 지어내지 않았다.

⇒ 🔴 **부장이 앱에서 S9 → `일정 편집`으로 실제 중식/석식 시각·장소·담당자를 넣어야 한다.**
그 전까지 S9는 「중식 07:50 · 중앙 현관」만 그리고 석식 줄은 **그리지 않는다**(정상).
