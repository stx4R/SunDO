### 🔴 **W-12 자신이 필요로 하는 인덱스는 0건이다** — 실측 근거

중복 검사 질의를 **등식(`in` 포함)만으로** 구성했기 때문이다. 스텁 하네스가 기록한 질의 로그 원문:

```json
{ "kind": "getDocs", "collection": "records",
  "wheres": [ { "field": "studentDocId", "op": "==", "value": "2026_20301" },
              { "field": "dateKey",      "op": "in", "value": ["2026-08-20", "2026-08-21"] } ],
  "orders": [] }
```

- `orders` 배열이 **비어 있다.** 범위 조건도 0개다.
- 등식 전용 질의는 자동 단일 필드 인덱스 병합으로 처리되며, **W-11이 IX-09에서 이미 실측한 성질**이다
  (`database_ToDo/W-11.md` §1 W11-3 — 등식 4개 조합이 복합 인덱스 없이 동작).
- ⚠ **다만 「인덱스 없이 실제로 도는가」를 실 Firestore에서 확인하지는 못했다**(쓰기 0건 제약).
  질의 **형태**만 실측이고, 인덱스 불요는 위 선례에 근거한 추론이다.
  **명부 시딩 후 실기기 1회 저장으로 확인해 주기 바란다** — 실패하면 `failed-precondition`이 뜨고,
  그때도 저장은 막히지 않는다(§3.8 설계).

## 3. 🔴 `users.recordCount` — 규칙 개정 판단 요청

**현상: 아무도 올리지 않으므로 `recordCount`는 영원히 `0`이다. 이것은 버그가 아니라 결정이다.**

| 항목 | 내용 |
| --- | --- |
| 충돌 | §9.3.1은 `recordCount`를 「누적 작성 건수」로 규정한다. 그러나 §9.6 `users` update 행과 부록 B의 **본인 자기 갱신 허용 키에 `recordCount`가 없다**(`lastActiveAt`·`notificationPrefs`·`displayNameRaw`·본인 탈퇴뿐). W-08 요청서 조건 6도 `recordCount` 불변을 명시한다 |
| 지금 넣으면 | W-04 임시 catch-all 규칙 덕에 **통과한다.** 그러다 W-15가 §9.6 본편을 배포하는 순간 **기록 저장이 통째로 막힌다** — 배치 안의 `users` 쓰기가 거부되면 `records` 쓰기도 함께 죽는다 |
| W-12의 선택 | **`records` 문서 1건만 쓴다.** `users`·`auditLogs`·`departments`에 한 글자도 쓰지 않는다 |
| 판단 요청 | **A안** §9.6 자기 갱신 허용 키에 `recordCount`를 추가하고 「+1만 허용」 조건을 건다 (`request.resource.data.recordCount == resource.data.recordCount + 1`). 클라이언트가 임의 값을 못 넣게 하려면 이 조건이 필수다<br>**B안** 프로파일 B(`beforeCreate` 트리거 또는 Callable)로 미룬다. 서버가 올리므로 규칙을 열지 않아도 된다<br>**C안** `recordCount` 필드를 §9.3.1에서 **삭제**하고, 필요할 때 `records` 집계 질의로 센다 |
| 추천 | **A안**. 실사용 규모(약 40명)에서 집계 질의보다 싸고, +1 제약이 규칙 한 줄로 표현된다 |

⚠ **`users` 쓰기가 이번 회차에도 1건 관측된다** — `users/{uid}.lastActiveAt`이다.

## 5. 🔴 서버 거부가 클라이언트에 도달하지 않는다 — W-17로 넘긴다

**측정으로 확정한 사실이다**(보고서 §1-3):

- `db`는 `persistentLocalCache`로 초기화돼 있다.
- `setDoc()`이 돌려주는 Promise는 **서버가 ack/거부할 때까지 resolve되지 않는다.**
  SDK 원문: 「The userCallback is resolved once the write was acked/rejected by the backend」
- 그래서 W-12는 `await`하지 않는다. **기다리면 오프라인에서 스피너가 영원히 돈다**(W-08에서 실제로 터진 실패).

**파급:**

| 상황 | 지금 일어나는 일 |
| --- | --- |
| 규칙 위반으로 서버가 거부 | 시트는 이미 닫혔고 토스트는 「기록 저장됨」이 떴다. 거부는 **콘솔 경고 1줄**로만 남는다(`[records] 전송 실패`) |
| BR-39 시각 위조(E-2002 ±5분) | **프로파일 A의 클라이언트는 서버 시각을 알 수 없다.** Rules의 `occurredAt <= request.time`이 최종 방어이고, 그 거부도 위와 같은 이유로 사용자에게 도달하지 않는다 |
| 오프라인 큐 | 조용히 실패한 건이 큐에 남아 있는지 사용자가 알 방법이 없다 |

→ **W-17(오프라인 큐·전송 대기 배지·TS-16)이 이어받을 항목이다.**
W-15 규칙 배포 직후가 이 경로가 처음으로 실제 문제가 되는 시점이므로, **W-15 검수 시 콘솔 경고를 함께 봐 주기 바란다.**
