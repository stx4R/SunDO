## 1. 🔴 서비스 워커 해제 절차 — 배포보다 먼저 적는다

### 1.1 이 워커가 무엇을 하는가 (그리고 하지 않는가)

`public/sw.js`는 **아무것도 캐시하지 않는다.** 캐시 전략은 W-20이다. 지금 하는 일은 셋뿐이다.

1. 버전이 붙은 캐시 이름(`sundo-shell-v0.12.0`)을 **정의만** 한다
2. 활성화될 때 **그 이름이 아닌 캐시를 전부 지운다**
3. 앱이 보낸 `SKIP_WAITING` 메시지를 받으면 즉시 활성화한다

⇒ **낡은 워커가 남아도 콘텐츠는 네트워크에서 온다.** 지금은 「붙박이」의 증상이 없다.
🔴 **그래서 더 위험하다** — W-20이 캐시를 붙이는 순간 그 사실이 바뀐다.

### 1.2 사용자가 직접 지우는 법 (Android Chrome · 데스크톱 Chrome)

1. 주소창에 `chrome://serviceworker-internals` 입력
2. `sundo-dev-8ef38.web.app` 항목을 찾아 **`Unregister`**
3. 이어서 사이트 데이터를 지운다 — 주소창 좌측 자물쇠(또는 ⓘ) → `쿠키 및 사이트 데이터` →
   `사이트 데이터 삭제`
4. 탭을 **전부 닫았다가** 다시 연다

**DevTools를 쓰는 경우**: `F12` → `Application` 탭 → 좌측 `Service Workers` →
`Unregister` → 좌측 `Storage` → `Clear site data`

### 1.3 iOS Safari

Safari에는 서비스 워커를 개별로 해제하는 UI가 없다.

1. 설정 → Safari → **고급** → **웹사이트 데이터** → `sundo-dev-8ef38.web.app` 스와이프 삭제
2. 홈 화면에 추가해 둔 아이콘이 있으면 **아이콘도 지우고 다시 추가**한다

### 1.4 🔴 원격으로 되돌리는 법 (개발자 쪽)

사용자에게 「지워 주세요」라고 말할 수 없는 상황을 위한 경로다. **워커를 없애지 말고,
자기를 지우는 워커를 배포한다.**

`public/sw.js`를 통째로 아래로 바꾸고 배포한다.

```js
self.addEventListener('install', () => self.skipWaiting())
self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const names = await caches.keys()
    await Promise.all(names.map((n) => caches.delete(n)))
    await self.registration.unregister()
    const clients = await self.clients.matchAll({ type: 'window' })
    for (const client of clients) client.navigate(client.url)
  })())
})
```

🔴 **`/sw.js`를 404로 만들지 마라.** 브라우저는 스크립트를 못 받으면 **기존 등록을 유지한다** —
지우려는 시도가 정확히 반대로 작동한다. 반드시 **위 내용의 파일을 같은 URL에 올려야** 한다.

⚠ `firebase.json`이 `/sw.js`에 `Cache-Control: no-cache`를 걸어 두었다. 이 경로가 실제로
도는 전제다 — 그 헤더를 지우지 마라.

### 1.5 배포 자체의 롤백

```
firebase hosting:rollback --project sundo-dev-8ef38
```

⚠ **이것은 서비스 워커를 지우지 않는다.** 직전 릴리스에 `sw.js`가 없었으면(= 이번이 첫 배포다)
`/sw.js`가 404가 되고 §1.4의 함정에 그대로 걸린다. **롤백은 §1.4를 대신하지 못한다.**

## 2. 🔴 배포 후 활성 `inviteCodes`를 내린다 — 검증이 끝나는 즉시

### 왜

지시서 §0.3 결정 1 안전 조건 2다. 지금 겹치는 조건이 셋이다.

| 조건 | 상태 |
| --- | --- |
| 공개 URL | 🔴 **이번 배포로 생긴다** |
| 활성 가입 코드 | 🔴 **있다** |
| 시도 횟수 제한 | 🔴 **없다** — App Check도 BR-30 레이트 리밋도 W-22다 |

가입 코드는 `^[A-Z]{4}-[0-9]{4}$`에서 혼동 문자 `I`·`O`를 뺀 형식이다.
🔴 **`inviteCodes` 문서 ID가 코드 문자열 자체다**(W-08 안 1) — 즉 **단건 `get`으로 추측을 검증할 수 있다.**
막는 것이 아무것도 없는 상태에서 URL이 밖으로 나가면 그것이 곧 대입 시도 경로가 된다.

⚠ 코드를 맞혀도 **부장 승인**이 남아 있어 데이터에는 닿지 못한다. 내리는 이유는
「승인 대기 문서가 쌓이는 것」과 「부장에게 가짜 신청이 가는 것」을 막기 위해서다.

### 절차 (콘솔)

1. Firebase 콘솔 → 프로젝트 **`sundo-dev-8ef38`** → Firestore Database
2. `departments` → `dshs-jayul` → 하위 컬렉션 `inviteCodes`
3. `isActive: true`인 문서를 **전부** 찾는다
4. 각 문서에 대해
   - `isActive` → **`false`**
   - `revokedAt` → **현재 시각**(타임스탬프)
5. 🔴 **문서를 지우지 마라.** `users.inviteCodeId`가 이 문서를 가리킨다 — 지우면 가입 이력의
   참조가 끊긴다(§9.3.1)
6. `departments/dshs-jayul`의 `activeInviteCodeId`를 **`null`**로 둔다

### 되돌리기

다시 검증할 일이 생기면 S8 관리 화면의 **코드 재발급**(OP-10)을 쓴다.
손으로 `isActive`를 되돌리지 마라 — `useCount`·`expiresAt`이 과거 값 그대로다.

## 3. Firestore 리전 — ✅ 닫혔다. 콘솔 작업이 필요 없다

W-18이 올린 확인 1건이다. **콘솔에 들어가지 않고 CLI로 확정했다.**

```
$ firebase firestore:databases:get "(default)" --project sundo-dev-8ef38 --json
  "locationId": "asia-northeast3",
  "type": "FIRESTORE_NATIVE",
  "createTime": "2026-08-20T15:50:01.343577Z"
```

⇒ **`asia-northeast3` (서울) — 국내다.**

| 결과 | 내용 |
| --- | --- |
| 국외 이전 고지 | **불필요** |
| `src/lib/policy.ts` | **수정 0줄** — 이 문단은 애초에 위치를 주장하지 않는다. 그대로가 맞다 |
| `database_ToDo/W-18.md` §1 | **닫힘.** 이 문서가 답이다 |

⚠ **Hosting은 별개다.** Firebase Hosting은 전 세계 CDN에서 정적 파일을 준다. 다만 그
파일에는 개인정보가 없다(앱 셸·글꼴·아이콘). **개인정보가 사는 곳은 Firestore이고 그것이 서울이다.**
