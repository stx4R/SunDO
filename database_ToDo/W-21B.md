## 1. 🔴 배포 순서 — 이 회차의 급소

### 1.1 왜 순서가 문제인가

§18.4의 전제는 「Rules·인덱스는 앱보다 **먼저**」다. **앱이 먼저 나가면 아직 없는 권한을
두드리기 때문**이다.

🔴 **그 논리가 이 회차의 절반에서 반대로 선다.**

| 규칙 변경 | 방향 | 먼저 배포하면 | 그래서 |
| --- | --- | --- | --- |
| `records` update (기능 9) | **넓힌다** | 옛 앱은 그 권한을 쓰지 않는다 — **아무것도 안 깨진다** | §18.4 그대로 **앱보다 먼저** |
| `inviteCodes` create/update (기능 12) | 🔴 **좁힌다** | 옛 앱의 화면에는 여전히 `코드 재발급` pill이 보이는데 **누르면 실패한다** | 🔴 **앱보다 뒤** |
| `departments` update (기능 12) | 🔴 **좁힌다** | 같음 — 재발급 배치의 3연산이 죽는다 | 🔴 **앱보다 뒤** |

⚠ 🔴 **W-20 §3.2가 「같은 논리가 반대로 서는」 예를 이미 남겼다. 같은 형태다** —
규칙이 *무엇을 하느냐*가 아니라 **틀렸을 때 무엇이 깨지느냐**가 순서를 정한다.

### 1.2 🔴 그래서 규칙을 **두 번** 배포한다

| 순서 | 무엇 | 파일 상태 |
| --- | --- | --- |
| ① | **넓히는 규칙만** 배포 (`records`) | `firestore.rules`에서 기능 12 블록 2개를 **옛 상태로 되돌린 임시본** |
| ② | **앱 배포** (`v0.15.0`) | — |
| ③ | 🔴 **좁히는 규칙 배포** (`inviteCodes` · `departments`) | 저장소의 `firestore.rules` **원본 그대로** |
| ④ | 스모크 (§3) | — |

**①의 임시본을 만드는 법** — 저장소 규칙에서 아래 두 곳만 옛 형태로 되돌린다.

```
// (가) inviteCodes
allow create: if isDev() && request.resource.data.code == codeId;
allow update: if request.resource.data.code == codeId
  && (isDev()
      || (isHead() && request.resource.data.diff(resource.data).affectedKeys()
                        .hasOnly(['useCount'])));
   ↓ 임시로 되돌린다
allow create: if isHead() && request.resource.data.code == codeId;
allow update: if isHead() && request.resource.data.code == codeId;

// (나) departments
allow update: if
     (isDev() && … .hasOnly(['activeInviteCodeId', 'updatedAt']))
  || (isHead() && … .hasOnly(['headUid', 'updatedAt']));
   ↓ 임시로 되돌린다
allow update: if isHead();
```

🔴 **임시본을 커밋하지 마라.** 배포 후 `git checkout -- firestore.rules`로 되돌린다 —
이 파일은 **이미 커밋된 상태**이므로 그 명령이 안전하다(W-21 §5 함정 6의 전제와 반대다.
그때는 커밋 전이라 위험했다).

### 1.3 ⚠ ②와 ③ 사이의 창

②와 ③ 사이에는 **새 앱 + 옛(넓은) 규칙**이 잠깐 공존한다. 그 동안 부장은 재발급 pill을
**보지 못하지만**(새 앱이 숨긴다) 규칙은 아직 그를 막지 않는다.

🔴 **지금은 그 창이 무해하다** — 실사용자가 **3명이고 전부 테스트 계정**이며 배포 URL이
공유되지 않았다. 그 사실이 이 순서를 허락하는 근거다.

⚠ 🔴 **실사용이 시작된 뒤에는 이 판단을 다시 해야 한다.** 그때는 ②③ 사이에 사람이
들어올 수 있고, 창을 없애려면 **①에서 좁히는 규칙까지 한 번에 배포하고 옛 앱의 실패를
감수**하거나(부장이 pill을 눌렀다가 실패한다) **점검 모드(`meta/appConfig`)로 막고**
바꿔야 한다. 보고서 §9에 그대로 올려 두었다.

### 1.4 확인란

- [ ] ① 넓히는 규칙만 배포했다 (임시본)
- [ ] ② 앱 `v0.15.0` 배포했다
- [ ] ③ 좁히는 규칙 배포했다 (저장소 원본)
- [ ] 🔴 `git status`가 깨끗하다 (임시본이 남지 않았다)

### 4.2 콘솔 우회 절차 — 코드를 손으로 만든다

- 🔴 **문서 ID가 곧 코드 문자열이다.** 자동 ID를 쓰지 마라.

**② 기존 활성 코드를 내린다**(BR-11 — 활성 코드는 최대 1개)

## 5. 🔴 삭제한 기록을 되돌리는 절차 (검증용)

### 5.1 먼저 알아 둘 것

🔴 **실기기에서 삭제를 확인하면 그 기록은 진짜로 `deleted`가 된다.**
목록·통계에서 즉시 빠지고 **앱에는 되돌리는 경로가 없다** — 규칙이 `active → deleted`
한 방향만 열려 있다(`RX-10`이 그것을 잠근다).

⇒ 🔴 **삭제를 검증하기 전에 이 절차를 먼저 읽어라.**

### 5.2 되돌리는 법 — 콘솔에서

Firebase 콘솔 → Firestore Database → 데이터 탭 → `records` → **그 문서**.

| 필드 | 되돌릴 값 |
| --- | --- |
| `status` | `deleted` → **`active`** |
| `deletedBy` | 필드를 **삭제**한다 (또는 `null`) |
| `deletedAt` | 필드를 **삭제**한다 (또는 `null`) |

🔴 **`auditLogs`의 `RECORD_DELETE` 로그는 지우지 마라.** 감사 로그는 수정·삭제가
전면 금지(§14.5 3번)이고 콘솔로 지우면 그 원칙이 무너진다. **삭제했다가 되돌렸다는
사실이 그대로 남는 것이 옳다.**

### 5.3 어느 문서인지 찾는 법

삭제 직전에 **학생 이름 + 시각**을 적어 두고, 콘솔에서 `records`를 `status == deleted`로
거른 뒤 `studentName`·`occurredAt`으로 찾는다.
🔴 **검증용으로 지울 기록을 미리 하나 정해 두는 편이 훨씬 쉽다.**

## 6. `inviteCodes` 재발급 왕복 (검증용)

기능 12가 제대로 좁혀졌는지 재려면 **Dev 계정으로** 한 바퀴 돈다.

1. `dev`로 로그인 → S8 → `코드 재발급` → MD-01 확인 → `새 코드가 발급되었습니다`
2. 🔴 콘솔에서 확인 — 옛 코드가 `isActive: false` + `revokedAt` 세팅 · 새 코드 문서 생성 ·
   `departments.activeInviteCodeId`가 새 값
3. **부장으로 바꿔 로그인** → S8 → 🔴 **pill이 없어야 한다** · `복사`만
4. (선택) 새 코드로 가입 신청 1건 → **부장이 승인** → 승인이 성공해야 한다(§3 스모크 8번)
5. 🔴 **끝나면 다시 내린다** — `dev`로 한 번 더 재발급해 검증용 코드를 만료시킨다

⚠ **부장 계정으로 재발급을 시도해 「실패하는지」 보려 하지 마라.** 새 앱은 버튼을
렌더하지 않으므로 정상 경로로는 도달할 수 없다. 규칙 쪽은 `C-1`·`C-3`·`B-3`·`P-5`가
에뮬레이터에서 이미 잠갔다.
