## 1. 🔴 배포 순서 — 인덱스가 **먼저**다

§18.4는 「Rules·인덱스 배포는 앱 배포보다 **먼저**」로 규정한다.
**앱이 먼저 나가면 아직 없는 권한·인덱스를 두드려 사용자에게 오류로 보인다.**
같은 이유가 이 문서 안에서도 한 번 더 적용된다 — **인덱스가 규칙보다 먼저**다.

| 순서 | 무엇 | 왜 |
| --- | --- | --- |
| ① | **인덱스** `firestore.indexes.json` | 빌드에 **수 분**이 걸린다. 콘솔에서 `사용 설정됨`이 될 때까지 질의가 `failed-precondition`이다 |
| ② | 인덱스 상태가 **`사용 설정됨`** 이 될 때까지 대기 | 규칙만 먼저 배포하면 S7이 「권한은 있는데 인덱스가 없어」 죽는다 — 원인 진단이 두 배로 어려워진다 |
| ③ | **규칙** `firestore.rules` | 여기서부터 catch-all이 사라진다 |
| ④ | 즉시 §4 스모크 7건 | 🔴 실패하면 **§3으로 1분 안에 되돌린다** |

## 2. 명령 전문 — 저장소 루트에서 그대로 붙여넣는다

### 2.1 로그인·프로젝트 선택 (최초 1회)

```bash
npx firebase login
npx firebase projects:list          # sundo-dev-8ef38 이 보이는지 확인
npx firebase use default            # .firebaserc 의 별칭 → sundo-dev-8ef38
```

> `.firebaserc` 에 `default = sundo-dev-8ef38` 이 이미 적혀 있다.
> 🔴 **`sundo-c5095` · `sundo-dev`(구 프로젝트)를 고르지 마라** — Firestore 미생성 상태다(PRD 말미).

### 2.2 ① 인덱스 배포

```bash
npx firebase deploy --only firestore:indexes
```

확인: **콘솔 → Firestore Database → 색인** 에서 🔴 **3건**이 `사용 설정됨`이 될 때까지 기다린다.

| --- | --- |
| IX-01 | `records`: `academicYear ASC, status ASC, occurredAt DESC` |
| IX-02 | `records`: `academicYear ASC, status ASC, reasonCode ASC, occurredAt DESC` |
| 🔴 **IX-08** | `students`: `academicYear ASC, grade ASC, classNo ASC, number ASC` |

> 🔴 **IX-08은 W-16D에서 추가됐다.** W-16 작성 시 §8 표가 W11-2(S5 `orderBy`)와 W11-3(S4 카운트)을
> 한 칸에 뭉개 누락됐다. `src/lib/roster.ts`의 `fetchStudents`가 등식 3개 + `orderBy('number')`라

### 2.3 ③ 규칙 배포

```bash
npx firebase deploy --only firestore:rules
```

확인: **콘솔 → Firestore Database → 규칙** 의 게시 시각이 방금인지, 본문 첫 줄이
`// SunDO — Firestore Security Rules` 인지 본다.

## 3. 🔴 1분 롤백 절차 — 스모크가 실패하면 **즉시** 실행한다

§18.4는 「Rules 롤백은 Git 이력에서 이전 버전 재배포」로 규정하는데,
🔴 **`firestore.rules`가 `v0.9.0`의 첫 커밋이라 이력에 이전 버전이 없다.**
그래서 W-04 임시 catch-all을 **`firestore.rules.catchall`로 보존**해 두었다.

```bash
# 1) 현재 규칙을 잃지 않게 옆으로 치운다
cp firestore.rules firestore.rules.broken

# 2) catch-all 을 규칙 자리에 놓는다
cp firestore.rules.catchall firestore.rules

# 3) 되돌린다 (인덱스는 건드리지 않는다 — 인덱스는 앱을 죽이지 않는다)
npx firebase deploy --only firestore:rules

# 4) 반드시 원복한다. 저장소에 catch-all 이 규칙 자리로 남으면 안 된다
cp firestore.rules.broken firestore.rules && rm firestore.rules.broken
```

> 🔴 **`firebase.json`은 `firestore.rules`만 가리킨다.** `firestore.rules.catchall`을
> 가리키게 바꾸지 마라 — 다음 배포가 조용히 catch-all을 올린다.
>
> 🔴 **되돌린 상태로 오래 두지 마라.** catch-all은 역할·상태 조건을 **하나도** 갖고 있지 않다.
> `@dshs.kr` 계정이면 누구나 전 컬렉션을 읽고 쓴다. 무엇이 실패했는지 §5의 테스트에
> 케이스로 옮기고, 고친 뒤 다시 배포한다.

## 6. 🔴 BR-18(부장 정확히 1명) — 규칙이 어디까지 보장하나

`database_ToDo/W-15B.md` §4가 「`headUid`를 단일 진실로 삼고 `users.role=='head'`를
파생으로 강제할 것인가」를 판단 요청으로 남겼다. **채택하지 않았다.**

**이유(에뮬레이터 실측 — 보고서 §2.3 Q-2)**: 규칙 안 `get()`은 **배치 이전 상태**를 본다.
양도 배치는 `users/{대상}.role='head'`와 `departments.headUid={대상}`을 **같은 배치**에 담으므로,
`users` 규칙이 `get(departments).headUid == uid`를 요구하면 평가 시점에는 아직 **현 부장**이라
**자기 배치를 스스로 거부한다.** 그 안은 양도와 양립하지 않는다.

**대신 규칙이 실제로 보장하는 것**

| 층 | 무엇 |
| --- | --- |
| 1 | `role` 변경은 **`head`·`dev`만**(T-4·T-5·T-6 거부) |
| 2 | 부장은 **자기 역할을 직접 못 바꾼다**(T-7 거부) — 단 **`head → member` 한 전이**만 열려 있다(T-2 통과, 양도의 강등) |
| 3 | 클라이언트 배치의 **원자성**(부분 성공 없음). 🔬 **규칙 계층에서도 성립함을 실측했다** — 3연산 중 1개가 거부되면 남은 문서 **0/2**다(보고서 §2.3 Q-3) |
| 4 | **BR-23 Dev 복구 경로**(양도 3연산 — B-6 통과) |

**남는 구멍 2가지 — 알고 남긴다**

1. **동시 양도 경쟁.** 두 배치가 각각 원자적이어도 「A→B」와 「A→C」가 겹치면 부장 2명이 될 수 있다.
   Rules는 집합을 셀 수 없어 막지 못한다.
2. **양도 없이 혼자 내려가는 head.** `role: head → member` 단독 update는 통과한다(부장 0명).
   규칙은 같은 배치의 형제 연산을 볼 수 없기 때문이다.

→ 🔴 **둘 다 §11.3의 `transferHeadRole` Cloud Function이 닫는다(v1.2).** §7 이관.
   그때까지는 **운영 규율**(양도는 부장 본인이 한 번에 한다)과 **감사 로그**가 사후 추적을 맡는다.
