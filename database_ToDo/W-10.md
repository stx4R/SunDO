## 1. 🔴 요청 1 — §2.3 인덱스 실측 결과

### 1-1. 무엇을 물었나

S3 홈이 쏘는 질의는 **세 개**이고 전부 **등식(equality)뿐**이다.

| # | 컬렉션 | 조건 | PRD가 설계해 둔 인덱스 |
| --- | --- | --- | --- |
| 1 | `records` | `status == 'active'` **and** `dateKey == '{오늘}'` | IX-03 (`status, dateKey`) |
| 2 | `records` | `status == 'active'` **and** `weekKey == '{이번 주}'` | IX-04 (`status, weekKey`) |
| 3 | `students` | `academicYear == 2026` **and** `isActive == true` **and** `grade == n` | IX-09 |

셋 다 `getCountFromServer()`(집계 질의)로 나간다.
**복합 인덱스가 필요한데 없으면 Firestore는 데이터가 0건이어도 `failed-precondition`을 던진다.**
그래서 `records`·`students`가 비어 있는 지금도 판별이 된다.

### 1-2. 실측 결과

✅ **측정 완료.** st4R 환경(`sundo-dev-8ef38` · 부장 계정 · `records`·`students` 공란)에서
**앱이 초기화한 SDK 인스턴스**로 직접 쐈다.

```
project=sundo-dev-8ef38  dateKey=2026-08-22  weekKey=2026-W34
OK        | W10-1 records  status+dateKey                          | count=0
OK        | W10-2 records  status+weekKey                          | count=0
OK        | W10-3 students academicYear+isActive+grade             | count=0
INDEX-REQ | W11-1 students academicYear+grade+classNo+isActive  orderBy number | failed-precondition
INDEX-REQ | W11-2 students academicYear+grade+classNo           orderBy number | failed-precondition
OK        | W11-3 students academicYear+isActive+grade+classNo  (count)        | count=0
```

| 행 | 회차 | 판정 |
| --- | --- | --- |
| W10-1 · W10-2 · W10-3 | **W-10(S3)** | **인덱스 불필요.** 세 질의 전부 인덱스 없이 집계가 수행됐다 |
| W11-1 · W11-2 | W-11(S5) | **인덱스 필요.** `orderBy('number')`가 붙어 `failed-precondition` |
| W11-3 | W-11(S4) | 인덱스 불필요. 반별 카운트는 그대로 돈다 |

🔴 **`count=0`을 「실패」로 읽지 마라.** 복합 인덱스가 없으면 Firestore는 **데이터가 0건이어도**
`failed-precondition`을 던진다. 값이 돌아왔다는 것은 집계가 실제로 수행됐다는 뜻이다.

🔴 **그래도 PRD §9.5의 IX-03·IX-04·IX-09를 지우지 마라.** 「없어도 된다」는 것은
**지금 S3가 쏘는 등식 전용 모양에 한정된 사실**이다. W11-1·W11-2가 보여주듯 정렬이 붙는 순간 갈린다.

**W-11이 요청하는 인덱스는 `database_ToDo/W-11.md`에 따로 있다**(IX-08 1건).

### 1-2-1. 🔴 이 값은 `public/__w10probe.js`로 잰 것이 아니다 — 그 프로브는 고장 나 있었다

W-10이 남긴 프로브는 **`projectId` 자리에 웹 API 키(`AIza…`)를 넣었다.** 존재하지 않는 프로젝트
경로로 질의가 나가 세 줄 전부 `Permission denied on resource project AIza…`로 죽었다.
**규칙 거부가 아니다** — 규칙 거부는 `Missing or insufficient permissions`다.
`public/`에 두면 번들에 섞여 배포되므로 **W-11이 삭제한다.**

다시 만들 일이 생기면(W-13 이후) 요구는 넷이다.

| # | 요구 | 이유 |
| --- | --- | --- |
| 1 | 앱이 초기화한 SDK 인스턴스를 그대로 쓴다(`lib/firebase`의 `db`를 import) | config를 다시 조립하면 위와 같은 사고가 난다 |
| 2 | 🔴 firestore 함수도 **앱과 같은 모듈 인스턴스**에서 가져온다 | `/@id/firebase/firestore`로 import하면 Vite가 별도 사본을 만들어 `collection(db, …)`이 `invalid-argument`를 뱉는다(실제로 겪었다). 해시가 매번 바뀌므로 경로를 하드코딩하지 말고 `performance.getEntriesByType('resource')`에서 실제 적재된 `firebase_firestore.js?v={해시}`를 찾아 import한다 |
| 3 | 머리글에 `db.app.options.projectId`를 찍는다 | `sundo-dev-8ef38`이 아니면 그 실행은 무효다 |
| 4 | 실패를 **세 갈래**로 분류한다 — `INDEX-REQ`(`failed-precondition`) / `RULES`(`permission-denied`) / `OTHER` | 지난번은 셋을 전부 `FAIL`로 뭉갰다 |

### 1-3. 이 결과로 무엇을 하나

- **`firestore.indexes.json` 작성 판단은 W-15가 한다.** 이 문서는 사실만 넘긴다.
- 🔴 **필요 없다는 결과가 나와도 PRD §9.5를 고치지 않았다.** 인덱스 설계표는 그대로 둔다 —
  `records`에 문서가 쌓이고 W-13(S7 기록 조회)이 정렬·범위 조건을 붙이는 순간 필요해질 수 있다.
- `failed-precondition`이 나왔다면 오류 메시지에 **인덱스 생성 링크가 그대로 들어 있다.**
  그 링크를 열면 콘솔이 필드 조합을 미리 채운 생성 화면을 띄운다 — 그대로 만들면 된다.

## 4. 검증 방법 — 무엇을 보면 성공을 아나

### 4-1. 인덱스를 만든 뒤 (§1이 「필요」로 나온 경우에만)

| # | 확인 | 성공 | 실패하면 |
| --- | --- | --- | --- |
| 1 | 콘솔 **Firestore → 색인 → 복합** 탭에서 상태가 `사용 설정됨` | 초록. `빌드 중`이면 기다린다 | `빌드 중`인 동안 질의는 계속 `failed-precondition`이다 |
| 2 | 앱 `/`(S3)에 로그인해 들어간다 | 통계 카드 2장에 **숫자**가 뜬다(`0 건`이어도 성공이다) | 수치가 `-` + `현황을 불러오지 못했습니다. 당겨서 새로고침` |
| 3 | DevTools 콘솔 | Firestore 오류 0건 | `The query requires an index` 문구가 남아 있으면 인덱스 조합이 다르다 |

🔴 **`0 건`과 `-`를 헷갈리지 마라.** `0 건`은 「조회 성공 · 기록 없음」이고 `-`는 「조회 실패」다.
코드가 둘을 절대 뭉개지 않도록 만들어 뒀다(`src/lib/stats.ts`의 `{ ok | failed }` 유니온).
