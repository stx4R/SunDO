# W-08 — Security Rules 요청서 (규칙 작성·배포는 **W-15**)

작업 지시서: `prompts/W-08.md` §10 · 보고서: `reports/W-08.md`

이 문서는 **규칙 파일이 아니다.** W-08은 규칙을 쓰지도 배포하지도 않았다.
S2 가입 신청이 실제로 동작하려면 규칙에 **무엇이 왜 필요한지**만 적는다.
실제 작성·배포는 W-15가 소유한다.

> ⚠ **지금 상태로는 S2가 동작하지 않는다.**
> 콘솔의 현재 규칙은 W-04 §5의 임시 규칙(`@dshs.kr`이면 전부 허용)이라 **우연히 통과한다.**
> W-15가 §9.6 본편 규칙을 배포하는 순간, 아래 3건이 없으면 S2는 **전부 막힌다.**

## 1. 저장소의 규칙 파일 현황 — **없다**

| 확인 | 결과 |
| --- | --- |
| `firestore.rules`·`*.rules` | **0건** |
| `firebase.json` · `.firebaserc` | **없음** |
| 규칙의 현재 정본 | **Firebase 콘솔의 텍스트**(W-04 §5에서 사람이 붙여 넣은 임시 규칙) |

즉 규칙은 아직 **코드로 관리되지 않는다.** W-15가 `firestore.rules`를 저장소에 만들고
`firebase deploy --only firestore:rules`로 배포하는 체계를 세울지도 함께 정해야 한다.
지금은 콘솔에서 직접 고치는 수밖에 없다.

## 2. 필요한 변경 3건

### 2-1. `inviteCodes` — 인증된 `@dshs.kr`의 **단건 `get`만** 연다

| 항목 | 내용 |
| --- | --- |
| 대상 | `departments/{deptId}/inviteCodes/{codeId}` |
| 허용 | **`get`(단건 조회)만.** `request.auth != null` 且 이메일이 `.*@dshs[.]kr$` |
| 계속 금지 | **`list`(목록 조회)** · `create` · `update` · `delete` → `head`·`dev` 유지 |
| 추가 조건 | 쓰기 시 `request.resource.data.code == codeId`를 강제한다 |
| 없으면 무엇이 실패하나 | S2의 **변형 C·D 전부.** `존재하지 않는 코드입니다`·`만료된 코드입니다`를 만들 수 없어 형식 검사만 남는다. 앱은 조회 실패를 `permission-denied`로 받아 **상단 배너 `네트워크에 연결할 수 없습니다`**를 띄우고 멈춘다 — 즉 **정상 코드를 가진 신입 부원도 가입할 수 없다** |

**`get`과 `list`는 Firestore Rules에서 분리된 권한이다.** `allow read`로 뭉뚱그리면
목록 조회까지 열려 **유효한 코드 전체가 유출된다.** 반드시 `allow get`으로 쓴다.

```
// W-15 참고용 골격. 그대로 붙여 넣지 말고 §9.6 전체와 함께 작성한다.
match /departments/{deptId}/inviteCodes/{codeId} {
  allow get: if isSchoolAccount();                  // ← 이번 요청 (list 아님)
  allow list, create, update, delete: if isHeadOrDev();
}
```

> **왜 안전한가**: 문서 ID가 코드 문자열 자체(`inviteCodes/DJSN-2691`)라
> **코드를 이미 아는 사람만** 1건을 읽을 수 있다. 목록이 잠겨 있으므로 열거가 불가능하고,
> 코드를 아는 것 자체가 이미 가입 자격이다. 읽어서 얻는 정보도 `isActive`·`expiresAt`·
> `useCount`뿐이라 개인정보가 없다.
>
> 무차별 대입은 `[A-Z]{4}-[0-9]{4}` = 4,569,760가지이고, BR-30 레이트 리밋(24시간 3회)과
> App Check가 W-15에서 함께 붙는다. **그 둘이 이 요청의 짝이다** — 하나만 배포하지 마라.

### 2-2. §9.6 필수 조건 2 · BR-30a의 예외 목록에 `inviteCodes/{code}` 단건 `get`을 추가한다

| 항목 | 내용 |
| --- | --- |
| 대상 | §9.6 「필수 규칙 조건」 2번 문장, BR-30a |
| 현재 문언 | `status == 'active'`가 아닌 계정은 `users/{본인}`·`approvalRequests/{본인}` **외 어떤 문서도 읽을 수 없다** |
| 필요한 문언 | 위 두 가지 **＋ `departments/{deptId}/inviteCodes/{codeId}` 단건 `get`** |
| 없으면 무엇이 실패하나 | 2-1을 아무리 열어도 이 조건이 **뒤에서 다시 막는다.** S2 체류 계정(`noProfile`)은 정의상 `active`가 아니다 — 규칙 두 곳이 서로 어긋난 채 배포되면 원인을 찾기 어렵다 |

### 2-3. `users` update — 본인의 **재신청 전이**를 좁게 연다

| 항목 | 내용 |
| --- | --- |
| 대상 | `users/{uid}`의 `update`, 본인(`request.auth.uid == uid`)일 때 |
| 허용 | 아래 **6개 조건을 전부 만족할 때만** |
| 없으면 무엇이 실패하나 | **BR-61 재가입과 BR-28 재신청이 통째로 막힌다.** 탈퇴 계정의 재가입, 거절 계정의 `가입 코드 다시 입력`(S2-1 → S2) 버튼이 **끝까지 갔다가 마지막 쓰기에서 실패**한다. 사용자에게는 `가입 신청에 실패했습니다`만 보인다 |

| # | 조건 |
| --- | --- |
| 1 | 이전 `status`가 `withdrawn` **또는** `rejected` (`resource.data.status`) |
| 2 | 새 `status`가 `pending` |
| 3 | `role == 'member'` 강제 (BR-62 — 이전 역할을 복원하지 않는다) |
| 4 | `withdrawnAt == null` 且 `rejectReason == null` |
| 5 | `anonymizedAt == null` (BR-63 — 익명화된 계정은 재활성하지 않는다) |
| 6 | 변경 필드가 `status`·`role`·`withdrawnAt`·`rejectReason`·`inviteCodeId`·`name`·`nameSource`·`displayNameRaw`·`updatedAt`의 **부분집합**(`hasOnly`). `createdAt`·`recordCount`·`email`·`uid`는 **불변** |

**앱이 실제로 쓰는 필드는 6개다** — `status`·`role`·`withdrawnAt`·`rejectReason`·`inviteCodeId`·`updatedAt`.
`name`·`nameSource`·`displayNameRaw`는 허용 목록에만 두고 재신청 경로에서 쓰지 않는다
(확정된 이름은 본인이 바꿀 수 없다 — §8.2.3 · DR-13).

> 이 예외는 §9.6 요약표의 `users` update 행과 **정면으로 보이지만 충돌이 아니다.**
> §9.6은 스스로 "요약"이라 밝히고 BR-61·BR-28이 동작을 명시하므로,
> 요약이 구체 규칙을 누락한 것으로 본다(지시서 §0.2 결정 2).
> 같은 종류의 선례가 이미 있다 — **§9.6 요약표 ≠ 부록 B 전문**(W-04 부칙 §2).

## 3. 🔴 시딩 — 이미 만들어 둔 `inviteCodes` 문서가 있으면 **다시 만들어야 한다**

문서 ID 규칙이 바뀌었다.

| | 이전(PRD §9.3.3 예시) | 이번 확정 |
| --- | --- | --- |
| 경로 | `inviteCodes/code_2026_03` | **`inviteCodes/DJSN-2691`** |
| 즉 | 임의 ID + `code` 필드 | **문서 ID = 코드 문자열 그대로** |

- **`code` 필드는 그대로 남긴다.** 문서 ID는 경로이고 필드는 데이터다. 규칙이
  `request.resource.data.code == codeId`로 둘이 갈라지지 않게 강제한다.
- 콘솔에 이미 만든 코드 문서가 있다면 **ID를 코드 문자열로 바꿔 새로 만들고 옛 문서를 지운다.**
  Firestore는 문서 ID를 바꿀 수 없어 재생성 외에 방법이 없다.
- `departments/dshs-jayul.activeInviteCodeId`도 새 문서 ID(= 코드 문자열)로 맞춘다.

**시딩 예시** — `departments/dshs-jayul/inviteCodes/DJSN-2691`

| 필드 | 타입 | 값 |
| --- | --- | --- |
| `code` | string | `DJSN-2691` (문서 ID와 **같아야 한다**) |
| `issuedBy` | string | 부장 uid |
| `issuedAt` | timestamp | 지금 |
| `expiresAt` | timestamp | 발급 + 14일 (BR-13) |
| `isActive` | boolean | `true` |
| `revokedAt` | timestamp | 비워 둔다(`null`) |
| `useCount` | number | `0` |
| `maxUses` | number | `30` |

> 코드 형식은 `^[A-Z]{4}-[0-9]{4}$` 9자 고정이고 혼동 문자 `I`·`O`는 쓰지 않는다(§9.3.3).
> 앱은 입력값을 대문자로 바꾸고 4자에서 `-`를 자동으로 넣으므로, **소문자로 알려 줘도 통과한다.**

### 3-1. `useCount`는 이제 가입 시점에 오르지 않는다

지시서 §0.2 결정 1(안 2)로 **증가 시점이 부장 승인(OP-09)으로 옮겨졌다.**
S2는 `inviteCodes`에 **한 글자도 쓰지 않는다.** 승인 쪽 증가는 **W-11(S8 관리)** 이 붙인다.

**그때까지 `useCount`는 계속 `0`이다.** 한도 초과 판정(BR-14)이 실질적으로 동작하지 않는다는
뜻이며, 이것은 버그가 아니라 W-11이 채울 자리다. `maxUses`를 임시로 낮춰 시험하지 마라 —
낮추면 정상 가입이 막힌다.

## 4. 검증 방법 — 규칙을 배포한 뒤 무엇을 눌러 보면 되나

| # | 조작 | 성공하면 | 실패하면(= 규칙이 덜 열림) |
| --- | --- | --- | --- |
| 1 | 새 `@dshs.kr` 계정으로 로그인 → S2에서 **없는 코드**(`ZZZZ-0000`) 입력 후 필드 밖 탭 | 입력 칸이 빨갛게 되고 `존재하지 않는 코드입니다` | 상단에 `네트워크에 연결할 수 없습니다` 배너 → **2-1 또는 2-2가 빠졌다** |
| 2 | 같은 화면에 **시딩한 코드**를 입력하고 필드 밖 탭 | 오른쪽에 초록 체크, `가입 신청` 버튼 활성 | 위와 같은 배너 → **2-1 또는 2-2가 빠졌다** |
| 3 | `가입 신청` 탭 | 승인 대기(S2-1) 화면으로 넘어간다 | `가입 신청에 실패했습니다` → `users` create 또는 `approvalRequests` create가 막혔다 |
| 4 | 콘솔에서 그 계정을 `status: 'rejected'`로 바꾸고 앱에서 `승인 확인` → `가입 코드 다시 입력` → 코드 재입력 후 제출 | 다시 S2-1로 넘어가고 `approvalRequests`에 **새 문서**가 1건 더 생긴다 | `가입 신청에 실패했습니다` → **2-3이 빠졌다** |
| 5 | 같은 계정을 `status: 'withdrawn'`으로 바꾸고 4번을 반복 | 상단에 `이전에 탈퇴한 계정입니다…` 배너가 뜨고 제출이 성공한다 | 위와 같음 → **2-3이 빠졌다** |
| 6 | 콘솔 `users/{uid}` 확인 | `createdAt`·`recordCount`가 **처음 값 그대로** | 값이 바뀌었으면 조건 6(`hasOnly`)이 느슨하다 |

**1·2번이 이 요청서의 핵심이다.** 두 문구를 구분해 보여 주지 못하면 규칙이 덜 열린 것이고,
반대로 코드 **목록**이 조회되면 너무 열린 것이다(`list`가 새어 나갔다).

## 5. W-15가 함께 판단해야 할 것 (이번 범위 밖)

| 항목 | 이유 |
| --- | --- |
| BR-30 가입 신청 레이트 리밋(24시간 3회) + **App Check** | §11.5가 이 둘을 짝으로 규정한다. 클라이언트 단독 카운터는 시크릿 탭으로 우회되는 연극이다. **2-1과 같은 회차에 배포해야 한다** |
| BR-63 익명화 계정(`anonymizedAt`) 처리 | §14.3 익명화가 아직 구현되지 않아 이 필드가 채워지는 경로가 없다. 조건 5는 미래를 위한 빗장이다 |
| `firestore.rules`를 저장소로 옮길지 | 지금은 콘솔 텍스트가 정본이라 변경 이력이 남지 않는다 |
