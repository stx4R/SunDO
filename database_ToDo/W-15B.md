## 1. 🔴 양도를 실기기로 확인하는 절차 — **세 번째 계정은 필요 없다**

`database_ToDo/W-15A.md` §2가 만든 **두 번째 계정**을 그대로 쓴다. 순서는 이어진다.

### 1.1 선행 조건 (W-15A에서 이어짐)

| # | 조건 | 출처 |
| --- | --- | --- |
| 1 | 부장 계정으로 `/admin` → `코드 재발급`이 첫 코드를 만든다 | W-15A §1 |
| 2 | 두 번째 `@dshs.kr` 계정으로 S2 가입 신청 | W-15A §2 |
| 3 | 부장이 그 신청을 **승인**한다 → 두 번째 계정이 `role='member'` · `status='active'`가 된다 | W-15A §2 |

🔴 **3번까지 끝나야 ② 목록에 양도 대상이 생긴다.** 그 전에는 EM-05 `양도할 수 있는 부원이 없습니다`가

### 1.2 양도 실행

1. 부장 계정 `/admin` → ② `부원 · 권한 양도` → 두 번째 계정 행의 `양도` 탭
2. 모달 `{이름}님에게 부장 권한을 넘깁니다. 내 계정은 부원으로 전환됩니다.` → `양도`
3. 기대: 토스트 `부장 권한을 양도했습니다` → 홈으로 이동 → **하단 독에서 `관리` 탭이 사라진다**
   🔴 **「접근 권한이 없습니다」가 뜨면 실패다** — 보고서 §4-2가 그 경로를 실측으로 막았다

### 1.3 콘솔에서 확인할 4가지 (= 배치 4연산)

| # | 문서 | 확인 |
| --- | --- | --- |
| 1 | `users/{두 번째 계정}` | `role: 'head'` · `updatedAt` 갱신 |
| 2 | `users/{원래 부장}` | `role: 'member'` · `updatedAt` 갱신 |
| 3 | `departments/dshs-jayul` | `headUid`가 두 번째 계정 uid |
| 4 | `auditLogs/{uuid}` | `action: 'HEAD_TRANSFER'` · `actorRole: 'head'` · `before {headUid: 원래 부장}` · `after {headUid: 두 번째}` · **이름·이메일 없음** |

🔴 **네 문서가 전부 바뀌었거나 전부 그대로여야 한다.** 셋만 바뀌어 있으면 배치 계약이 깨진 것이다.

### 1.4 🔴 **되돌리는 절차 — 양도는 앱에서 되돌릴 수 없다**

넘긴 사람은 더 이상 부장이 아니므로 **앱에는 되돌릴 경로가 없다.** Dev가 콘솔에서 직접 되돌린다.

> ⚠ **세 문서를 한 번에 고쳐라.** 하나만 고치면 「부장 2명」 또는 「부장 0명」 상태가 되고,
> 그 상태에서는 BR-18 불변식이 깨진 채로 앱이 돈다.

1. Firebase 콘솔 → Firestore → `users/{두 번째 계정}` → `role`을 `head` → **`member`**
2. `users/{원래 부장}` → `role`을 `member` → **`head`**
3. `departments/dshs-jayul` → `headUid`를 **원래 부장 uid**로
4. 원래 부장 계정에서 앱을 **완전히 새로고침**한다(역할은 다음 판정에서 반영된다 — R-06)
5. `auditLogs`는 **지우지 않는다.** §9.6 필수 조건 6이 수정·삭제를 전면 금지한다.
   되돌린 사실은 새 로그가 아니라 **이 문서의 실행 기록**으로 남긴다(v1.1의 ④ 감사 로그 화면이
   생기기 전까지는 콘솔에서만 보인다)

🔴 **`updatedAt`은 손대지 않아도 된다.** 다음 쓰기가 덮는다. 억지로 옛 값을 넣지 마라.

### 1.5 확인이 끝나면

원상 복구(§1.4)를 **반드시 실행한다.** 파일럿 운영은 원래 부장 계정으로 계속된다.

## 2. 인덱스 **0건** — IX-10을 쓰지 않는다

§9.5 IX-10은 `users`: `departmentId ASC, status ASC, role ASC, name ASC`다. **쓰지 않았다.**

| 질의 | 실제 형태 | 인덱스 |
| --- | --- | --- |
| ② 부원 목록 | `where('departmentId','==','dshs-jayul')` + `where('status','==','active')` — **등식 2개** | **불필요**(자동 인덱스) |
| 양도 전 확인 | `getDoc(users/{대상})` · `getDoc(departments/{id})` · `getDoc(users/{현 부장})` | **불필요** |

**질의 로그 실측**(스텁 하네스가 찍은 그대로):

```
users|departmentId:==:dshs-jayul,status:==:active
```

`orderBy`가 **없다.** 근거 2가지:

1. 🔴 IX-10은 **미생성**이다. `orderBy`를 붙이면 `failed-precondition`으로 목록이 통째로 죽는다.
2. 🔴 IX-10의 `role ASC`는 **알파벳 순**(`dev` · `head` · `member` · `teacher` · `vice`)이라
   조직도와 아무 관계가 없다. 서버에 맡겨도 원하는 순서가 나오지 않는다.
   → **역할 권한 순(부장 → 차장 → 부원 → 교사 → Dev) → 이름 가나다**로 **클라이언트가** 정렬한다.
   실사용 규모가 약 40명이라 정렬 비용이 무의미하다.

**S8은 인덱스를 0건 요구한다**(W-15A §3과 같은 결론). 🔴 `firestore.indexes.json`을 만들지 마라.

## 3. 🔴 규칙 회차(W-16) — 이번 회차 신규 재검증 시나리오 **14건**

> 지금은 전부 통과한다. **통과의 이유가 「W-04 임시 catch-all이 검증을 안 해서」다.**

### 3.1 `users` **list** — 🔴 앱에서 처음 쓰는 형태다

W-13은 `documentId() in` 묶음 읽기였고 W-15A는 `users`를 읽지 않았다.
§9.6의 `users` read는 「본인 또는 `active` 부서원」인데, **문서 단위 조건을 `list`에 그대로 걸면
Firestore는 질의 전체를 거부한다**(규칙이 질의의 결과 집합을 미리 증명할 수 있어야 한다).

| # | 시나리오 | §9.6 근거 | 기대 |
| --- | --- | --- | --- |
| **M-1** | `active` 부서원(`member`)이 `where(departmentId=='dshs-jayul') + where(status=='active')` **list** | `users` read | **통과** |
| **M-2** | `pending` 계정이 같은 list | 같은 행 | 🔴 **거부** |
| **M-3** | 미인증이 같은 list | 같은 행 | 🔴 **거부** |

⚠ **M-1이 이번 회차 최대의 위험이다.** 규칙을 「본인 문서만」으로 좁게 쓰면 ②가 통째로 죽고,
넓게 쓰면 부서 전체의 `users` 문서가 전 필드 노출된다(§9.6 각주 R-b가 다루는 그 문제다).
앱은 **이름·역할만 화면에 그린다**(클라이언트 규율 — W-14 결정 3). 규칙이 필드를 제한할 수 없으므로
**각주로 닫는 결정이 이미 서 있다.** §5.1 R-b 참조.

### 3.2 `users` 역할 변경 — 🔴 **한 배치에 남의 문서 2건**

| # | 시나리오 | §9.6 근거 | 기대 |
| --- | --- | --- | --- |
| **T-1** | `head`가 남의 `users/{uid}.role`을 `member → head` | update 「역할 변경은 `head`·`dev`만」 | **통과** |
| **T-2** | `head`가 **현 부장(남)**의 `role`을 `head → member` | 같은 행 | **통과** |
| **T-3** | 🔴 **`dev`가 T-1 + T-2를 한 배치로 실행** | §4.1 「Dev는 전 기능 접근」(결정 2) | **통과** — `head`가 아닌 계정이 남의 `role`을 바꾼다 |
| **T-4** | `vice`가 T-1을 시도 | 같은 행 | 🔴 **거부** |
| **T-5** | `teacher`가 T-1을 시도 | 「교사는 어떤 쓰기도 불가」(§4.2 단서 3) | 🔴 **거부** |
| **T-6** | `member`가 T-1을 시도 | 같은 행 | 🔴 **거부** |
| **T-7** | `head`가 **본인** `role`을 직접 바꾼다 | 🔴 **BR-21 · R-04** | 🔴 **거부** |

🔴 **T-2와 T-7이 갈리는 지점을 규칙이 표현할 수 있어야 한다.** 부장은 남의 `role`은 바꿔도
자기 `role`은 못 바꾼다. 「`request.auth.uid != resource.id`」 조건 없이 열면 R-04가 무너지고,
그 조건을 **배치의 다른 연산에까지** 걸면 T-2(자기 강등이 아니라 **현 부장 강등**)가 막힌다.
⚠ head가 실행할 때 T-2의 대상은 실제로 **본인**이다 — 🔴 **그래서 「본인 role 변경 금지」를
그대로 쓰면 양도가 죽는다.** BR-21이 금지하는 것은 「양도를 거치지 않은 단독 role 변경」이고,
양도 배치는 `departments.headUid` 갱신을 **같은 배치에** 갖는다. 그 차이를 규칙이 봐야 한다.

### 3.5 🔴 배치 조합 — **시뮬레이터로 반드시 통째로 돌려라**

```
writeBatch (양도 · 4연산):
  users/{대상}                       update   ← T-1
  users/{현 부장}                    update   ← T-2   🔴 head 실행이면 곧 본인이다
  departments/dshs-jayul             update   ← P-1
  auditLogs/{uuid}                   create   ← L-4
```

```
writeBatch (양도 · 3연산 — 🔴 BR-23 부장 0명 복구 경로):
  users/{대상}                       update   ← T-1
  departments/dshs-jayul             update   ← P-1
  auditLogs/{uuid}                   create   ← L-4
```

🔴 **3연산 조합을 빼먹지 마라.** 현 부장 문서가 없거나 `role !== 'head'`일 때 앱이 실제로 내는 형태이고,

⚠ 네 규칙 중 **하나만 좁아도 양도가 통째로 죽는다.** 개별 테스트만 통과시키고 넘어가지 마라.

## 4. 🔴 부장 1명 불변식(BR-18)은 **Rules가 최종 보장자다**

**클라이언트 배치는 「정확히 1명」을 보장하지 못한다.** 측정으로 확인한 사실이다(보고서 §4-3):

- 앱은 커밋 전에 `getDoc`으로 대상(BR-20)과 현 부장을 확인하고, 네 연산을 **한 배치**로 커밋한다.
  부분 성공은 없다(실측 — 3번째 연산에 실패를 주입하면 쓰기 **0건**, 네 문서 전부 이전 상태).
- 🔴 **그러나 같은 순간 다른 부장·Dev가 다른 사람에게 양도하는 경쟁은 막지 못한다.**
  두 배치가 각각 원자적이어도 「A→B」와 「A→C」가 겹치면 결과가 부장 2명이 될 수 있다.
  확인과 커밋 사이에 창이 있고, 클라이언트에는 그 창을 닫을 수단이 없다.

**규칙 회차가 판단해야 하는 것 3가지**

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **§9.6 필수 조건 3(역할 판정)** | 역할을 `request.auth.token`이 아니라 `users/{uid}` 문서에서 읽는다면, 같은 트랜잭션이 그 문서를 바꾸는 양도에서 **판정 시점**이 문제가 된다. `get()`은 배치 **이전** 상태를 본다 — 그 전제를 명시할 것 |
| 2 | **BR-18을 규칙으로 강제할 수 있는가** | Rules는 「부서에 `role=='head'`인 문서가 정확히 1개」를 **셀 수 없다**(집합 질의 불가). 실질 강제는 `departments.headUid`를 **단일 진실**로 삼고 `users.role=='head'`를 그 파생으로 보는 것이다 — 🔴 **`headUid`와 어긋난 `role: 'head'` 쓰기를 거부**하면 불변식이 문서 1개로 좁혀진다. 채택 여부를 결정할 것 |
| 3 | **BR-23 Dev 복구 경로** | 위 2를 채택하면 **부장 0명 상태에서 Dev가 `headUid`를 먼저 쓰는 순서**가 필요하다. §3.5의 3연산 조합이 그 형태다 |

⚠ §11.3의 `transferHeadRole` Cloud Function(「부장 1명 불변식 서버 강제」)은 **MVP 범위가 아니다.**
서버 강제를 도입할 때까지는 위 2가 유일한 방어선이다.
