### 4.5 🔴 배치 조합 — **시뮬레이터로 반드시 함께 돌려라**

**승인 배치는 4개 컬렉션을 동시에 건드린다.** Firestore 배치는 **한 연산이라도 규칙에 걸리면 전체가 거부된다.**

```
writeBatch:
  users/{uid}                                     update   ← U-1
  approvalRequests/{id}                           update   ← A-3의 반대(head는 통과해야 한다)
  departments/{dept}/inviteCodes/{codeId}         update   ← C-5
  auditLogs/{uuid}                                create   ← L-1
```

```
writeBatch (재발급):
  departments/{dept}/inviteCodes/{old}            update   ← C-3
  departments/{dept}/inviteCodes/{new}            create   ← C-1
  departments/{dept}                              update   ← `departments` update = head·dev
  auditLogs/{uuid}                                create   ← L-1
```

🔴 **네 규칙 중 하나만 좁아도 승인·재발급이 통째로 죽는다.** 개별 테스트만 통과시키고 넘어가지 마라 —
**위 두 조합을 그대로 시뮬레이터에 넣어야 한다.**

⚠ 거절 배치는 `users` + `approvalRequests` + `auditLogs` **3연산**이고 `inviteCodes`를 건드리지 않는다.

  스텁으로 재현하니 **pill 4개가 잠긴 채 그대로 남았다**(토스트도 없고 행도 그대로).

  `commit()`의 promise는 서버 확인까지 resolve되지 않는다 — W-12 §1-3).
- 🔴 **이번 회차에 타임아웃을 발명하지 않았다.** 임의의 제한 시간은 「느린 네트워크」와 「끊김」을 구분하지 못하고,
  그 판정은 오프라인 큐 설계와 함께 정해져야 한다.

→ **W-20이 이어받는다.** 함께 볼 것: 전송 대기 배지(BR-41) · 강제 플러시 · TS-16 · `records`의 조용한 실패 경로(W-12 §5).
