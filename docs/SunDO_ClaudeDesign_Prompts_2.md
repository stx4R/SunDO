## 입력 필드 ★v2 신규 — 앱의 모든 텍스트 입력에 예외 없이 적용

### 공통 규격
높이 56, radius 14, 배경 `rgba(255,255,255,0.55)`,
테두리 `1px rgba(255,255,255,0.8)`, 안쪽 그림자 `inset 0 1px 3px rgba(20,53,38,0.05)`.
padding `22px 16px 8px` (윗공간은 떠오른 라벨 자리). 값 텍스트 15/500 `#14352A`.
값이 숫자·시각·코드면 `tabular-nums`.

### 1) Floating Label
- 비어 있고 비포커스 → 라벨이 입력 영역 세로 중앙, 15/500, `rgba(20,53,38,0.45)`.
- 포커스 또는 값 있음 → 라벨이 상단에서 9px 지점으로, 11.5/700, `#2E6B4C`.
- 이동·축소를 동시에 0.18s `cubic-bezier(.2,.8,.25,1)`. **좌측 기준선 16px은 고정**(좌우로 흔들리지 않는다).
- placeholder는 원칙적으로 쓰지 않는다. 형식 예시가 필요한 필드만 **포커스 중에만** placeholder를 `rgba(20,53,38,0.30)`으로 보인다.
- 구현: `placeholder=" "` + `:placeholder-shown` / `:focus` 형제 선택자.

### 2) Border Focus
- 비포커스 `1px rgba(255,255,255,0.8)` → 포커스 `1.5px #2E6B4C`, 0.15s.
- 포커스 시 바깥으로 포커스 링 `0 0 0 3px rgba(46,107,76,0.12)`.
- 배경도 `rgba(255,255,255,0.72)`로 살짝 밝아진다.

### 3) Blinking Cursor
- 실제 `input`에는 `caret-color:#2E6B4C`.
- 시안(정지 이미지) 상태에서는 커서를 직접 그린다 — 폭 1.5, 높이 18, `#2E6B4C`, radius 1.
- 깜빡임 주기 1.06s, `step-end`, 켜짐 53% : 꺼짐 47%.
- 타이핑 중에는 깜빡임을 멈추고 항상 켜진 상태를 유지하다가, 마지막 키 입력 0.5s 후 다시 깜빡인다.
- 정지 시안에서는 **켜진 상태**로 그린다.

### 4) Validation
- **성공**: 테두리 `1.5px #2E6B4C`. 우측 16px에 원형 20px 체크 아이콘 `#2E6B4C`.
  체크는 `stroke-dashoffset`로 0.28s 그려지고, 필드가 y `-2 → 0`으로 0.2s 정착.
- **실패**: 테두리 `1.5px #C0392B`, 라벨도 `#C0392B`, 우측 16px에 느낌표 원형 20px `#C0392B`.
  필드 전체 shake — x `0 → -6 → 5 → -3 → 0`, 0.32s `ease-out`.
  필드 아래 6px에 11/500 `#C0392B` 에러 문구가 높이 `0 → auto` + 투명도 `0 → 1`로 0.2s 펼쳐진다.
- **검사 중**(서버 확인이 필요한 값): 우측에 `#2E6B4C` 스피너 16px, 테두리는 포커스 상태 유지.
- 검증 시점: blur 시 1차, 제출 시 전체. 한 번 에러가 뜬 필드는 값이 바뀔 때마다 즉시 재검사한다.
- shake는 에러당 1회만. 에러 상태에서 재포커스해도 반복하지 않는다.

### 5) 비활성 / 읽기 전용
- **읽기 전용**: 배경 `rgba(31,81,56,0.06)`, 테두리 없음, 우측 16px에 자물쇠 아이콘 14px `rgba(20,53,38,0.45)`.
  라벨은 항상 떠 있는 상태로 고정. 커서 없음.
- **제출 중**: 전체 투명도 0.6, 커서·깜빡임 정지.

### 적용 대상 (빠짐없이)
가입 코드 · 순찰 시간 · 순찰 장소 · 담당자 이름 검색 · 기록 사유 `기타` 기입 박스 · 설정 화면의 모든 입력.

## 하단 독(Dock) ★v2 개정 — 5탭

## 6. 결과물 확인 목록 (v2)

v1의 7개 항목에 아래 8개를 더한다.

**v1 유지 항목**
1. 배경 그라디언트와 오라 3개가 있는가
2. 컬러가 팔레트 밖으로 나가지 않았는가 (`#C0392B`는 에러·파괴적 액션에만)
3. 18px 미만 보조 텍스트의 불투명도가 0.70 이상인가
4. 모든 버튼·칩의 높이가 44px 이상인가
5. 문구가 프롬프트에 적힌 그대로인가 (마침표 유무까지)
6. 카드가 glass, 학년·반 버튼류가 neu, 주 액션이 그라디언트 버튼인가
7. 숫자에 `tabular-nums`가 적용됐는가

**v2 추가 항목**
8. 이메일·비밀번호 입력이 앱 어디에도 남아 있지 않은가
9. 구글 `G` 로고를 초록으로 칠하거나 단색화하지 않았는가
10. 모든 입력이 56px 높이 + Floating Label을 갖췄는가. placeholder-only 입력이 0개인가
11. 라벨이 떠오를 때 좌측 기준선(16px, 아이콘 있으면 44px)이 흔들리지 않는가
12. 포커스 상태에 테두리 1.5px `#2E6B4C` + 포커스 링 + 커서가 모두 있는가
13. 검증 성공·실패·검사 중 3상태가 각각 그려졌는가 (실패에는 shake와 펼침 에러 문구까지)
14. 독이 5탭(부원 4탭)이고 항목 간 간격이 8px 이상 남는가
15. 사유가 3종이고, `기타` 태그가 line 스타일인가. 필터 칩이 한 줄에 4개 들어가는가
16. Footer의 영어 3개 문자열이 원문 그대로인가 (`SunDO` / `© 2026 SunDO. All rights reserved.` / `Developed by stx4R`)

**보안 주의**: OAuth 요청에 `hd=dshs.kr`를 넣어도 그건 **힌트일 뿐 강제가 아니다**. 인증 성공 후 클라이언트에서 도메인을 다시 확인하고, 불일치면 즉시 `signOut()` + 계정 삭제, 그리고 Security Rules에서도 `request.auth.token.email.matches('.*@dshs\\.kr$')`로 한 번 더 막아야 한다. 세 겹 다 필요하다.

### 🔴 충돌 2 — 기타 사유의 자유 서술 (PR-02)

PRD §14.1에 이렇게 박혀 있다.

> **PR-02** 기록에는 자유 서술 메모 필드를 두지 않는다. 주관적 서술이 학생에게 불이익을 줄 수 있기 때문이다.

`기타` 기입형 박스는 이 원칙을 정면으로 어긴다. 처리 방법은 둘 중 하나다 → **Q2에서 확정 필요**.

- **A안(현재 프롬프트가 그린 것)**: PR-02를 개정한다. 20자 상한 + 가이드 문구 + 감사 로그 대상 포함으로 위험을 낮춘다.
- **B안**: 자유 입력을 없애고 `기타` 선택 시 사전 정의된 항목(명찰 미착용 / 두발 규정 위반 / 지각 …)을 고르는 목록으로 바꾼다. PR-02를 지키면서 사유는 늘릴 수 있다.

## 8. 확인이 필요한 질문

### 반드시 먼저 답해야 하는 것 (답에 따라 산출물이 뒤집힘)

**Q1. 이름을 어디서 가져오나?**
설정에서 이름 변경을 막으려면 이름의 출처가 하나로 고정돼야 한다.
- **A안 (현재 프롬프트)**: 구글 계정의 표시 이름을 그대로 쓰고 앱에서는 읽기 전용.
  → 학교 Workspace 계정의 표시 이름이 `KIM MINJUN` 같은 영문이거나 `2101김민준` 같은 학번 포함 형식이면 화면 곳곳이 지저분해진다.
- **B안**: 가입 신청 화면에서 이름을 **한 번만** 입력받고 이후 잠근다.
  → R-02에 [입력 필드] 하나가 더 붙는다. 변경은 부장에게 요청하는 방식.

**대전대신고 Google 계정의 표시 이름이 실제로 어떤 형식인지** 확인해 주면 바로 정할 수 있다.

**Q2. `기타` 사유를 자유 입력으로 갈 것인가?**
위 §7 충돌 2의 A안 / B안 중 선택. 개인정보 원칙을 세운 게 PRD 본인이라 임의로 못 뒤집었다.
(참고로 B안이 안전하고 집계도 깔끔하지만, 현장에서 예외 상황을 못 담는다는 단점이 분명하다)

### 확정되면 좋은 것

**Q3. Footer를 어디까지 노출하나?**
현재는 **설정 · 로그인 · 승인 대기 · 개인정보 처리방침 · 이용약관** 5곳으로 잡았다.
홈·기록·일정처럼 매일 쓰는 화면 하단에도 넣을지? (개인적으로는 넣지 않는 쪽을 권한다. 스크롤 끝마다 저작권 줄이 나오면 도구가 아니라 홍보물처럼 보인다)

**Q4. 정책 문서를 몇 개 만들 것인가?**
Footer에 `개인정보 처리방침 / 서비스 이용약관 / 오픈소스 라이선스` 3개를 그려 뒀다.
지금 실제로 존재하는 건 개인정보 처리방침(P-10)뿐이다.
- 3개 다 만든다면 → 나머지 2개는 P-10과 같은 레이아웃에 제목·소제목만 갈아끼우면 된다(프롬프트 추가 불필요).
- 개인정보 처리방침만 둔다면 → R-06의 링크 줄을 1개로 줄인다.

**Q5. 설정 화면의 알림 카드를 MVP에 넣을 것인가?**
PRD §13.1·D-12 기준으로 Web Push는 **v1.1 이관**이다. 지금 토글을 넣으면 눌러도 아무 일이 없다.
- 넣는다 → R-05 변형 C(잠금 + 안내)를 기본 상태로 쓴다.
- 뺀다 → 카드 ②를 삭제하고 ①③④만 남긴다. 화면이 조금 허전해진다.

**Q6. 계정 탈퇴 행이 필요한가?**
현재는 `로그아웃`만 넣었다. 탈퇴를 넣으면 "본인이 작성한 기록을 어떻게 처리할지"(익명화 / 유지 / 삭제)를 PRD §14.3에 먼저 정의해야 한다. 지금은 정의가 없어서 뺐다.

**Q7. 용어 확인 — `실내화 불량` vs `실내화 미착용`**
요청서에는 `실내화 불량`으로 적혀 있는데, PRD와 프로토타입의 확정값은 `실내화 미착용`이다.
프롬프트는 **`실내화 미착용`으로 통일**해 뒀다. 실제로 명칭을 바꿀 생각이었다면 알려 달라. 8곳(세그먼트·필터 칩·태그·감사 로그·빈 상태 등)을 한 번에 고쳐야 한다.

**Q8. 부원의 독은 4탭이 맞나?**
부원은 `관리` 탭이 없으므로 홈·기록·일정·설정 4탭이 된다.
`관리`를 회색 비활성으로 남겨 두는 방식이 아니라 **항목 자체를 렌더링하지 않는** 기존 PRD 규칙을 그대로 따랐다.
