## 4. 판단과 이탈

### 4-1. 🔴 배치 계약 — 「부분 성공이 없다」를 실측으로 잠갔다

`writeBatch` 하나로 커밋하고 실패하면 `{ ok: false, code }`를 돌려준다. 롤백 코드를 따로 쓰지 않았다
(`signup.ts` §106의 「`writeBatch`가 원자적이므로 부분 생성 문서가 남지 않는다」와 같은 계약).

**스텁이 3번째 연산에서 던지도록 만들어 실측했다** — 쓰기 로그 **0건**, 네 문서 전부 이전 상태,
화면의 행도 그대로다(DoD 25). 🔴 **이것이 이 회차의 첫 계약이라 하네스에 「부분 성공 재현 모드」를 따로 만들었다.**

### 4-2. 🔴 `useCount`는 **존재를 미리 확인**하고 배치에 넣는다

`batch.update`는 대상 문서가 없으면 **배치 전체를 실패시킨다.** 그래서 `request.inviteCodeId`가 있어도
그 문서를 `getDoc`으로 먼저 확인하고, 없으면 **그 연산만 빼고** 승인을 진행한다.

🔴 **코드 문서 때문에 사람의 가입이 막히면 안 된다.** 실측 — `inviteCodeId`가 `null`인 경우와
코드 문서가 사라진 경우 둘 다 **쓰기 3연산으로 승인 성공**(DoD 21).

대가: 승인 경로에 `getDoc` 1회가 추가된다. 배치를 살리는 값으로는 싸다.

### 4-3. 🔴 승인 시점에 한도를 검사하지 않는다 (결정 1)

`useCount >= maxUses`여도 승인은 성공하고 `useCount`는 그대로 +1 된다. 실측 — `30 → 31`.
**경고 UI를 만들지 않았다** — §8.10에 문구가 없고, 없는 문구를 지어내면 §4-4 위반이다.

BR-14의 실질 게이트는 **신청 시점(S2 `lookupInviteCode`의 `unusable`)**이고, 승인은 부장의 명시적 판단이라
사람이 이미 게이트다. 초과분은 「이미 신청을 통과한 사람」으로 상한이 묶인다.
→ §7 신규 항목(「BR-14는 신청 시점 검사임을 각주로」).

### 4-4. 🔴 「읽기 전용」은 `disabled`가 아니라 **부재**다

차장·교사는 `승인`·`거절` pill이 **렌더되지 않는다**(실측 `pills: []`). `disabled`로 두면
스크린리더가 「버튼이 있는데 못 누른다」로 읽고, 왜 못 누르는지 설명할 문구가 §8.10에 없다.
§8.8.3 #10의 「차장·교사는 버튼 미표시」가 그대로다.

### 4-5. 오프라인 안내는 **네 번째 위험색 배너가 아니다**

§8.8.6이 배너 문구를 규정하는데, 전역 `.ofb`는 `AppShell` 소유라 화면이 문구를 바꿀 수 없다
(바꾸려면 `AppShell`·`OfflineBanner`를 고쳐야 하고 둘 다 불가침이다).

→ **`.adm-off`를 따로 만들었다.** 기하(`radius 12` · `padding 11px 13px`)는 기존 인라인 배너 3벌에서
빌리고 **배경은 중립 틴트**를 썼다. 오프라인은 오류가 아니라 상태이고, 위험색을 쓰면
W-13 §0.1-4가 예약한 **`.banner` 승격 대상이 네 벌째**가 된다.

🔴 **그래서 이번 회차는 `.banner` 승격 트리거를 당기지 않았다** — 예약은 「같은 값의 **위험색** 배너가
네 번째로 필요해지는 화면」에 그대로 남아 있다. 실측 — `.ofb` **1개** 유지.

### 4-6. §7.5의 「관리 화면 마지막 카드 130px」을 화면이 10px로 채웠다

`AppShell`은 `hasDock`으로 **120px**을 준다. 130px을 주려면 `bottomGap` prop을 써야 하는데
그러려면 `router.tsx`가 `handle`을 읽어 넘겨야 한다 — **둘 다 이번 회차의 불가침 파일이다.**

→ **여백 소유 계약(120px은 `AppShell`)은 그대로 두고, 관리 화면에만 있는 10px 차이만 화면이 갖는다**
(`.adm-main { padding-bottom: 10px }`). 실측 `120 + 10 = 130px`.

### 4-7. 🔴 오프라인 배치 — **타임아웃을 발명하지 않았다** (§9-4)

| 경로 | 실측 |
| --- | --- |
| 오프라인 진입 | 버튼 **6개 전부 `disabled`** · 안내 문구 표시 · 쓰기 **0** · **강제 클릭 후에도 0** |
| 🔴 **커밋 시작 후 단절** | `commit()`이 영원히 pending인 모드에서 — pill 4개가 **잠긴 채로 남는다**. 토스트 없음, 행 그대로, 배치는 큐에 1개 |

**W-08 §5-7에서 실제로 스피너가 영원히 돌았던 것과 같은 성질**이다(`persistentLocalCache`가 켜져 있으면
`commit()`의 promise는 서버 확인까지 resolve되지 않는다 — W-12 §1-3).

🔴 **임의의 제한 시간은 「느린 네트워크」와 「끊김」을 구분하지 못한다.** 그 판정은 오프라인 큐 설계와
함께 정해져야 하므로 **오프라인 회차(W-20)로 넘겼다** — `database_ToDo/W-15A.md` §7.

### 4-8. `.pill-fill` 그림자 — **유예의 조건이 충족됐다** (판단 요청)

W-03A §0.3-2가 「`.pill-fill` 그림자 없음은 의도된 차이다. **W-03B에서 실제 목록 행에 렌더한 뒤에도
어색하면 그때 다시 본다**」로 유예했는데, `.pill`은 그 뒤로 **소비자가 0개**였다.
🔴 **이번 회차가 그 「실제 목록 행」이다.**

- design `9a`의 `승인` pill: `box-shadow: 0 5px 12px rgba(31,81,56,0.28)`
- 현재 `.pill-fill`: 그림자 **없음**(§7.3 원문)

**이번 회차에 바꾸지 않았다** — 사용자가 확정한 결정을 실측 없이 뒤집지 않는다.
실측값을 남기니 판단은 PM 소유다(§7 신규 항목).

### 4-9. `14px` 토큰을 코드에서 먼저 만들지 않았다

지시서 §4-3이 「`14px`은 이미 소비자 2곳이다 — 세 번째가 나오면 승격하라」로 지시했고,
`.mrow-name`이 **세 번째**다. 🔴 **그런데 토큰을 코드에 먼저 만들지 않았다.**

`--text-*`는 **§7.2 스케일의 사본**이다. 스케일에 없는 이름을 `@theme`에 넣고 `lib/cn.ts`까지 등록하면
**PRD가 모르는 스케일이 코드에만 생긴다** — W-07 §5-6이 고친 문제(`@theme`에 추가하고 `cn.ts` 등록을
빠뜨림)의 반대 방향 사고다. §7.2에 편입하는 것이 먼저이고 그것은 PM 소유다.
→ **§7에 「세 번째 소비자가 나왔다. 승격 시점이다」로 올렸다.**

### 4-10. 코드 생성기를 `inviteCode.ts`에 뒀다

§3.6이 `inviteCode.ts` 또는 `admin.ts` 중 하나로 열어 뒀다. **`inviteCode.ts`를 골랐다** —
`INVITE_CODE_PATTERN`·`formatInviteCode`(S2 입력 변형)와 **같은 형식 규격**을 공유하기 때문이다.
생성과 검증이 다른 파일로 갈리면 한쪽만 고쳐지는 날이 온다.
그 파일의 문서 주석이 이미 「순수 함수다. DOM·Firestore를 참조하지 않는다」로 성격을 규정하고 있고,
`crypto.getRandomValues`는 그 규정을 깨지 않는다(하네스가 node에서 직접 불러 10,000회 돌렸다).

**모듈로 편향 제거** — `256 % 24 = 16`이라 `byte % 24`는 앞 16글자를 11/256, 뒤 8글자를 10/256로 뽑는다.
상한 `256 - (256 % n)` 이상인 바이트를 버리는 **거부 표집**으로 균등하게 만들었다.
숫자 8종은 `256 % 8 = 0`이라 버려지는 바이트가 없다 — 같은 코드가 두 경우를 모두 처리한다.

### 4-11. T-07의 「신규 수신」 판정에서 ref 두 개를 함께 되돌린다

초안에서 **초기 로드 행이 전부 `rise`로 튀었다.** 원인: 구독을 다시 걸 때 `seenRef`만 비우고
`serverSynced`(상태)는 살아 있어, 새 구독의 첫(캐시) 스냅샷이 통째로 「신규」로 보였다.
StrictMode 이중 마운트와 T-07 새로고침에서 **실제로** 그렇게 찍혔다.

→ 효과 본문에서 **`seenRef`와 `syncedRef`를 함께 되돌리고**, `syncedRef`는 상태 미러링 효과가 아니라
**스냅샷 콜백이 직접 올린다**(`live`를 먼저 읽은 뒤). 실측 — 초기 `rising: [false, false]`,

## 6. 검증 환경

- **스텁 하네스** — 앞 회차와 같은 방식. 임시 별칭 5개. 이번에 새로 필요했던 4가지:
  1. 🔴 **`writeBatch` 스텁** — 연산을 큐에 쌓고 `commit()`에서 **스냅샷 사본에 전부 적용한 뒤** 성공했을 때만
     실제 저장소에 반영한다. `failBatchAt: n`으로 **부분 성공을 재현**하고(쓰기 로그도 0건이어야 통과),
     `hangCommit: true`로 **영원히 pending**을 만든다.
  2. **`increment` 센티널** — `{ __increment: n }`을 커밋 시점에 이전 값에 더한다. `useCount` 3→4를 관측했다.
  3. **`onSnapshot` + `getDoc` 혼용** — W-13·W-14의 스텁을 합쳤다. 🔴 **`getDoc`은 오프라인·캐시 미스에서
     `unavailable`로 throw**한다(W-14 P1). 문서 저장소를 **경로 문자열 → 문서** `Map`으로 바꿔
     `departments/{id}/inviteCodes/{code}` 하위 컬렉션을 그대로 표현했다(`doc`·`collection`이 가변 인자다).
  4. **역할 주입 5종** — 픽스처의 `users/uid-head.role`을 갈아 끼워 섹션 노출을 전수로 쟀다.
- **순수 함수 실측** — `node --experimental-strip-types`로 `src/lib/inviteCode.ts`를 **그대로 import**해
  10,000회 돌렸다. 브라우저를 거치지 않아 하네스와 독립이다.
- 헤드리스 **Chrome**을 CDP로 직접 구동(의존성 0). 430×902 · reduce · 루트 `font-size: 32px`.
- **측정 후 별칭 5개와 `src/__stub/`을 전부 제거했다.** 증거 3가지:
  ① `grep -rn "__stub\|__STUB__\|w15-" src/ vite.config.ts package.json` → **0건**
  ② 번들이 스텁 제거 전후 **`1,030.03 kB`** 동일(기준선 `1,020.08 kB`)
  ③ `git status`에 `vite.config.ts`가 **없다**
- 하네스 파일(`w15-cdp.mjs`·`w15-fixture.mjs`·`w15-measure*.mjs`·`w15-codes.mjs`·`w15-out*.json`)은
  저장소 루트의 임시 파일이고 **커밋하지 않았다**.

**측정 함정 — 앞 회차의 것을 적용했고 3건이 새로 나왔다**

1. ✅ **② `__WRITES__`를 경로별로 세라** — 이번엔 **한 배치에 4개 컬렉션**이다.
   🔴 게다가 `useLastActiveAt`(DR-12)가 `users/uid-head`를 상시로 쓴다 — **행위자 본인 경로를 걸러야**
   승인 배치의 4연산이 보인다(W-12의 같은 함정이 이번엔 `users/{본인}`으로 나타난다).
2. ✅ **⑤ StrictMode 이중 마운트** — 질의·구독이 2배로 찍힌다. 구독 수는 영향받지 않는다(cleanup이 해제한다).
3. 🔴 **신규 — 「강제 탭」을 `button.disabled = false` + `click()`으로 흉내 내면 재현되지 않는다.**
   React가 재렌더로 `disabled`를 되돌려 모달이 열리지 않았다. **실제로 일어날 수 있는 경쟁**으로 바꿨다 —
   발급 이력 조회를 1.5s 늦추면 그 사이 버튼이 활성이라 모달을 열 수 있고, 확인 시점에는 한도가 확정돼 있다.
   그때 E-3002가 떴고 쓰기는 0건이었다.
4. 🔴 **신규 — 사라지는 행의 애니메이션은 살아 있는 요소로 잴 수 없다.** 처리된 행은 구독이 즉시 지우므로
   `.mrow-leave`를 찾는 순간 이미 없다. **같은 클래스를 붙인 임시 노드를 만들어 computed를 읽었다**
   (`fadeOut 0.2s` 확인). reduce 검증도 같은 방법을 썼다.
5. 🔴 **신규 — 승인·거절 대상 행의 인덱스를 고정하지 마라.** 클라이언트 정렬이 `createdAt` 내림차순이라
   픽스처를 오름차순으로 넣으면 **0번 행이 `신청자2`**다. 이름으로 확인하지 않으면 엉뚱한 문서를 검사하게 된다.

### 8-2. 🔴 부장 1명 불변식(BR-18)이 배치로 어떻게 강제되나

BR-19가 「`대상 → head` + `본인 → member` + `departments.headUid` 갱신을 **단일 배치**로. 부분 성공은 없다」로 규정한다.

```
writeBatch:
  users/{대상}          .role = 'head',   updatedAt
  users/{본인}          .role = 'member', updatedAt
  departments/{dept}    .headUid = {대상}, updatedAt
  auditLogs/{uuid}      action: 'HEAD_TRANSFER'
```

🔴 **클라이언트 배치는 「정확히 1명」을 보장하지 못한다.** 두 연산이 원자적으로 함께 적용될 뿐,
「같은 순간 다른 부장이 다른 사람에게 양도하는」 경쟁은 막지 못한다.
**실질 보장은 Rules(§9.6 필수 조건 3의 역할 판정)와 BR-23의 Dev 복구 경로**다 —
W-15B는 그 사실을 요청서에 적고 규칙 회차에 넘겨야 한다.

또한 **BR-21**(부장은 자신의 역할을 직접 수정할 수 없다)과 **BR-20**(대상은 `active` 且 `member|vice`)은
클라이언트 검증 + Rules 이중이어야 한다. 목록에서 본인 행을 빼는 것만으로는 부족하다.

### 8-3. `users` 목록 조회가 IX-10을 요구하는가 — **요구하지 않게 만들 수 있다**

§9.5 IX-10은 `users`: `departmentId ASC, status ASC, role ASC, name ASC`다.
🔴 **`orderBy`를 서버에 맡기면 미생성 인덱스에 의존한다.** 이번 회차의 승인 대기 목록과 **같은 판단**을 권한다 —
`where('departmentId','==',…)` + `where('status','==','active')` **등식 2개**로 읽고 **클라이언트에서 정렬**하라.
실사용 규모가 약 40명이라 정렬 비용이 무의미하다. 그러면 W-15B도 인덱스 0건이다.

⚠ §9.6은 `users` read를 「본인 또는 `active` 부서원」으로 열어 두지만 **`list` 형태는 처음이다**
(W-13은 `documentId() in` 묶음, W-15A는 `users`를 읽지 않는다). **규칙 회차 재검증 항목이 하나 는다.**

### 8-4. 중첩 포커스 트랩이 W-15B에서 도달하는가 — **아직 아니다**
