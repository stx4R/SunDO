### 1.2 `resolve()`의 재사용 가능성 — §3의 전제

| 확인 항목 | 결과 | 조치 |
| --- | --- | --- |
| 시작 시 `status`를 `loading`으로 되돌리는가 | **아니다.** `resolve()`는 시작에서 `status`를 건드리지 않고 **끝에서만** 확정한다 | 규칙 2가 그대로 성립. 추가 수정 불필요 |
| 실패 시 `status`가 어떻게 되는가 | 🔴 **`getDoc` 실패 경로가 `setProfile(null)` + `setStatus('loading')`을 한다**(`AuthProvider.tsx:232-233`) | **규칙 2·3 위반이다.** `loading`이 되면 `AuthGate`가 스플래시를 씌워 S2-1이 30초마다 사라지고, `profile`이 비면 신원 요약 줄도 사라진다. → `{ silent?: boolean }` 매개변수를 더해 재조회에서만 이 두 줄을 건너뛰게 했다(§3) |
| 현재 `User` 객체를 어디서 얻는가 | `onAuthStateChanged` 콜백 인자로만 받는다 | `refresh()`는 `auth.currentUser`를 쓴다. 재인증을 유발하지 않는다 |
| DR-12 동기화·감사 로그를 함께 하는가 | DR-12는 **한다**(`nameSource !== 'manual' && displayNameRaw !== raw`일 때만). **감사 로그는 하지 않는다** — `grep -rn "auditLog\|PROFILE_SYNC" src/`의 유일한 결과가 "W-15 이후다"라고 적은 **주석 1줄**이다 | 조건부라 갱신이 끝난 뒤에는 다시 돌지 않는다. **"멈추고 물어라" 조건이 발동하지 않았다.** DoD 11로 실측 확인 |

### 1.4 `승인 확인` 스피너 색 — 🔴 §8 토큰 승격의 단서가 발동한다

| 항목 | S1 Google 버튼(`12b`) | S2-1 `승인 확인`(`3c`) |
| --- | --- | --- |
| 구현 방식 | CSS 테두리(`border` + `border-top-color`) | **SVG 원호**(`<circle>` 트랙 + `<path>` 호) |
| 회전부 | `#2E6B4C` | **`#1F5138`** |
| 트랙 | `rgba(46,107,76,0.22)` | **`rgba(31,81,56,0.22)`** |
| 모션 | `spin .8s linear infinite` | `spin .8s linear infinite` |

**트랙 색이 다르다.** §8의 단서("design 원문에서 S2-1 트랙이 `rgba(46,107,76,0.22)`가 아니면 승격하지 말고 보고만 하라")가 그대로 발동한다.

두 값의 관계를 보면 규칙이 보인다 — **트랙은 회전부 색의 알파 0.22다.**
`#2E6B4C` → `rgba(46,107,76,0.22)`, `#1F5138` → `rgba(31,81,56,0.22)`.
공유할 수 있는 것은 색이 아니라 **"회전부의 22%"라는 관계**이고, 그건 토큰 1개로 표현되지 않는다.
**승격하지 않았다.** §7에 PRD 반영 후보로 올린다.

## 5. 판단이 필요했던 지점

### 5-1. 뱃지 내부 하이라이트 `0.85` vs design `0.8` — W-06 §5-2와 같은 건

`--highlight-top` 공유 토큰(`.glass`·`.dock`·`.pend-badge`)에서 온다. W-02가 design 다수값 `0.85`로
확정하고 W-04가 재확인했으며, W-06 §0.2-2가 **유지**로 회신했다. 같은 판단을 이어간다.

### 5-2. 🔴 변형 B의 보조 줄 — **지시서를 따르고 design·PRD와 갈렸다**

| 출처 | 규정 |
| --- | --- |
| 지시서 §5.3 | B 보조 = **(없음)** |
| design `3b` | 보조 줄 **있다** — `승인 결과는 이 화면에서 자동으로 반영됩니다.` |
| PRD §8.2.6 | 보조 줄은 본표에 있고, `거절 상태` 행은 **제목·본문·버튼만** 덮어쓴다 → 있는 쪽 |

design과 PRD가 함께 "있다"이고 지시서만 "없다"인, 흔치 않은 형태다.
**지시서를 따랐다.** 결정적 근거는 **지시서 내부의 일관성**이다 —

§6.1이 `폴링은 pending에서만 돈다. rejected에서는 돌지 않는다`고 규정한다(DoD 13으로 실측 확인, 0회).
그러면 B에서 `승인 결과는 이 화면에서 자동으로 반영됩니다`는 **사실이 아닌 문장**이 된다.
자동 반영되지 않는 화면에서 자동 반영을 약속하면, 사용자는 오지 않을 변화를 기다린다.
design 3b는 §6.1의 폴링 규칙보다 먼저 그려진 화면이고, 그 규칙과 함께 읽으면 보조 줄은 **잔여물**이다.

**되돌리기 비용은 조건 1개다**(`{!rejected && ...}` 제거). §6에 PRD 반영 후보로 올린다.

### 5-3. 칩 점의 이징 — `ease-in-out`(design) vs `ease`(PRD)

W-05 §5.2에서 이미 정리한 건이다. §7.4가 `pulseDot 1.6s ease infinite`를 명시하므로 PRD를 따랐고,
`.splash-dot`도 같은 값이다. **두 점의 이징이 갈라지지 않게** 같은 판단을 유지했다.

### 5-4. `승인 확인` 버튼의 내부 링 — `.neu`를 건드리지 않았다

design `3a`·`3c`의 버튼에는 `.neu`의 내부 링(`inset 0 0 0 1px rgba(255,255,255,0.6)`)이 없고,
`:active` 그림자 퍼짐도 `5px/12px`(우리 `.neu`는 `7px/16px`), 눌림 배율도 `0.97`(우리는 `0.98`)이다.

**PRD §7.3이 `neu`를 "그라디언트 + `--shadow-neu` + **내부 링**, `:active`는 인셋 + `scale(0.98)`"로
명시한다.** 충돌 해소 순서 1번이 그대로 적용되어 PRD가 이긴다.
게다가 `.neu`는 S4 학년 버튼·S5 반 버튼·S8 코드 재발급 버튼이 함께 쓰는 **공유 표면**이라,
S2-1 하나 때문에 내리면 세 화면이 함께 움직인다.

같은 이유로 **변형 C의 눌림 표현(`.pend-busy`)도 design 3c의 `5px/12px`가 아니라
`.neu:active`와 같은 `7px/16px` + 내부 링**으로 맞췄다. 같은 표면의 눌림이 두 벌 생기면 갈라진다.

### 5-5. B 주 버튼의 광택(`shine`) — design에 없고 PRD에 있다

design `3b`의 라벨에는 광택 표기가 없다. PRD §7.3이 `shine → btnp 내부 텍스트`,
§7.4가 `shine 2.8s linear infinite → 주 버튼 라벨`을 명시한다. 충돌 해소 순서 1번으로 PRD를 따랐고,
`PrimaryButton`이 이미 그렇게 구현돼 있어 **추가 코드는 없다.**

### 5-6. ⚠️ 지시서 밖의 수정 1건 — `cn.ts`에 W-06 토큰 2종을 등록했다

**이것은 지시서가 요구하지 않은 변경이다.** 사용자가 판단할 수 있게 먼저 적는다.

W-06에서 `@theme`에 `--text-brand`·`--text-subtitle`을 추가하면서 `src/lib/cn.ts`의
`classGroups`에 등록하지 않았다. PROGRESS의 확정 규칙("`@theme`에 새 커스텀 스케일을 추가하면
`cn.ts`의 `classGroups`에도 함께 등록해야 한다")을 W-06이 지키지 못한 것이다.

당시에는 두 값이 CSS 클래스(`.brand-title`·`.brand-sub`)로만 쓰여 증상이 없었다. 그런데
**이번에 `승인 확인`·`로그아웃` 라벨이 `cn('text-subtitle', …)` 형태로 유틸리티를 처음 쓴다.**
등록이 없으면 tailwind-merge가 `text-subtitle`을 **색**으로 보고 `text-sundo-800`과 같은 그룹으로
묶어 **뒤엣것만 남긴다** — 글자 크기가 조용히 사라지는 W-02 §4.4의 결함과 같은 형태다.

2줄 추가로 막았다. **되돌리려면 `cn.ts`의 `'brand', 'subtitle'` 2줄을 지우면 되지만,
지우면 이번 회차의 13px 라벨이 깨진다.**

### 5-7. ⚠️ 지시서 밖의 수정 2건 — `NeuButton`에 `aria-disabled`를 붙였다

§7이 "`승인 확인` — 쿨다운·확인 중 모두 `aria-disabled="true"`"를 요구하고 DoD 24가 이를 검사한다.
그런데 `NeuButton`의 API(`{ children, onClick?, radius?, disabled?, className? }`)에는
임의 속성을 넘길 방법이 없어, **실측에서 `aria-disabled: null`이 나왔다.**

선택지는 둘이었다 — (a) `NeuButton`에 1줄 추가, (b) S2-1에서 `NeuButton`을 버리고 생 `<button>`에
`.neu` 클래스를 직접 붙이기. (b)는 §5.2의 "주 버튼 = `NeuButton`"을 어긴다. **(a)를 택했다.**

`aria-disabled={disabled || undefined}`는 네이티브 `disabled`를 그대로 반영할 뿐이라
다른 `NeuButton` 사용처(아직 없다)에도 무해하다.

### 5-8. 하단 영역을 `absolute`가 아니라 흐름으로 고정했다

design 3a는 `position:absolute; left:22px; right:22px; bottom:104px`이다. 그대로 옮기지 않았다.

- `104px`은 목업 프레임의 홈 인디케이터 영역을 포함한 값이라 `env(safe-area-inset-bottom)` 기준으로
  옮길 수 없다. 지시서 §5.1이 **`safe-area + 26px`**을 지정했고 그 값을 썼다.
- `absolute`로 두면 200% 확대에서 본문과 겹친다. `min-h-full` + `flex-1` 중앙 정렬 + 흐름 마지막
  블록으로 두면 확대 시 자연스럽게 세로 스크롤이 된다(DoD 26 — 가로 스크롤 0, 세로만 넘침).

Footer 간격은 `로그아웃` 상자 아래 **20px**을 맞췄다 — 부모 `gap-3`(12px) + 래퍼 `-10px` +
`Footer`의 `pt-[18px]` = 20px. design 3a도 `gap 12px` + 래퍼 `margin-top:8px` = 20px이다(실측 20px 일치).

## 9. 🔴 W-12에 넘길 전제 — 지금 심는 부채

**`onSnapshot`으로 전환하면 아래 둘을 반드시 걷어내야 한다.**

| 제거 대상 | 위치 | 이유 |
| --- | --- | --- |
| `refresh()` | `src/contexts/AuthProvider.tsx` | 구독이 들어오면 수동 재조회가 중복이 된다. `resolve()`의 `{ silent }` 매개변수도 함께 의미를 잃는다 |
| 30초 폴링 루프 | `src/screens/Pending.tsx` | 구독이 상태 변화를 밀어 주므로 주기 조회가 순수 낭비다. `visibilitychange` 핸들러·`pollTimer`·`runRefresh(false)` 경로 전부 |
| `승인 확인` 버튼 자체 | `src/screens/Pending.tsx` | §8.2.6이 버튼을 규정하므로 **남긴다.** 다만 쿨다운의 의미는 달라진다 — 구독 중에는 강제 재조회가 필요 없다. **§8.2.6 개정 여부를 W-12가 판단해야 한다** |

**A안을 택한 이유를 함께 남긴다** — B(`onSnapshot`)의 기각 사유는 "규칙이 아직 임시인 상태에서,
W-17이 다시 볼 예정인 `getDoc` 경로 위에 모든 인증 읽기의 형태를 바꾸는 베팅"이었다.

`resolve()`를 재사용하므로 W-17이 `getDoc` 경로를 고치면 `refresh()`도 함께 고쳐진다.

그 대신 **W-12가 걷어내야 할 코드가 두 곳 생겼다.** 그것이 이 선택의 값이다.

**`AuthProvider`는 실물 그대로 두고, 그 아래의 Firebase 모듈만 갈아 끼웠다.**

- `vite.config.ts`에 **임시** 별칭 4개 → `firebase/firestore` · `firebase/auth` · `lib/firebase`를
  `src/__stub/*`로 치환. `getDoc` 호출 횟수·성공/실패/무응답을 테스트가 직접 지시한다.
