## 2. 🔴 Q-1~Q-5 실측 전문 — 이 다섯이 규칙 구조를 결정했다

### 2-1. Q-1 — `list`는 경로 와일드카드 조건을 **증명하지 못한다**

세 가지 규칙 형태를 같은 데이터에 대고 돌렸다.

| 규칙 | 단건 `get`(본인) | 단건 `get`(남) | 컬렉션 `list` |
| --- | --- | --- | --- |
| `allow read: if request.auth.uid == uid \|\| true` | 허용 | 허용 | 허용 |
| 🔴 `allow read: if request.auth.uid == uid` | 허용 | — | 🔴 **거부**(`permission-denied`) |
| `allow get: 본인` + `allow list: 인증` | 허용 | **거부** | 허용 |

같은 「본인만」 규칙에서 **`where(__name__ == 본인)`으로 좁힌 질의는 통과했다.**

**해석** — `list`는 「질의가 규칙 조건을 **스스로 증명**할 수 있을 때」만 통과한다.
S8 ②의 질의는 `departmentId ==` + `status ==`라 「본인」을 증명할 수 없다.
**부록 B의 `allow read` 뭉치기를 그대로 쓰면 S8 ②(부원 목록)와 S7(작성자 이름 묶음 읽기)이 배포 순간 죽는다.**

→ **`users`·`approvalRequests`·`records`·`students`·`dutySchedules`·`auditLogs`·`inviteCodes` 전부 `get`/`list`를 나눴다.**
`records`처럼 문서별 절이 없어 판정이 같은 곳도 **나눠 적었다** — 나중에 문서별 조건이 붙을 때 `list`가 조용히 죽지 않도록.

### 2-2. Q-2 — 배치 안 `get()`은 **배치 이전** 상태를 본다

`dept.headUid`를 대상 uid로 바꾸는 연산과 `users/{대상}.role='head'`를 **같은 배치**에 넣고,
`users` 규칙이 `get(dept).headUid == uid`를 요구하게 했다.

```
배치가 같은 배치의 dept 변경을 근거로 users write   →  거부 (permission-denied)
   evaluation error at L8:23 for 'update' @ L8, false for 'update' @ L8
```

**해석** — 규칙은 **형제 연산의 결과를 볼 수 없다.** 그런 조건을 쓰면 배치가 **자기 자신을 거부**한다.
통과하는 경로가 아예 없다.

🔴 **그래서 「`departments.headUid`를 단일 진실로 삼고 `users.role=='head'`를 파생으로 강제한다」는 안(W-15B §4)을 채택하지 않았다.** — §4-3

🔴 **같은 사실이 반대 방향으로도 일한다.** head가 실행하는 양도 배치는 같은 배치에서 본인을 `member`로 내리는데,
`departments` update의 `isHead()`가 부르는 `get()`은 **배치 이전**을 보므로 여전히 `head`로 읽혀 **통과한다**(`B-4`).
「배치 안에서 자기 권한을 먼저 버리면 뒤 연산이 죽는다」는 걱정은 이 스키마에서 성립하지 않는다.
**규칙 파일 `departments` 블록 주석에 그 사실을 적어 뒀다** — 우리가 그것에 기대고 있기 때문이다.

### 2-3. Q-3 — 배치는 **부분 성공이 없다**

허용 컬렉션 2 + 거부 컬렉션 1로 3연산 배치를 만들었다.

```
3연산 중 2번째만 거부되는 배치        →  거부 (permission-denied)
거부 뒤 실제로 남은 허용 연산 문서 수   →  0 / 2
```

**해석** — 「4연산 중 3개는 통과한다」는 관측은 **의미가 없다.** 개별 연산 테스트로 배치를 대체할 수 없다.
그래서 배치 조합 **16케이스를 실제 `writeBatch`로** 돌렸다(§3-3).

### 2-4. Q-4 — 규칙 `get()`의 과금과 상한 (수치)

| 측정 | 결과 |
| --- | --- |
| 단건 write · **서로 다른** 문서 `get()` 9회 | 허용 |
| 단건 write · **서로 다른** 문서 `get()` 10회 | 허용 |
| 🔴 단건 write · **서로 다른** 문서 `get()` 11회 | **거부** — `Service call error. Function: [get] … costs/c10` |
| 🔴 단건 write · **같은** 문서 `get()` 15회 | **허용** |
| 배치 3연산 × 서로 다른 문서 8회(합계 24) | 허용 |
| 배치 4연산 × 서로 다른 문서 6회(합계 24) | 허용 |

**해석 세 가지**

1. **캐시된다.** 같은 문서를 몇 번 보든 **1회**다. → `isActive()`·`role()`·`isHead()`를 한 규칙에서 몇 번 부르든 **연산당 1읽기**다.
2. **상한은 서로 다른 문서 기준 10건**이고, **연산마다** 적용된다(합계 24가 통과했다).
3. **비용** — 이 규칙에서 가장 무거운 요청은 **승인 4연산 배치 = 4읽기**다.
   S6 저장 2연산은 **1읽기**다(본인 `users` update는 `request.auth.uid == uid`에서 갈려 `get()`을 돌지 않는다).
   부원 40명 · 하루 400건 저장을 가정해도 **하루 400읽기 추가**로, 무료 한도(50,000/일)의 0.8%다. **무시 가능하다.**

⚠ **이 수치는 에뮬레이터 값이다.** 프로덕션 문서는 배치·트랜잭션의 상한을 **요청 합계 20**으로 적는데,
에뮬레이터는 합계 24를 통과시켰다(연산별로만 센다). **우리 규칙은 연산당 최대 1읽기라 어느 쪽 상한에도 걸리지 않는다** —
그래서 이 차이가 이번 배포의 위험은 아니다. 규칙에 `get()`을 더 붙이는 회차가 오면 **다시 재야 한다.**

### 2-5. 🔴 Q-5(신규) — `$` 앵커는 아무것도 막고 있지 않다

**지시서에 없던 측정이다.** 역검증에서 `no-dollar-anchor`(정규식 끝의 `$` 제거)가
**아무 테스트도 빨갛게 만들지 못해서** 원인을 찾다 나왔다.

| 정규식 | `ok@dshs.kr` | `attacker@dshs.kr.evil.com` | `dshs.kr@evil.com` |
| --- | --- | --- | --- |
| `.*@dshs[.]kr$` | 허용 | **거부** | 거부 |
| `.*@dshs[.]kr` (**`$` 없음**) | 허용 | 🔴 **거부** | 거부 |
| `.*@dshs[.]kr.*` | 허용 | 🔴 **허용** | 거부 |

**해석** — Rules의 `matches()`는 **문자열 전체 일치**다. `$`가 있든 없든 결과가 같다.
실제로 뚫리는 형태는 **끝에 `.*`가 붙었을 때**뿐이다.

🔴 **PRD §9.6 필수 조건 1과 부록 B 주석의 「없으면 `attacker@dshs.kr.evil.com`이 통과한다」는 사실이 아니다.**
`$`는 **유지했다**(필수 조건 1이 요구하고, 부분 일치 API로 옮겨 가는 날의 이중 방어다).
다만 **「이것이 막고 있다」로 읽으면 안 된다** — 그렇게 읽으면 정규식을 손볼 때 진짜 급소(`.*` 접미)를 놓친다.

**조치 3가지**
- 규칙 파일 주석을 실측대로 고쳤다(`firestore.rules` `isSignedIn()` 위).
- 역검증에 **`domain-suffix-open`**(끝에 `.*`)를 추가했다 → `SEC-4a`가 **빨개진다.** 도메인 방어가 살아 있다는 증거는 이것이다.
- `no-dollar-anchor`는 **「아무것도 빨개지지 않는 것이 정답」인 변형**으로 남겼다(`breaks: []`). 러너가 그 기대를 채점한다.

## 4. 판단과 이탈

### 4-1. 🔴 `get`과 `list`를 **전 컬렉션에서** 나눴다

Q-1의 답이 「나눠야 한다」였다(§2-1). 지시서 §3.2가 지목한 4개(`users`·`approvalRequests`·`records`·`students`)를 넘어
**`dutySchedules`·`auditLogs`·`inviteCodes`까지 전부** 나눴다. 판정이 같은 곳도 나눠 적은 이유는
**나중에 문서별 조건이 붙을 때 `list`가 조용히 죽는 것을 막기 위해서**다. 그 사실을 규칙 주석에 남겼다.

### 4-2. 🔴 `users` list는 **넓게 열고, 필드 제한은 클라이언트가 맡는다**

이번 회차 최대 위험이다(W-15B §8-5 1순위). **좁게 쓰면 S8 ②가 통째로 죽고, 넓게 쓰면 부서 전체 `users`가 전 필드 노출된다.**

**후자를 택했다.** 근거는 이미 닫혀 있다 — 결정 R-b · W-14 결정 3.
**Rules의 `allow read`는 문서 단위라 필드 제한을 표현할 수 없다.** 「부원은 이름·역할만」은 규칙이 표현할 수 없는 조항이고,
실제로 S8 ②는 이메일을 그리지 않는다(W-15B DoD 7 실측). **그 사실을 규칙 파일 주석에 명시했다**(지시서 §3.2 요구).

### 4-3. 🔴 BR-18(부장 정확히 1명) — **규칙은 끝까지 보장하지 못한다.** 그래서 보장하는 척하지 않았다

W-15B §4의 판단 요청(「`headUid`를 단일 진실로 삼고 `users.role=='head'`를 파생으로 강제할 것인가」)에 대한 답은
**「채택하지 않는다」**다. 근거는 Q-2 실측이다 — 그 조건은 **양도 배치가 자기 자신을 거부하게 만든다**(§2-2).

**규칙이 실제로 보장하는 것 3층**

| 층 | 무엇 | 증거 |
| --- | --- | --- |
| 1 | `role` 변경은 `head`·`dev`만 | `T-4`·`T-5`·`T-6` 거부 |
| 2 | 부장은 자기 역할을 직접 못 바꾼다 — **`head → member` 한 전이만** 열려 있다 | `T-7` 거부 · `T-2` 통과 |
| 3 | 클라이언트 배치의 **원자성** | 🔬 **Q-3 실측** — 3연산 중 1개 거부 시 남은 문서 **0/2** |

**남는 구멍 2가지 — 알고 남긴다**

1. **동시 양도 경쟁.** Rules는 **집합을 셀 수 없다**(`role == 'head'`인 문서가 몇 개인지 규칙 안에서 알 수 없다).
2. **양도 없이 혼자 내려가는 head.** `head → member` 단독 update는 통과한다(부장 0명). 규칙은 형제 연산을 못 본다.

→ 둘 다 §11.3 `transferHeadRole` Cloud Function이 닫는다(v1.2).
🔴 **그때까지 BR-23 Dev 복구 경로(양도 3연산)가 유일한 탈출구이므로 규칙이 그것을 막지 않도록 `B-6`이 지킨다.**
**규칙 파일 주석에 이 세 층과 두 구멍을 전부 적었다** — 다음 사람이 「규칙이 BR-18을 보장한다」로 오해하면 위험하다.

### 4-4. 🔴 BR-21 ↔ 양도의 자기 강등을 **한 전이로** 갈랐다

「본인 `role` 변경 금지」를 그대로 쓰면 **head 실행 양도가 죽는다**(강등 대상이 곧 본인이다 — W-15B §4-1).
`selfDemoteOnTransfer(uid)`로 **`head → member` 한 전이만** 열었고, 허용 키도 `role`·`updatedAt` 2개로 묶었다.

🔴 **`departments.headUid` 갱신을 조건으로 걸지 않았다** — Q-2 때문이다.
이 함수만으로는 「양도 없이 혼자 내려가는 head」를 막지 못하지만, **그것을 막으려는 조건은 양도 자체를 죽인다.**
지시서 §3.4의 방향을 그대로 따랐고, T-2(통과)·T-7(거부)을 **둘 다** 실측했다.

### 4-5. `recordCount` **단독 update를 허용으로 판단했다** (지시서 §3.6이 판단을 요구한 항목)

`records` create 없이 `recordCount`만 +1 하는 단독 update는 **통과한다**(`RC-5`).

**막을 수 없다.** 규칙은 형제 연산을 볼 수 없으므로(Q-2) 「같은 배치에 `records` create가 있는가」를 조건에 쓸 방법이 없다.
**막을 필요도 낮다** — 상한이 「한 번에 +1」이라 남용해도 자기 카운트를 부풀릴 뿐이고,
그 값은 지표(M-02)에만 쓰인다. 실질 차단은 §11.3 Cloud Function 소유다(v1.2).
**이 판단을 규칙 파일 주석과 `database_ToDo/W-16.md` §7에 남겼다.**

⚠ 함께 판단한 것 — **`head`는 남의 `recordCount`를 임의 값으로 바꿀 수 있다**(`RC-7` 통과).
§9.6이 「역할·기타 상태 변경은 `head`·`dev`만」으로 `users` update를 넓게 열어 둔 결과다. **좁히지 않았다** —
좁히면 승인 배치(`status`·`approvedBy`·`approvedAt`)를 필드 단위로 다시 규정해야 하고, 그것은 이 회차의 범위가 아니다.

### 4-6. `records.ts` — **한 줄이 아니라 한 곳**, 계약은 그대로다

지시서는 「한 줄」이라 적었지만 실제 변경은 `setDoc` 1건 → `writeBatch` 2연산이라 **한 함수 본문**이 바뀐다(+27/−10).
**깨지 않은 것 3가지**

- `writeRecord`는 여전히 **`void`**를 돌려준다. 호출부가 실수로 기다릴 방법이 없다(W-12 §5-3).
- `batch.commit()`을 **`await`하지 않는다.** 오프라인에서 resolve되지 않기 때문이다(W-08 §5-7 · W-12 §1-3).
- `catch`로 삼키고 `console.error`로 흔적만 남기는 형태도 그대로다.

⚠ **`batch.update`는 대상 문서가 없으면 배치 전체를 실패시킨다**(W-15A §4-2).
`users/{본인}`은 `AuthProvider`가 문서를 읽어 `status === 'active'`를 확인한 뒤에야 S6에 도달하므로 **항상 존재한다.**
**그 전제를 주석에 남겼다.**

### 4-7. 인덱스는 **2건**이다 — §9.5의 13건 중

앱이 실제로 내는 질의가 요구하는 것만 넣었다: **IX-01**(`academicYear`·`status`·`occurredAt DESC`) ·
**IX-02**(+`reasonCode`). 나머지 11건의 미포함 이유는 `database_ToDo/W-16.md` §8에 표로 있다.

**단일 필드 면제 4종**(`records.studentName`·`records.reasonText`·`users.email`·`users.displayNameRaw`)은
`fieldOverrides`의 `"indexes": []`로 **표현할 수 있었다.**
🔴 **특히 `reasonText`는 인덱싱하면 §14.1 PR-02의 통제 취지가 무너진다** — 자유 기입이 검색 가능해진다.

### 4-8. 롤백 원본을 **별도 파일**로 남겼다

§18.4는 「Rules 롤백 = Git 이력에서 이전 버전 재배포」로 규정하는데 **이번이 `firestore.rules`의 첫 커밋**이라
이력에 이전 버전이 없다. W-04 임시 catch-all을 `firestore.rules.catchall`로 보존했고,
🔴 **`firebase.json`이 그 파일을 가리키지 않는다.** 1분 롤백 절차는 `database_ToDo/W-16.md` §3이다.

### 4-9. 의존성 2개를 `devDependencies`로만 추가했다 (결정 1 · 규약 예외)

`firebase-tools@^15.28.1` · `@firebase/rules-unit-testing@^5.0.2`.

## 6. 검증 환경과 측정 함정

### 6-1. 🔴 Java가 「있는데도 없다」 — PATH 앞자리 문제

에뮬레이터는 Java 11+를 요구한다. **설치돼 있어도 `java -version`이 8을 내면 뜨지 않는다** —
Oracle Java 8이 시스템 PATH 앞자리를 잡고 있으면 Temurin 21을 새로 깔아도 앞의 것이 먼저 잡힌다.
**세션 PATH에 21을 앞에 끼운 창에서 Claude Code를 띄워** 해결했다(`openjdk 21.0.12.1`).
🔴 **「Java를 설치했다」와 「에뮬레이터가 쓰는 Java가 21이다」는 다른 문장이다.**

### 6-2. 실 Firestore 접속 0건을 만드는 방법

`initializeTestEnvironment`의 `projectId`를 **`demo-` 접두사**로 줬다(`demo-sundo-rules`).
에뮬레이터가 그것을 「demo 프로젝트」로 인식해 **비에뮬레이터 서비스 접근 시도를 실패시킨다**:

```
Detected demo project ID "demo-sundo-rules", emulated services will use a demo configuration
and attempts to access non-emulated services for this project will fail.
```

`sundo-dev-8ef38`은 테스트 어디에도 없다.

### 6-3. 🔴 픽스처를 `withSecurityRulesDisabled`로 심어야 하는 이유

규칙을 통과시켜 심으면 **테스트가 검증 대상에 의존하게 된다.** 규칙이 넓어졌을 때 픽스처가 함께 통과해
결함을 가린다. `harness.mjs`의 `seed()`·`put()`이 전부 규칙을 끈 채로 쓴다.

### 6-4. 이 회차 고유의 함정 5건

1. 🔴 **「통과」만 확인하면 조건을 안 쓴 규칙도 통과한다.** → 역검증 18변형(§3-4). **이 회차의 최대 산출이 여기서 나왔다**(§2-5).
2. 🔴 **배치는 한 연산만 걸려도 전체가 거부된다.** 개별 테스트로 대체 불가 → 배치 16케이스를 실제 `writeBatch`로.
3. **에뮬레이터의 기본 규칙은 전부 허용이다.** 규칙 파일이 실제로 로드됐는지 먼저 확인해야 한다 →
   `LOAD-1`(PRD 밖 컬렉션 `zzruleprobe` 읽기·쓰기 거부)로 매 실행 확인. 프로브에도 같은 확인이 있다.
4. **`request.time`은 에뮬레이터 시각이다.** `occurredAt +5분` 케이스가 여기 걸린다 —
   픽스처의 시각을 절대값이 아니라 **`Date.now()` 기준 상대값**으로 만들어 피했다.
5. 🔴 **신규 — 저장소 규칙 파일은 CRLF이고 변형 조각은 LF다.** 정규화 없이 `includes()`로 찾으면
   **조각을 영원히 못 찾는다.** `run.mjs`가 비교 전 LF로 정규화하고, 원복은 **바이트 사본**에서 한다
   (정규화한 문자열을 되쓰면 파일 전체 줄바꿈이 바뀐다).

## 8. 다음 회차(W-17 — S10 설정 + 계정 탈퇴)에 넘길 전제

### 8-1. 🔴 `selfWithdraw()` 규칙이 **이미 서 있고 S10이 그 첫 소비자다**

```
resource.data.status == 'active'
resource.data.role != 'head'                      // BR-56 · R-07
request.resource.data.status == 'withdrawn'
affectedKeys().hasOnly(['status','withdrawnAt','updatedAt'])   // 🔴 정확히 3개
```

🔴 **허용 키 3개를 코드가 정확히 맞춰야 한다.** 하나라도 더 쓰면(예: `withdrawReason`·`anonymizedAt`)
**탈퇴가 통째로 거부된다.** `SEC-9c`가 그 케이스를 이미 잡고 있다(탈퇴하면서 `role`을 함께 바꾸면 거부).
**규칙을 넓히기 전에 §9.6 필수 조건 7과 대조하고, 넓혀야 한다면 물어라.**

### 8-2. 부장 탈퇴 차단은 **규칙과 클라이언트 양쪽**에서 막는다

- **규칙** — `resource.data.role != 'head'`(`SEC-9a` 거부). 역검증 `selfwithdraw-head-allowed`가 이 조건이 살아 있음을 증명한다.
- **클라이언트** — S10이 부장에게 탈퇴 버튼을 **비활성**으로 그려야 한다(§8.11 · BR-56).
  🔴 **규칙만 믿으면 사용자는 「눌렀는데 아무 일도 안 일어난다」를 본다** — 문구가 §8.10에 없다면 그것이 W-17의 규격 공백이다.
- ⚠ **`dev`는 막히지 않는다** — `role != 'head'`만 보므로 Dev 계정은 탈퇴할 수 있다. 의도인지 확인이 필요하다.

### 8-3. `departments.memberCount` 감소(BR-57)는 **규칙에서 열려 있다**

`departments` update가 `isHead()`이므로 **부장·Dev만** 바꿀 수 있다.
