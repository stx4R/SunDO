## 0. W-03C 보고서 §7 미회신 4건 — 원문 재수록

지시서 §0.1-5에 따라 **요약하지 않고 원문 그대로** 옮긴다. 회신은 다음 회차에 받는다.
(5번 `ToastProvider` 위치는 W-05 §4-2에서 그대로 구현했으므로 해소됐다.)

> 1. **§1의 지정 문자열을 바꿨다**(§4-1). `fs.rmSync`가 이 Node(v24.2.0/Windows)에서 프로세스째
>    죽어서 `fs.promises.rm`으로 갔다. 의존성·실행 방식·의도는 그대로다.
>    - 되돌리기 비용: `package.json` 1줄. 단 되돌리면 빌드가 다시 죽는다.
>    - **W-03B 보고서 §8-1의 "OneDrive 원인" 진단은 오진이었다.** PRD/보고서에 반영이 필요하면 알려달라.
>    - 근본 대응(선택): Node LTS(22.x)로 내리면 `rmSync`가 정상 동작할 가능성이 높다. 확인해 볼지.
> 2. **시트 내부 하이라이트가 design보다 알파 0.05 낮다**(§4-6). 지시서 §5.1·§2.1을 따른 결과다.
>    원문(0.9)으로 되돌리려면 `.sheet` 1줄만 바꾸면 된다.
> 3. **시트 모션이 design `sheetUp`과 다르다**(§4-5). 지시서·DoD 14가 `translateY(110%)`를
>    명시해 그쪽을 따랐다. design 연출(55% + 페이드)로 갈지 정해달라.
> 4. **토스트에 수동 닫기 수단이 없다.** §6.4 규격대로 2.2초 자동 소멸만 있다. AC-10이
>    "토스트에만 의존해 중요한 정보를 전달하지 말라"고 하므로 현행이 규격 위반은 아니다.
>    다만 스크린리더 사용자가 낭독 도중 사라질 수 있다 — W-18 접근성 점검 항목으로 넘긴다.

> **2번은 이미 해소됐다.** W-04 §2에서 design 원문 `0.9`로 되돌렸다(W-04 지시서 §2 지시).
> 원문을 그대로 옮기라는 §0.1-5 지시에 따라 삭제하지 않고 이 주석만 덧붙인다.

### 2.2 `AuthProvider` 계약 (읽기만 함 — 로직 수정 0줄)

| 확인 항목 | 결과 |
| --- | --- |
| `signIn` 시그니처 | `() => Promise<void>`. **throw하지 않는다** — 모든 실패를 내부에서 잡아 `errorCode`로 노출한다. 시작 시 `setErrorCode(null)`로 초기화한다 |
| `errorCode` 타입 | `string \| null`. **닫힌 union이 아니다** — Firebase의 `error.code`가 그대로 통과한다 |
| `errorCode` 리터럴 폴백 5종 | `auth/redirect-failed` · `auth/delete-user-failed` · `firestore/get-profile-failed` · `firestore/profile-sync-failed` · `auth/unknown`. (설정 지점 10곳: `AuthProvider.tsx:124·175·210·257·275·291·297·302·310`) |
| 취소 코드 | **`auth/popup-closed-by-user`.** W-04 §9가 "취소는 에러가 아니다 — 이 코드가 `errorCode`로 온다"고 명시 |
| 차단 코드 | **`errorCode`에 도달하지 않는다.** `auth/popup-blocked`·`auth/cancelled-popup-request`·`auth/operation-not-supported-in-this-environment`는 `REDIRECT_FALLBACK_CODES`에 있어 조용히 리다이렉트로 폴백한다(EC-30 — "사용자에게 에러를 노출하지 않는다"). 폴백 자체가 실패하면 `auth/redirect-failed`가 대신 온다 |
| 시도 초과 코드 | `auth/too-many-requests` (Firebase 표준. `signIn`의 `catch`가 그대로 통과시킨다) |
| `status` union | **9개**: `loading` · `signedOut` · `domainRejected` · `noProfile` · `pending` · `active` · `rejected` · `suspended` · `withdrawn` |
| `rejectedEmail` / `clearRejection` | `string \| null` / `() => void`. `clearRejection`은 `domainRejected`를 `signedOut`으로 되돌리고 `rejectedEmail`·`errorCode`를 비운다 |
| 도메인 불일치 시 `deleteUser`+`signOut` | **`AuthProvider`가 이미 부른다**(`resolve()` 내부, `deleteUser` → `signOut` 순서). **S1은 배너·칩만 그린다** |

> **W-05 §3이 다룬 12개는 `status` union이 아니라 접근 매트릭스의 열(役 7 + 상태 5)이다.**
> `active` 하나가 부원·차장·부장·교사·Dev 5열을 덮고 `loading`은 스플래시가 먹어 매트릭스에 없다.
> 9 + (active가 5열) − (loading 제외) = 12. **어긋난 항목 없다.**

**차단 코드가 `errorCode`에 도달하지 않는 것은 결함이 아니다.** §6.3 표의 "팝업 차단·사용자 취소 → TS-17"에서
차단 절반은 EC-30 설계상 발화하지 않는 것이 맞다. 그래도 방어로 `CANCEL_CODES`에 넣어 두었다(§4-3).

## 5. 판단이 필요했던 지점

### 5-1. 부제의 `blurIn` — design에 없고 PRD에 있다

design `12a`의 부제에는 `animation` 선언이 **없다.** PRD §8.1.2 #3은 `blurIn 0.5s 지연`을 명시하고
지시서 §6.1 #3도 `blurIn`이라 적었다.

**충돌 해소 순서 1번(PRD가 명시한 값이 있고 design이 손실 없는 이형이 아니면 → PRD)** 을 적용했다.
모션을 뺀 것은 이형이 아니라 **누락**이다 — 로고(`rise`)와 타이틀(글자별 `blurIn`)이 순차로 들어오는데
부제만 처음부터 떠 있으면 T-01 등장 순서가 끊긴다. 지연 `0.5s`는 타이틀 마지막 글자(`0.37s`)
다음이라는 점에서도 PRD 값이 자연스럽다. Splash(`10a`)의 부제는 design 원문에 `blurIn .35s ease .5s both`가
**있으므로**, 12a의 부재는 전사 누락으로 본다.

### 5-2. 카드 내부 하이라이트 `0.85` vs design 12a `0.8`

design 12a는 `inset 0 1px 0 rgba(255,255,255,0.8)`, 구현은 `0.85`다.

**바꾸지 않았다.** 이 값은 `.glass`가 아니라 **`--highlight-top` 공유 토큰**에서 온다.
`.glass`와 `.dock` 2곳이 함께 쓰고(W-04 DoD 5), W-02가 design 원문 `0.85`로 확정한 뒤
W-04 §2에서 재확인한 값이다. S1 하나 때문에 토큰을 내리면 **하단 독까지 함께 움직인다.**

- 차이는 흰색 inset 하이라이트의 알파 0.05다. 430px 화면에서 육안 식별이 불가능하다.
- design 안에서도 `0.85`(다수)와 `0.8`(12a)이 갈린다 — 12a 쪽이 소수다.
- 되돌리기 비용: `.glass`만 따로 떼면 1줄. 다만 `--highlight-top`의 존재 이유가 사라진다.

**§8-2의 확인 요청으로 올린다.**

### 5-3. 🟡 오프라인 배너를 밀어내지 않고 덮었다 (지시서 §5.2 지시)

| 출처 | 규정 |
| --- | --- |
| PRD §6.4 | `상단 고정` · `z-index 70` |
| design `12d` | 흐름 안에서 콘텐츠를 밀어냄 (컨테이너 `padding:54px 0 0` + 배너 `flex:none`) |

**충돌 해소 순서 1번을 적용해 PRD를 따랐다** — `position: absolute` · `z-index 70`으로 띄우고
콘텐츠를 밀어내지 않는다. 밀어내기는 `AppShell`에 슬롯을 하나 더 요구하는데, S1은 세로 중앙
정렬이라 상단에 여유가 있어 겹침이 문제가 되지 않는다(실측: 배너 하단 `56px`, 로고 상단은 그보다 한참 아래).

**독이 있는 화면(W-08 이후)에서 H1과 겹치면 그때 재판단한다.** S3·S7·S8·S9·S10은 상단 정렬이라
`safe-area + 34px`에서 제목이 시작하고 배너는 `safe-area + 16px`~`+56px`을 먹는다 — **겹친다.**
그 화면들을 만들 때 `AppShell`에 배너 슬롯을 넣는 안을 다시 봐야 한다.

**상단 오프셋 `16px`은 신규 확정값이다.** design 12d의 `54px`은 목업 프레임의 상태 표시줄을
포함한 값이라 `env(safe-area-inset-top)` 기준으로 옮길 수 없다(음수가 된다). 독의
`bottom: calc(env(safe-area-inset-bottom) + 16px)`을 위아래로 뒤집어 좌우 `18px`과 함께
**독의 거울상**이 되게 했다. 값을 새로 지어낸 것이 아니라 §6.2 확정값을 재사용한 것이다.

### 5-4. 연속 탭 차단은 상태가 아니라 ref로 해야 한다 — 실측에서 발견한 결함

`submitting` 상태와 DOM `disabled`만으로는 **같은 태스크 안의 연속 탭을 막지 못한다.**
실측에서 5회 연속 탭에 `signIn`이 **5회** 호출됐다 — React가 리렌더하기 전이라 5개의 핸들러가
전부 `submitting === false`를 보고, DOM `disabled`도 아직 붙지 않는다.

동기적으로 즉시 서는 `submittingRef` 빗장을 추가해 **1회**로 잡았다.
DoD 18이 이것을 지정하지 않았다면 놓쳤을 결함이다. 실기기에서도 더블탭·접근성 도구의
연속 활성화로 재현 가능하다.

### 5-5. `.splash-title` · `.splash-sub` → `.brand-title` · `.brand-sub` 개명

토큰 승격 후 S1이 이 두 클래스를 **그대로 공유**하게 됐다. 이름에 `splash`가 남아 있으면
W-07 이후 "스플래시 스타일"인 줄 알고 고쳤을 때 S1이 함께 깨진다. `BrandLogo`/`.brand-logo`와
같은 이름 체계로 맞췄다.

**시각 규격은 한 글자도 바뀌지 않았다** — 선택자 이름만 바꾸고 §4.2에서 Splash 전 항목을 재측정해 확인했다.

### 5-6. 로그인 시도 실패 배너를 변형 A에 얹었다 (6번째 변형을 만들지 않았다)

§6.3은 시도 초과·네트워크·알 수 없는 오류를 "카드 내 배너"라 하는데 §6.4의 변형 목록에는
A~E만 있다. C·E가 `status`로 갈리는 것과 달리 이 셋은 `errorCode`로 갈리므로 **변형 A + 배너**로 다뤘다.

C·E일 때는 시도 실패 배너를 띄우지 않는다. `domainRejected`는 `auth/delete-user-failed`를
동반할 수 있어(W-04 §6) 둘 다 그리면 카드에 빨간 배너가 2개 쌓인다. 도메인 거절이 더 구체적인 원인이다.

### 5-7. 토큰화하지 않고 인라인으로 남긴 리터럴 (W-06 신규분)

W-03B §3 기준(서로 다른 컴포넌트 2개 이상에서 쓰이면 토큰) — 아래는 전부 **1곳**이다.

## 8. 사용자 확인이 필요한 사항

1. **칩 X 버튼의 `aria-label` `거절된 계정 지우기`** — PRD에 없어 신설한 문구다(§6.6 지시).

2. **카드 내부 하이라이트 `0.85` 유지** (§5-2). design 12a는 `0.8`이다.

   제목과 겹친다. `AppShell`에 배너 슬롯을 넣을지 그때 결정해야 한다. **지금 막고 있는 것은 없다.**
4. **W-03C §7의 미회신 4건** (§0). 원문을 재수록했다.
5. **번들 950kB(gzip 287kB).** W-16 그대로. 이번 회차에 한 일은 없다.

## 9. W-07(S2 · S2-1)에 넘길 전제

### 이미 있는 것

- **라우팅·가드·전환 모션은 전부 있다.** `/signup`은 `noProfile`·`withdrawn`, `/pending`은
  `pending`·`rejected`만 들어온다(`RequireAuth`의 `allow`). **화면 안에서 `navigate()`로
  인증 흐름을 만들지 마라** — `status`가 바뀌면 라우터가 옮긴다.
- `BrandLogo` · `.brand-title` · `.brand-sub` · `Footer variant="compact"` · `OfflineBanner` ·
  `useOnline` · `useToast`가 그대로 쓸 수 있다.
- S2-1은 Footer 축약형 화면이다(§6.4). `onNavigate={(path) => navigate(path)}`를 **직접 넘겨야 한다** —
  W-06은 S1분만 연결했다.
- 재가입 안내 배너(EC-39 `이전에 탈퇴한 계정입니다…`)는 `status === 'withdrawn'`으로 갈린다.
- 거절 변형은 `/pending`에서 `status === 'rejected'` + `profile.rejectReason`으로 갈린다.

### 🔴 S2-1 승인 자동 감지에 필요한 것 — **이번에 만들지 않았다**

§6.1이 S2-1의 이탈 경로를 `승인 감지 → S3`으로 규정한다. 그런데 **`AuthProvider`는
`users/{uid}`를 `getDoc`으로 1회만 읽는다**(W-05 §6). 계약에 재조회 수단이 없다.

```ts
const { status, profile, parsed, rejectedEmail, errorCode,
        signIn, signOut, clearRejection } = useAuth()
//                                          ^ refresh()가 없다
```

W-07이 승인 감지를 붙이려면 아래 중 하나가 먼저 필요하다. **어느 쪽이든 `AuthProvider` 계약 변경이다.**

| 안 | 내용 | 비용 | 걸리는 것 |
| --- | --- | --- | --- |
| A | `refresh(): Promise<void>` 추가 — 현재 사용자로 `resolve()`를 다시 돌린다 | 작다. `resolve`가 이미 분리돼 있다 | **W-05 §9 캐시 폴백**(→ W-17)이 그대로 남는다. 승인됐는데 캐시가 `pending`을 들고 있으면 감지에 실패한다 |
| B | `onSnapshot` 구독으로 전환 | 크다. R-06 실시간 반영이 덤으로 온다 | **W-12 범위다.** 지금 하면 W-12가 빈다 |
| C | S2-1 화면이 직접 `getDoc`을 호출 | 화면에 인증 판정 로직이 생긴다 | `AuthProvider`가 판정을 독점한다는 W-04 계약이 깨진다 |

**이번에 만들지 않았다**(지시서 §10-7 지시). W-07 지시서에서 A·B·C 중 하나를 지정해 주기 바란다.
지정이 없으면 W-07은 "수동 새로고침 버튼"으로 축소하거나 착수 자체가 막힌다.

### 주의

- **`rejectedEmail`을 건드리지 마라.** S1의 T-05·T-06이 이 값에 달려 있다.
- **화면 안에 `position: absolute`를 쓸 때 기준을 확인하라.** `blurIn` 래퍼의 `filter`가
  남아 있어 스테이지가 아니라 래퍼가 컨테이닝 블록이 된다(W-05 §4-4).
- **가입 흐름은 `inviteCodes` 조회와 OP-01 배치 쓰기를 요구한다.** Firebase 콘솔은 아직
  **임시 규칙**이다(W-04 §9). 규칙 없이 쓰기를 붙이면 W-15에서 전부 다시 봐야 한다.
- 오프라인 배너를 S2·S2-1에 붙일지는 §5-3의 겹침 판단과 함께 본다. 두 화면 모두 중앙 정렬이라
  S1과 같은 조건이다.
