#### 🔴 P9 — `includeMetadataChanges`가 **필수**다 (SDK 소스 실측)

`@firebase/firestore` `QueryListener`를 읽었다. 두 함수가 §3.2를 결정한다.

```js
shouldRaiseInitialEvent(snap, onlineState) {
  if (!snap.fromCache) return true                       // 서버 동기화된 첫 이벤트는 항상
  if (!this.listensToRemoteStore()) return true
  const maybeOnline = onlineState !== 'Offline'
  if (this.options.waitForSyncWhenOnline && maybeOnline) return false
  return (!snap.docs.isEmpty() || snap.hasCachedResults || onlineState === 'Offline')
}
shouldRaiseEvent(snap) {
  if (snap.docChanges.length > 0) return true
  const hasPendingWritesChanged = this.snap && this.snap.hasPendingWrites !== snap.hasPendingWrites
  if (snap.syncStateChanged || hasPendingWritesChanged) return this.options.includeMetadataChanges === true
  return false
}
```

- `waitForSyncWhenOnline: true`는 **`getDocs`/`getDoc` 전용**이다(`index.node.mjs`의 `executeQueryFrom*` 2곳).
  `onSnapshot`의 기본 옵션은 `{ includeMetadataChanges: false, source: 'default' }`이고 `waitForSyncWhenOnline`은 **없다**.
- 🔴 그래서 기본값으로 두면 **캐시 스냅샷 이후 서버가 같은 문서를 확인해도 콜백이 오지 않는다**
  (`docChanges` 0건 + `syncStateChanged`는 `includeMetadataChanges === true`일 때만 통과).
  = `fromCache: true → false` 전환을 앱이 **영원히 관측하지 못하고**, §3.2의 동기화 칩이 「동기화 지연」에 머문다.
- → `subscribeRecords`가 `{ includeMetadataChanges: true }`를 **명시한다.**
  ⚠ 서버 왕복이 필요한 관측(실제 `fromCache` 플립)은 접속 0 제약 때문에 **실 SDK로 재현하지 못했다** — 소스 인용이 근거다.
  스텁 하네스는 이 순서를 그대로 흉내 내 §3.2의 4상태를 전부 재현했다(§2 DoD 27).

#### P2-b가 바꾼 설계 — EM-02의 전제

**오프라인·빈 캐시에서 13ms 만에 `size: 0`이 떨어진다.** 그것을 「기록이 없다」로 읽으면
W-10 §5-3이 막으려던 **「오늘 0건」이라는 거짓말**과 같은 종류가 된다(§8.7.2가 실패를 ER-02, 빈 상태를 EM-02로
**따로** 규정하는 이유와 같은 정신이다).

→ **EM-02는 `fromCache === false` 스냅샷을 한 번이라도 받았거나 캐시에 행이 있을 때만 띄운다.**
그 전까지는 5행 스켈레톤이 유지되고, **왜 기다리는지는 동기화 칩이 말한다**(`오프라인` / `동기화 지연`).
§8.7.5의 오프라인 행(「배너 + 캐시 목록」)은 캐시가 **비었을 때**를 규정하지 않으므로 이탈이 아니다 → §7 신규 4번.

## 4. 판단과 이탈

### 4-1. 🔴 `includeMetadataChanges: true`는 선택이 아니라 요구다

§1-3 P9 전문. 지시서 §3.2의 「지연 = 온라인인데 `fromCache === true`가 계속됨」은
기본 옵션에서 **관측 자체가 불가능**하다. 이 한 줄이 없으면 칩이 영원히 `동기화 지연`에 머문다.

## 8. 다음 회차(S9 선도 일정 / S8 관리)에 넘길 전제

### 8-1. 🔴 실시간 구독 패턴을 다른 화면이 재사용할 때의 규칙

§3.7의 6개 규칙은 **S7 전용이 아니라 이 앱의 구독 계약이다.** 그대로 따르라.

1. **구독은 첫 페이지 1개.** 과거 페이지는 `getDocs` 정적 배열이다.
2. **병합은 문서 ID 기준 `Map` 합집합.** 🔴 `docChanges()`의 `removed`로 지우지 마라 —
   `limit` 창 밖으로 밀려난 문서도 `removed`로 오기 때문에, 지우면 고정 커서와 함께 **구멍**이 생긴다.
   그 대가로 **`status: 'deleted'`로 바뀐 문서가 목록에 남는다** — v1.1 삭제 회차가 소유할 지점이다(§8-4).
3. **커서는 첫 페이지의 마지막 문서에 고정.** 스냅샷마다 갱신하지 마라.
4. 🔴 **`{ includeMetadataChanges: true }`를 붙여라.** 없으면 `fromCache` 전환이 콜백으로 오지 않는다(§4-1).
5. 🔴 **언마운트에서 반드시 해제.** 독 이동은 `replace`라 화면이 언마운트된다.
   구독 2개가 동시에 살면 **둘 다 콜백을 받는다**(§1-3 P5 실측).
6. 🔴 **캐시만으로 비어 있는 결과를 「없음」으로 읽지 마라**(§1-3 P2-b · §4-5).
   `stats.ts`/`roster.ts`/`records.ts`가 공유하는 「실패 ≠ 0건」 규칙의 구독판이다.
7. **W-07 §9의 부채는 아직 남아 있다** — S2-1의 `refresh()` 폴링 루프. 이제 `onSnapshot`이 앱에 들어왔으므로
   그 부채를 갚을 수 있는 상태가 됐다. **다만 W-13은 손대지 않았다**(범위 밖).

### 8-2. `IntersectionObserver` root 확보 방법의 재사용성

`useContext(ScrollRootContext)` **한 줄이면 된다**(§4-2). `AppShell`을 고칠 필요도, DOM을 거슬러 오를 필요도 없다.
