## 1. 사전 조사 (지시서 §2 4건 + 사용자 추가 1건)

### 1.1 design `12d`의 밀어내기 구조 — 그리고 **채택본은 `12d`가 아니라 `10b`다**

`design/index.html`을 2단계 이스케이프 해제(`reports/W-02.md` §5 방법)해 원문을 꺼냈다.
배너 배경 `rgba(20,53,38,0.88)`이 나오는 프레임은 **2개**다.

| 프레임 | §20.7 대조표 | 컨테이너 | 배너 | 콘텐츠 래퍼 |
| --- | --- | --- | --- | --- |
| `12d S1-login 오프라인` | S1 채택본 `12a`~`12e` 중 하나 | `padding: 54px 0 0` · flex column | `margin: 0 18px` · `height: 40px` · `flex: none` | `flex: 1` · `padding: 0 22px` (세로 중앙) |
| **`10b 오프라인 배너`** | **`스플래시·배너·토스트 = 10a~10f` — 배너의 채택본** | `padding-top: 74px` · flex column | **완전히 동일** | `padding: 22px 22px 0` (상단 정렬) |

**두 프레임의 배너 자체는 한 값도 다르지 않다** — `margin: 0 18px` · `height: 40` · `radius 14` ·
`rgba(20,53,38,0.88)` · `blur(12px)` · `padding: 0 16px` · `gap: 8` · svg `14` · `12px/700` · 문구 동일.
구현이 두 프레임 **모두**와 일치한다.

#### 🔴 `54px`의 분해 — **분해되지 않는다. 그리고 그것이 결론이다**

| 확인 | 결과 |
| --- | --- |
| 다른 프레임의 상단 값 | `12a`·`12b`·`12c`·`12e`·`13a` 전부 **`padding: 88px 22px 0`** (파일 전체에서 `padding:88px` **61회**) |
| 88 − 54 | **34** — 목업에서 배너는 콘텐츠 시작선보다 34px 위에서 시작한다 |
| 상태 표시줄 몫 `S` 역산 | 앱 확정값 26px(§7.5)을 대입하면 `88 = S + 26` → `S = 62`. 그러면 12d의 배너 오프셋이 `54 − 62 = ` **−8px**(음수) |
| 🔴 두 배너 프레임의 불일치 | **`12d`는 `54px`, `10b`는 `74px`** — **같은 컴포넌트인데 20px 다르다** |
| `IOSDevice` 프레임 원본 | 외부 컴포넌트 참조(`f5cedef8-…#/ios-frame.jsx`)라 번들에 없다. 상태 표시줄 높이를 직접 읽을 수 없다 |

**컨테이너 `padding-top`은 프레임마다 눈대중으로 잡힌 값이라 이식 대상이 아니다.**
W-06 §5-3의 판단(`54px`은 목업 상태 표시줄을 포함해 `env(safe-area-inset-top)` 기준으로
옮길 수 없다)이 옳았고, 이번에 **두 프레임이 서로 어긋난다는 근거가 하나 더 붙었다.**

→ 상단 오프셋 **`16px`은 그대로 유지**한다. 독의 `bottom: calc(env(safe-area-inset-bottom) + 16px)`
+ 좌우 `18px`을 위아래로 뒤집은 **거울상**이다(§6.2 확정값의 재사용이지 신규 창작이 아니다).

#### 🔴 배너 하단 ↔ 콘텐츠 간격 — **design에서 유도되지 않는다.** §3.2 규칙을 썼다

`10b`에는 그 값이 **있다**: 콘텐츠 래퍼 `padding: 22px 22px 0` → 간격 **22px**.
그런데 그 값을 쓰지 않았다. 근거 3가지다.

1. **§20.7이 그 부분을 명시적으로 근거에서 제외한다.**
   `| 스플래시 · 배너 · 토스트 | 10a~10f | 배경 목록이 구버전이나 주제는 배너·토스트다.`
   **`배경을 근거로 쓰지 않는다`** — `padding: 22px 22px 0`은 배너가 아니라 그 아래
   **본문(배경) 래퍼**의 선언이다. 10b의 본문은 구버전 「최근 기록」 화면이다.
2. **두 프레임이 배너 위치부터 어긋난다**(54 vs 74). 자기 일관성이 없는 출처는 유도의 근거가 아니다.
3. **22px을 쓰면 세 개의 확정 요구와 동시에 충돌한다** — §3.2 1·2행(배너 세로 `56` · 콘텐츠 시작
   `기존 + 56`), DoD 6(`정확히 56px`), DoD 11(`safe-area + 26 + 56`). 그리고 배너 유무로
   화면 패딩이 26→22로 흔들려 §7.5 명시값이 깨진다(§0.4 순서 1 — PRD 우선).

→ **§3.2 규칙 채택**: 기존 상단 패딩(`26px` / 독 `34px`)을 그대로 유지한다. 새 간격 값 0개.

> **10b는 §0.2 결정을 더 강하게 뒷받침한다.** 12d는 세로 중앙 정렬이라 밀어내기와 오버레이의
> 차이가 거의 보이지 않는 화면이다. **10b는 상단 정렬 화면(독 있음)인데 배너가 흐름 안에서
> 본문을 밀어낸다** — 채택본 자체가 밀어내기다. 지시서 §0.2가 옳았고 근거가 하나 늘었다.

### 1.4 배너와 딤의 z 관계 (변경 전 실측) — **검증법이 틀렸다는 것을 여기서 발견했다**

| 요소 | position | z-index | 부모 |
| --- | --- | --- | --- |
| `.dim` | absolute | **40** | `.ovl-root` |
| `.ofb` | absolute | **70** | `.ovl-root` |

같은 부모라 z 비교는 성립하고 배너가 위다. **그런데 `elementFromPoint(배너 중앙)`은 `dim dim-open`을 반환한다.**
`.ofb`가 `pointer-events: none`이라 히트테스트에서 제외되기 때문이다 —
**페인트 순서와 히트테스트 결과가 다르다.** DoD 9가 지정한 검증법은 현행에서도 이미 실패한다(§3-2).

## 3. 판단이 필요했던 지점

### 3-1. 🔴 스플래시가 배너를 덮지 못하게 된다 — **멈추고 물었다**

§1.5의 조사 결과가 **둘로 갈렸다.**

- 스택 컨텍스트는 **공유한다** → `z 100 > 70` 비교는 성립한다. (사용자가 지정한 중단 조건은 성립하지 않았다)
- 그러나 밀어내기로 스크롤 영역이 56px 줄면 `.splash`도 함께 줄어 **겹칠 기하가 사라진다.**
  실측: `splash.y = 56` · 배너 `16 ~ 56` → `geometricOverlap: false`.

DoD 15(`배너가 스플래시에 가려진다`)와 DoD 6(`정확히 56px`)이 **스플래시에서만** 성립하지 않는다.
선택지 2개와 되돌리기 비용을 붙여 물었고 **안 1(수용 + DoD 개정)** 을 회신받았다.

| | 안 1 (채택) | 안 2 (기각) |
| --- | --- | --- |
| 방법 | 그대로 둔다 | 스테이지에 `--ofb-block: 56px` + `.splash { top: calc(0px - var(--ofb-block,0px)) }` |
| 스플래시 첫 요소 | `368 → 396` (**Δ 28**) | Δ 0 |
| 배너 | 판정 중에 **보인다** | 가려진다(현행과 동일) |
| 코드 | **0줄** | 2줄(새 메커니즘) |

**왜 안 1이 손실이 아닌가**: 지시서 §4 Splash 행이 적은 근거가 그대로 이쪽을 지지한다 —
「판정 중에는 화면 자체가 없으므로 가릴 콘텐츠도 없다」. 가려지는 것이 없고, 3초 뒤
`네트워크에 연결할 수 없습니다`로 끝날 수 있는 대기에서 오프라인을 미리 알리는 것은 **정보 이득**이다.
배너를 조건부로 끄는 코드도 넣지 않았다(§4 지시 준수).

**Δ가 스플래시만 28인 이유**: `.splash`는 스크롤 영역 기준 `absolute; inset: 0`이라 상자가 56px
줄면 세로 중앙이 절반(28px)만 내려간다. 나머지 5화면의 `main`은 흐름 안이라 상자째 56px 내려간다
(`main`의 `min-h-full`은 부모 `.blur-in`의 높이가 auto라 애초에 발동하지 않는다 — 기존 성질이고 이번에 건드리지 않았다).

### 3-2. 🔴 DoD 9의 `elementFromPoint` 검증법이 **현행에서도 이미 실패한다** — 물었다

§1.4에서 발견했다. `.ofb`가 `pointer-events: none`이라 히트테스트에서 제외되고,
`elementFromPoint(배너 중앙)`은 배너가 아니라 **딤**을 반환한다. 페인트 순서와 무관한 결과다.

배너를 흐름으로 옮기면 `.ovl-root`의 상속이 끊겨 기본값 `auto`가 되므로,
**DoD 9는 문자 그대로 통과하지만 대신 시트가 열린 동안 배너 띠(상단 40px)에서
딤 탭-투-클로즈가 죽는다.** 선택지를 붙여 물었고 **`pointer-events: none` 유지**를 회신받았다.

- `.ofb`에 `pointer-events: none` **선언 1줄**을 넣어 계산값을 보존했다. 값을 새로 만든 것이
  아니라 상속으로 얻던 것을 명시로 옮긴 것이다(§0.3 「배너의 시각·거동 규격 불변」에 맞는다).
- **DoD 9는 두 가지로 다시 증명했다**(§4.4). `pointer-events`는 페인트에 영향이 없으므로
  프로브에서만 `auto`로 바꿔 페인트 순서를 읽었고, 딤의 z를 40/80으로 갈라 차등 픽셀을 찍었다.

### 3-3. 1차 픽셀 검증이 틀렸다 — 방법을 갈아치웠다

처음에는 「딤 유무로 배너 픽셀이 변하지 않으면 가려지지 않은 것」으로 판정하려 했다.
**틀렸다.** `.ofb`는 `backdrop-filter: blur(12px)` + 알파 `0.88`이라 **뒤에 깔린** 딤도 픽셀을 바꾼다.
`bannerPixelUnchanged: false`가 나왔고, 이것을 「딤이 배너를 덮었다」로 읽었다면 오판이었다.
§4.4의 차등 방식으로 교체했다. **투명하거나 backdrop-filter가 걸린 요소에는 픽셀 동일성 판정을 쓰지 마라.**

### 3-4. `z-index: 70`이 `position: static`에서도 듣는 이유

`.ofb`는 이제 `position: static`이다. 보통 `z-index`는 무시되지만 **flex 항목은 예외다**
(CSS Flexbox §5.4 — flex 항목의 `z-index`는 `position`과 무관하게 적용되고 스택 컨텍스트를 만든다).
실측으로 확인했다: computed `position: static` · `z-index: 70`이고 페인트 스택에서 딤보다 위다.
**스테이지를 flex 컬럼에서 되돌리면 이 관계가 조용히 깨진다.** CSS 주석에 남겼다.

### 3-5. S1에서 `<OfflineBanner />` 호출을 지웠다

배너가 전역 1개가 됐으므로 화면이 다시 그리면 `.ofb`가 2개가 된다.
`useOnline()` 자체는 S1에 그대로 뒀다 — 버튼 `opacity 0.45`와 안내 줄 교체가 계속 쓴다(§4.1).
**셋은 함께 쓰는 것이 맞다**(DoD 13·14로 증명). 지시서 §4.1 준수.

### 3-6. 스크롤 영역을 `h-full` → `flex-1 min-h-0`으로 바꿨다

flex 컬럼에서 `h-full`(100%)은 스테이지 전체 높이를 잡아 배너만큼 넘친다.
`min-h-0`이 없으면 flex 항목의 자동 최소 크기 때문에 콘텐츠가 길 때 축소되지 않는다.
**배너가 없을 때의 결과 높이는 902px로 이전과 같다**(실측 §4.1의 `scroll` 값).
