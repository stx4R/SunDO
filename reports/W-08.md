## 1. 사전 조사 4건 (지시서 §2)

### 1.1 design S2 프레임 — **R-02 적용본이다**

`data-screen-label` 속성으로 식별했다. 내용 추정이 아니다.

| ID | 라벨 | R-02 적용 여부 |
| --- | --- | --- |
| `13a` | `S2-signup 기본` — A 기본 · 코드 비어 있음 | ✅ 입력이 **가입 코드 1개뿐** |
| `13b` | `S2-signup 입력 중` — B 포커스 | ✅ |
| `13c` | `S2-signup 검증 성공` — C | ✅ |
| `13d` | `S2-signup 검증 실패` — D | ✅ |
| `13e` | `S2-signup 제출 중` — E | ✅ |
| `20d` | `S2-signup-fallback 이름 파싱 실패` — F | ✅ 이름 입력 1개 **추가** |
| `20e` | `S2-signup-fallback 재가입` — G 안내 배너 | ✅ |

- 프레임 그룹 제목이 **`S2-signup · 가입 코드 단일 입력 5변형`**이다. v1의 5개 입력(이름·이메일·
  비밀번호·비밀번호 확인·코드)은 **어느 프레임에도 없다.** 미적용본은 존재하지 않는다.
- **재가입 배너(EC-39)는 `20e`에 그려져 있다.** §6.2의 배치를 §4 골격에서 유도할 필요가 없었다 —
  원문값(`mt 24px` · `radius 12` · `padding 11px 13px` · `gap 8` · `rgba(31,81,56,0.08)` ·
  아이콘 14px · 텍스트 `12px/500 lh 1.45 #1F5138`)을 그대로 썼고, 배너가 붙으면 **신원 카드의
  상단 여백이 24px → 12px로 줄어드는 것**까지 `20e` 원문이다.
- `20d`·`20e`가 `13a`~`13e`보다 **나중 그룹**이지만 같은 변형의 재판본이 아니라 **F·G 추가 변형**이다.
  A~E와 충돌하는 값이 없어 "최신본 채택" 규약이 발동하지 않았다.

### 1.2 🔴 `Field`가 캐럿 위치를 지킬 수 있는가 — **통로가 없었다**

| 확인 항목 | 조사 결과 |
| --- | --- |
| `onChange`가 넘기는 것 | **값(`string`)이다.** `onChange={(e) => handleChange(e.target.value)}` — 이벤트도 `input` 요소도 화면에 도달하지 않는다 |
| `FieldHandle`(ref)이 노출하는 것 | **`validate()` · `focus()` 2개뿐.** `setSelectionRange`를 부를 통로가 없다 |
| 값이 외부에서 바뀔 때 캐럿 처리 | **아무 처리도 없다.** 제어 컴포넌트라 브라우저가 캐럿을 문자열 끝으로 민다 |

→ 지시서 §2.2의 「통로가 **없다**」 분기다. **`Field`를 확장했다**(prop 1개 + 핸들 1개). 근거는 §5-2.

### 1.3 진입 3상태의 실제 값

`AuthProvider`를 스텁 위에서 실제로 돌려 확인했다(부록).

| 상태 | `profile` | `parsed` | 이름 출처 | 이메일 출처 |
| --- | --- | --- | --- | --- |
| `noProfile` | **`null`** (문서 없음 → `setProfile(null)`) | `ParseResult` | `parsed.name`, 실패 시 **직접 입력** | **`auth.currentUser.email`** |
| `withdrawn` | `UserProfile` 전체 | `ParseResult` | **`profile.name`** | `profile.email` |
| `rejected` | `UserProfile` 전체 | `ParseResult` | **`profile.name`** | `profile.email` |

- **`parsed`는 세 상태 모두 존재한다.** `resolve()`가 `users` 조회보다 **먼저** `setParsed()`를 부르기
  때문이다(`AuthProvider.tsx` — 도메인 검증 직후). 문서가 없어도 파싱 결과는 있다.
- 세 상태가 같은 코드 경로를 탄다. 값의 출처가 갈리는 지점은 **`profile?.x ?? authUser?.x`** 한 줄뿐이고
  화면이 상태로 분기하지 않는다.
- `uid`도 같다 — `profile?.uid ?? authUser?.uid`. `noProfile`에서는 후자만 존재한다.

## 5. 판단이 필요했던 지점

### 5-1. 🔴 제출 버튼 활성 조건 — **"검증 성공"이 아니라 "9자 완성"으로 했다**

| 출처 | 규정 |
| --- | --- |
| PRD §8.2.2 #9 · 지시서 §4.2 | 비활성 = **`코드 미입력` 시** `opacity 0.45` |
| 지시서 §6.1 | A(비어 있음) `0.45` · B(입력 중) **여전히 `0.45`** · C(검증 성공) **버튼 활성** |
| design `13b` | 7자 입력 상태에서 `opacity 0.45` + `pointer-events: none` |
| design `13d` | **검증 실패(9자) 상태에서 버튼이 활성**(`cursor:pointer` + `:active scale`) |

세 자료를 동시에 만족하는 규칙은 **"9자를 다 채웠는가"** 하나뿐이다. `13b`(7자)는 비활성,
`13d`(9자·실패)는 활성, `13a`(0자)는 비활성 — 전부 맞는다.

**"검증 성공일 때만 활성" 규칙은 막다른 길을 만든다.** 사용자가 코드를 다 치고 곧바로
`가입 신청`을 누르는 것이 가장 흔한 동선인데, 그 시점에는 아직 blur가 일어나지 않아 검증이
없다. 버튼이 비활성이면 **탭이 버튼에 닿지 않아 blur도 일어나지 않는다** — 화면이 영영
반응하지 않는다. 형식이 틀린 9자(`1234-5678`)도 같은 이유로 활성으로 두고, 탭하면 blur →
`코드 형식이 올바르지 않습니다`가 뜨게 했다.

제출은 어차피 **서버에서 다시 판정한다**(§5.2 EC-07). 클라이언트 버튼은 "보낼 수 있는 모양인가"만
본다. **되돌리려면 조건 1개**(`code.length === 9` → `verifiedRef.current === code`)이지만,
그러면 design `13d`와 어긋나고 위 막다른 길이 생긴다.

### 5-2. ⚠️ `Field` 확장 2건 — 지시서 §2.2가 허용한 범위 안이다

| 확장 | 내용 | 이유 |
| --- | --- | --- |
| **prop `transform?`** | `(raw, caret) => { value, caret }`. `Field`가 결과를 `onChange`로 올리고 **캐럿을 직접 복원**한다 | §1.2 — 화면이 `input` 요소에 닿을 방법이 없다. 값 변형이 필요한 입력은 앞으로도 나온다(S6 기타 사유 · S9 검색) |
| **`FieldHandle.reset()`** | 성공·실패 표시를 지우고 검증 이전 상태로 되돌린다. 값은 건드리지 않는다 | 🔴 **조회 실패(ER-01)를 그릴 방법이 없었다.** blur가 켜 둔 성공 체크를 그대로 두면 "확인됨"이라는 **거짓말**이 되고, 에러로 그리면 정상 코드에 실패 딱지가 붙는다. `validate`는 `string \| null` 2값이라 "판정 없음"을 표현하지 못한다 |

**prop 증가는 1개다**(지시서의 중단 기준은 "prop 2개 초과"). `reset()`은 prop이 아니라 기존 핸들에
붙은 3번째 메서드이고, `validate()`·`focus()`와 같은 성격이다.

구현에서 주의한 것 2가지:
- 캐럿 복원은 `useLayoutEffect`다. `useEffect`면 브라우저가 한 번 그린 뒤에 커서가 움직여 **깜빡인다.**
- **의존성 배열이 없다.** 변형 결과가 직전 값과 같으면(9자 초과 입력) React가 리렌더를 건너뛸 수 있고,
  그때 DOM에는 버려진 원문이 남는다. 효과 안의 `if (el.value !== value) el.value = value`가 유일한
  복구 경로다. 실측으로 확인했다(`DJSN-2691`에서 `5` 입력 → 값 그대로, 캐럿 9).

**`Field`를 쓰는 화면은 아직 S2뿐이라 회귀 표면이 없다.** `transform`을 주지 않으면 기존 경로와
바이트 단위로 같다(`caretRef`가 `null`이라 효과가 즉시 반환한다).

### 5-3. 검증 중에 성공 테두리가 먼저 켜진다 — **고치지 않았다**

`Field`의 성공 상태는 **blur에서 켜진다**(W-03A §4-2 · W-03B §1 확정). 서버 조회는 그 뒤에 시작되므로,
조회 대기 중에는 `ff-ok`(초록 1.5px 링 + `settleY 0.2s`)가 이미 켜져 있다. **체크 아이콘은 보이지
않는다** — `checking`이 우선이라 스피너로 가려진다(실측: `endIcon: ff-spin` `16px`).

PRD §7.3의 「Validation — 검사 중」은 **`테두리는 포커스 상태 유지`**를 요구한다. blur된 필드에
포커스 링을 다시 그릴 수는 없고, `ff-ok`의 초록 1.5px는 포커스 테두리와 **같은 색·같은 굵기**다
(다른 것은 바깥 3px 글로우뿐). 즉 지금 상태가 규격에 가장 가깝다.

대안은 `checking`일 때 `ff-ok`를 끄는 것인데, 그러면 테두리가 **기본(흰색 1px)** 으로 떨어져
규격에서 더 멀어진다. 남는 부작용은 `settleY`가 0.2s 일찍 재생되는 것 하나다. **W-18 후보로 올린다.**

### 5-4. 이름 폴백은 **입력 카드 바깥**에 뒀다

지시서 §4.2 표는 이름 입력을 「입력 카드」 행에 넣었지만, 같은 지시서 §5.3과 PRD §8.2.3은
**`신원 카드 아래에 이름 입력 필드 1개`**라 적고 design `20d`도 신원 카드와 입력 카드 **사이**에
그린다. 2:1로 갈려 다수를 따랐다 — 실측 순서는 `헤더 → 신원 카드 → ER-14 → 이름 필드 → 입력 카드`다.

### 5-5. 이름 폴백은 **확정된 이름이 없을 때만** 연다

`parsed` 실패만으로 열면, 이름이 이미 확정된 재신청·재가입 계정(`profile.name`이 있다)에서도 입력이
열려 **본인이 이름을 바꿀 수 있게 된다.** §8.2.3은 `파싱 실패 계정의 이후 변경 — 본인은 변경할 수 없다.
부장·Dev만 관리 화면에서 수정한다`고 명시한다. 그래서 조건을 `파싱 실패 **且** 저장된 이름 없음`으로 했다.

같은 이유로 **재활성 배치는 `name`·`nameSource`·`displayNameRaw`를 쓰지 않는다.** 규칙 요청서의
허용 목록에는 남겨 두되(§0.2 결정 2 조건 6) 코드가 쓰지 않는다 — `manual` 계정의 이름을 파싱값이
덮는 사고(DR-13)를 구조적으로 막는다.

### 5-6. ⚠️ 오프라인 처리를 넣었다 — 지시서에 없고 PRD에 있다

지시서 §4·§6은 오프라인을 다루지 않지만 **PRD §8.2.5에 행이 있다**(`버튼 비활성 + 힌트
'오프라인 상태에서는 가입할 수 없습니다'`). 충돌 해소 순서 1번(PRD 명시 · design 침묵)을 적용했다.

**넣지 않았을 때의 실제 피해가 크다.** Firestore는 오프라인 지속성이 켜져 있어(`persistentLocalCache`)
`batch.commit()`이 **서버 응답을 받을 때까지 resolve되지 않는다.** 오프라인에서 제출하면 변형 E의
스피너가 **영원히 돈다** — 취소할 방법도 없다. 힌트 교체 대상은 §8.2.2에 「힌트」가 코드 힌트 1개뿐이라
그 줄을 바꿨다(S1의 힌트 교체와 같은 방식). 실측: 힌트 `오프라인 상태에서는 가입할 수 없습니다`,
버튼 `disabled` + `opacity 0.45`.

### 5-7. 오프라인 **배너**는 S2에 붙이지 않았다 — 겹침 재판단을 유예한다

W-06 §5-3이 남긴 🟡 항목("독이 있는 화면에서 제목과 겹치면 W-08에서 재판단")의 답이다.

`.ofb`는 `top: calc(safe-area + 16px)`이고 S2의 뒤로 버튼·제목은 `safe-area + 26px`에서 시작한다.
**S2는 겹치는 첫 화면이다.** 겹침을 없애려면 `AppShell`에 배너 슬롯을 만들어 콘텐츠를 밀어내야 하는데,
그것은 전 화면의 상단 여백 계약을 바꾸는 일이라 이번 지시서 범위 밖이다. 대신 §5-6의 **힌트 + 버튼
비활성**으로 오프라인을 알리므로 정보가 사라지지는 않는다.

**독이 있는 화면(S3 이후)에서 다시 마주친다.** `AppShell` 슬롯 신설과 함께 판단해야 한다.

### 5-8. `.s2-banner`를 새로 만들었다 — `.s1-banner`를 재사용하지 않았다

지시서 §4 #9는 「S1의 `.s1-banner`와 **같은 형태**」라 적었다. 선언 5줄이 같지만 클래스를 공유하지
않았다. `.s1-banner`는 S1에서 **2줄(items-start) / 1줄(items-center)** 두 형태로 갈려 있고, S1이
그 갈래를 조정하면 S2가 함께 움직인다. 화면별 클래스 규약(`.s1-*` · `.pend-*`)에도 맞다.
**공유되는 것은 색 하나이고, 그것은 이번에 토큰으로 승격했다**(§9).

### 5-9. design과 갈린 5칸

| # | 항목 | 판단 |

### 5-10. 하이라이트 `0.85` vs design `0.8` — W-07 §5-1과 같은 건이다

신원·입력 카드는 `GlassCard`(`.glass`)를 쓰고, 뒤로 버튼은 `--highlight-top`을 참조한다. 둘 다
`rgba(255,255,255,0.85)`이고 design `13a`는 `0.8`이다. W-04 §2에서 `--highlight-top`을 design `20c`
원문(0.85)으로 확정했고 `.glass`·`.dock`·`.pend-badge`가 공유한다. **한 화면 때문에 되돌리면
공유 토큰이 갈라진다.** W-06·W-07과 같은 판단을 유지했다.

### 5-11. ⚠️ 지시서 밖의 수정 1건 — `PrimaryButton`에 `aria-disabled` 1줄

지시서 §8이 「제출 버튼 — 진행 중 `aria-disabled="true"`」를 요구하는데 `PrimaryButton`은
`disabled`·`aria-busy`만 붙이고 있었다. prop이 열려 있지 않아 화면에서 줄 방법이 없다.

`aria-disabled={disabled || loading || undefined}` — **W-07 §5-7이 `NeuButton`에 넣은 줄과 같다.**
네이티브 상태를 반영할 뿐이라 부작용이 없고, 이번 회차에 §0.1-3으로 승인된 조치와 동일하다.
S2-1의 `가입 코드 다시 입력` 버튼(같은 컴포넌트)에도 함께 적용되지만 시각 변화는 0이다(실측 §4.9).

### 5-12. T-04의 순서 — 클라이언트 검증을 서버 조회 **앞**에 뒀다

지시서 §7 T-04는 `① 코드 재조회 → ② 배치 → ③ refresh`다. 구현은 `① 형식·이름 검증 → ② 재조회 →
③ 배치 → ④ refresh`다. 이름이 비어 있는데도 서버를 한 번 다녀오는 것이 낭비이고, 그 조회는
**어차피 버려진다.** 지시서가 말하는 「코드 재검증」의 자리는 그대로다(배치 직전). DoD 16의
`getDoc` 2회는 정상 경로에서 그대로 성립한다(실측 확인).

### 5-13. 변형 E에서 `Field`의 `submitting` prop을 쓰지 않았다

`.ff-sub`는 `opacity 0.6`을 준다. 카드가 이미 `0.6`이라 함께 쓰면 필드만 **0.36**으로 겹쳐 어두워진다
(design `13e`는 카드 전체가 균일한 `0.6`이다). 카드 투명도만 쓰고 커서 정지는 `.s2-busy input {
caret-color: transparent }` 1줄로 냈다. 실측 `rgba(0,0,0,0)`.

### 5-14. 늦게 끝난 조회가 새 값을 덮지 않게 했다

blur → 조회 중에 사용자가 값을 고치면 옛 조회 결과가 뒤늦게 도착해 **바뀐 값에 판정을 붙인다.**
`lookupSeq` 카운터로 최신 요청만 반영한다(`AuthProvider`의 `seqRef`와 같은 방식). 값이 바뀌는
순간 `serverErrorRef`·`verifiedRef`를 **동기적으로** 비우는 것도 같은 이유다 — `Field`가 그 직후
재검사를 돌리므로 비동기로 비우면 옛 문구가 한 번 더 뜬다.

### 5-15. 토큰화하지 않고 리터럴로 남긴 값 (W-08 신규분)

| 값 | 사용처 | 이유 |
| --- | --- | --- |
| `0 6px 18px rgba(20,53,38,0.08)` | `.s2-back` 1곳 | W-03B §3 기준(컴포넌트 2개 이상) 미달 |
| `1px solid rgba(255,255,255,0.75)` | `.s2-back` 1곳 | 〃 (`--color-sundo-border-light`는 `0.7`이라 다른 값이다) |
| `letter-spacing: 0.1em` | `.s2-code input` 1곳 | 〃 |
| `rgba(255,255,255,0.35)`(E 스피너 트랙) | `.btnp-spin` 1곳(W-03B) | **트랙 = 회전부 색의 알파** 관계인데 이 스피너의 회전부는 흰색이다. `0.22`(밝은 배경) 대 `0.35`(진한 배경)는 값이 아니라 대비 조건이 다르다 — W-07 §1.4의 관계 규칙을 그대로 따르면 통일하면 안 된다 |

## 8. `already-exists`가 도달 불가인 근거 (지시서 §12-8)

§11.2 OP-01 실패 표의 마지막 행 — `already-exists / 이미 pending 신청 존재 / '이미 신청이 접수되었습니다'`.
**이 문구를 만들지 않았다.** 세 겹으로 도달할 수 없다.

| # | 근거 |
| --- | --- |
| 1 | **`users.status`와 `approvalRequests.status`는 같은 배치에서 함께 쓰인다.** `writeBatch`는 원자적이라 "신청은 있는데 사용자 상태는 아직 아님"이라는 중간 상태가 존재하지 않는다 |
| 2 | **`pending` 계정은 S2에 도달하지 못한다.** `/signup`의 `allow`는 `noProfile`·`withdrawn`·`rejected` 3개뿐이고 `pending`의 착지는 `/pending`이다. **실측**: `status='pending'`으로 `/signup` 직접 진입 → `/pending`(S2-1)로 리다이렉트(§4.10) |
| 3 | **거절된 신청은 `pending`이 아니다.** 부장이 거절하면 `approvalRequests.status='rejected'` + `users.status='rejected'`가 된다. 이 상태의 재신청은 **BR-28이 명시적으로 허용**하므로 막으면 오히려 규격 위반이다 |
| 4 | 문서 ID가 `{uid}_{ms}`라 Firestore 차원의 ID 충돌도 일어나지 않는다(`setDoc`은 덮어쓰기이며 밀리초가 다르다) |

즉 이 실패 코드가 발생하려면 **라우터 가드가 뚫리거나 배치의 원자성이 깨져야 한다.** 둘 다
이 코드가 다룰 상황이 아니다. **§6-13으로 PRD에서 삭제할 것을 제안한다.**
