#### 1-3-1. W-10의 세 질의 — **복합 인덱스가 필요 없다**

🔴 **`count=0`은 「실패해서 0」이 아니다.** `failed-precondition`은 데이터가 0건이어도 던져진다(§1-1).
세 질의가 값을 돌려줬다는 것은 **집계가 실제로 수행됐다**는 뜻이다.
§2.3이 세운 「등식뿐이라 단일 필드 인덱스로 충분하다」는 판단이 실측으로 확인됐다.

#### 1-3-2. 그래도 §9.5를 고치지 않았다 — 근거가 뒤 3행에 있다

**`orderBy`가 붙는 순간 갈린다.** W11-1·W11-2는 등식 조건이 3~4개인데 **다른 필드로 정렬**하자
둘 다 `failed-precondition`이 났다. §1-3의 「없어도 된다」는 **지금 S3가 쏘는 모양에 한정된 사실**이고,
W-13(S7 기록 조회)이 정렬·범위 조건을 붙이면 IX-03·IX-04가 곧바로 필요해진다.
`database_ToDo/W-10.md` §1-3이 예고한 그대로다.

**W11-1과 W11-2가 서로 다른 인덱스라는 것**도 이 실행에서 드러났다 —
`isActive`를 서버 질의에 넣느냐가 인덱스 하나를 가른다. W-11 §2.2의 A/B 선택이 이 값으로 결정된다.

#### 1-3-3. 🔴 `public/__w10probe.js`는 고장 나 있었다 — W-11이 삭제한다

W-10이 브라우저에서 쏘려고 남긴 프로브는 **`projectId` 자리에 웹 API 키(`AIza…`)를 넣었다.**
존재하지 않는 프로젝트 경로로 질의가 나갔고 세 줄이 전부
`Permission denied on resource project AIza…`로 죽었다.
**규칙 거부가 아니다** — 규칙 거부는 `Missing or insufficient permissions`다.
당시 이 출력을 「미인증이라 임시 규칙이 먼저 막았다」로 읽은 것은 **오독이었다.**

`public/`에 두면 번들에 섞여 배포된다. **W-11 DoD 31이 삭제를 잠근다.**

### 1-4. §2.4 `records`에 `academicYear`를 넣을지 — **넣지 않았다**

| 근거 | 내용 |
| --- | --- |
| 1 | `dateKey`(`YYYY-MM-DD`)·`weekKey`(`YYYY-Www`)는 **특정 일자·주차를 가리키므로 학년도가 이미 결정된다.** 같은 `dateKey`가 두 학년도에 속할 수 없다 |
| 2 | IX-03(`status, dateKey`)·IX-04(`status, weekKey`)에 **`academicYear`가 없다.** 조건을 하나 더 붙이면 설계된 인덱스와 어긋난다 |
| 3 | 조건이 늘면 §2.3의 「등식뿐이라 복합 인덱스가 불필요할 수 있다」는 판단 자체가 바뀐다 |

**대신 §12.1 ST-05의 문언 보완을 §5 PRD 반영 목록에 올렸다.** ST-05가 「모든 카운터는 현재
`academicYear` 범위 내로 한정한다」라고만 적혀 있어, 문자 그대로 읽으면 필터를 붙여야 하는 것처럼 보인다.
실제로 필요한 문언은 「`dateKey`·`weekKey`로 한정되는 카운터는 학년도가 이미 결정되므로 별도 필터를 붙이지 않는다」다.

`students` 카운트에는 **`academicYear`를 붙였다** — 이쪽은 학년도가 조건에서 결정되지 않고
부서 문서의 `academicYear`(2026)를 그대로 쓴다(§5.3 · IX-09).

### 4-1. `dateKeys.ts` — ISO 주차 경계를 정면으로 다뤘다 (DoD 20)

`getUTCFullYear()`를 그대로 쓰면 연말·연초가 틀린다. ISO-8601은 **「그 주의 목요일이 속한 해」**가
주차연도이므로 12월 29~31일이 다음 해 `W01`이 되고, 1월 1~3일이 전년 `W52`/`W53`이 된다.
목요일로 이동 → 그 해 1월 4일이 속한 주의 목요일과의 간격 ÷ 7 + 1로 계산했다.

### 4-2. 🔴 로딩 스켈레톤을 `6d`에서 다시 가져왔다

착수 시점 코드의 `.s3-skel`은 `border-radius: pill` · `background: tint-10`으로 **지어낸 값**이었다.
§20.7이 「로딩 스켈레톤 = `6a`~`6d`」를 **채택**으로 적고 있고 `6d`가 홈 스켈레톤이므로,
§0.4 순서 2(PRD가 침묵하고 design에 값이 있으면 design)에 따라 원문으로 교체했다.

| 무엇을 | 어디서 | 왜 |
| --- | --- | --- |
| 폭 40 · 높이 22 · 반경 8 · 3정지점 그라디언트 | **`6d` 원문** | §8.3.5는 「폭 40px」만 규정하고 높이·반경·배경에 침묵한다 |
| 카드 패딩 `14px 16px` · 반경 `18` | **`1d` + §7.3** | `6d`는 `16px 18px`/`20`이지만 §7.3 반경 스케일이 stat = **18**로 못 박는다(순서 1) |
| 인사말 자리 스켈레톤 높이 `1em` | **유도** | `6d`에 인사말이 없다. 13px 줄에서 줄 높이가 흔들리지 않는 값이다(실측: 삽입 전후 `.s3-hello` 높이 `19.5` 불변) |

**같은 3정지점 그라디언트가 `6a`~`6d` 전부에 쓰인다.** 지금은 사용처가 S3 하나뿐이라 W-03B의
토큰화 기준(서로 다른 컴포넌트 2개 이상)에 못 미쳐 `.s3-skel`에 뒀다.
**W-11(S5 학생 목록 스켈레톤 `6a`)이 두 번째 사용처를 만들면 공용 `.skel`로 승격해야 한다.**

### 4-3. design `1d`를 따르지 않은 3칸

**a. 제목 굵기 `800` → `700`.** PRD §7.2 타입 스케일이 **H1 = 28px / 700 / -0.01em**으로 명시한다(§0.4 순서 1).
`6d`의 홈 제목도 `font-weight:700`이라 신판본과도 일치한다. `1d`의 800이 舊 값이다.

**b. 유리 처리 `blur(16px)` · `0 8px 24px/0.08` → `.glass` 토큰(`blur(18px)` · `0 8px 26px/0.09`).**
W-02가 §7.1 토큰으로 이미 이식해 둔 값이고 저장소의 모든 유리 표면이 이것을 쓴다.
`1d`만 따로 두면 **같은 화면 안에서 독(`.dock`)과 통계 카드의 유리가 갈린다.**
`6d`가 `blur(18px)` · `0 8px 26px/0.09`를 쓰는 것이 결정적이다 — **신판본이 §7.1 토큰 쪽이다.**

**c. 눌림 `scale(0.985)` → `scale(0.98)`.** PRD §8.3.2 #5가 「인셋 + `scale(0.98)`」로 명시한다(순서 1).
`.neu:active`가 이미 그 값이고 W-04 이후 모든 뉴모피즘 표면이 공유한다.

### 4-4. ⚠ 인사말 스켈레톤은 도달하지 않는다 — 코드는 남겼다

§8.3.5 로딩 행은 「인사말은 이름 자리 스켈레톤」을 규정하고 `Home.tsx`가 그 분기를 갖고 있다
(`profile ? … : <span className="s3-skel" />`). **그런데 실행되지 않는다.**

`AuthProvider`가 `setProfile(next)`와 `setStatus(next.status)`를 같은 커밋에서 세우고,
`RequireAuth`는 `status === 'active'`일 때만 S3를 렌더한다. 즉 **S3가 마운트되는 순간 `profile`은 항상 있다.**
`refresh()`도 `silent: true`라 실패해도 `profile`을 비우지 않는다(W-07 §3.2 규칙 3).

실측에서도 `delayMs 900`으로 조회를 늦춘 3시점(1300·1500·1700ms) 전부
`.s3-hello` = `안녕하세요, 유이준님`이고 `.s3-hello .s3-skel`은 없었다.

**분기를 지우지 않았다.** 지우면 `profile`이 `null`이 될 수 있는 미래(예: W-17의 캐시 폴백 정정,
또는 스플래시 없이 S3를 직접 그리는 변경)에 이름 자리가 `undefined`로 샌다.
스켈레톤 CSS 자체는 검증했다 — 같은 클래스를 인사말에 주입하면 `40 × 13px`이고 줄 높이가 흔들리지 않는다.
**§8.3.5 로딩 행의 인사말 항목이 현재 라우터 계약에서 관측 불가능하다는 사실을 §5 PRD 목록에 올렸다.**

### 4-5. T-05가 부서 문서와 명부 카운트까지 다시 읽는다

§8.3.4 T-05의 문언은 「통계 **재조회**」다. `load(true)`는 통계 2건 + 부서 1건 + 명부 3건을 전부 다시 읽는다
(실측: `getCountFromServer` 5→10, `getDoc` 2→3).

**그렇게 둔 이유**: 학년 버튼의 활성/비활성이 `students` 카운트에서 나오는데(§8.3.2 #5),
통계만 갱신하면 「명부를 방금 넣었는데 당겨도 버튼이 계속 회색」이 된다.
ER-08 문구가 `당겨서 새로고침`이라 사용자는 **화면 전체가 최신이 됐다고 읽는다** — 통계만 갱신하면
UI가 사실과 어긋난다(§0.4 예외 1). 부서 문서는 `classCountByGrade`(부제)를 준다.

**비용은 진입 1회분과 같은 6회 읽기다.** T-05는 사용자가 명시적으로 당겼을 때만 돈다.
T-02(탭 재진입)는 여전히 **네트워크 0건**이다(DoD 11).

### 4-6. `sparkle`을 컴포넌트가 아니라 명령형 함수로 만들었다

T-03은 sparkle과 라우팅을 **같은 프레임**에 건다(§2.2에서 design이 그렇게 한다고 확인).
React 컴포넌트가 화면 소유라면 `navigate()` 직후 S3가 언마운트되면서 포털도 함께 사라져
**0.5s 애니메이션이 첫 프레임에서 끊긴다.**

명령형으로 `.ovl-root`에 직접 붙이면 소유자가 없어 전환을 가로질러 살아남고 550ms 뒤 스스로 지운다.
실측: 이동 380ms 뒤 `.spark` 1개(살아 있음) · 900ms 뒤 0개.

design은 `position: fixed` + `document.body` + `z-index: 9999`를 쓰지만 **`.ovl-root`(스테이지 기준
`absolute`)로 옮겼다.** `fixed`로 두면 430px보다 넓은 화면에서 스테이지를 벗어난다(W-03B §4-9와 같은 이유).

`prefers-reduced-motion: reduce`에서는 **아예 만들지 않는다.** CSS로 `animation: none`만 걸면
`from{opacity:1}`이 적용되지 않아 막대 7개가 550ms 동안 그대로 떠 있는다.
CSS 쪽에도 `.spark i { animation: none; opacity: 0 }`을 이중 잠금으로 남겼다.

### 4-7. `usePullToRefresh`가 `preventDefault`를 부르지 않는다 — 리스너 전부 `passive`

§8.3.4 T-05의 애니메이션 열이 `—`이고 §7.4에 당김 인디케이터가 없다.
**따라올 시각 요소가 없으므로 기본 동작을 막을 이유가 없다.**
그래서 `touchstart`/`touchmove`/`touchend`/`touchcancel`을 전부 `{ passive: true }`로 붙였다.

결과적으로 **iOS Safari 바운스와 충돌할 지점이 없다**(지시서 §4.4가 「충돌하면 멈추고 물어라」로
지목한 항목이다 — 충돌이 발생하지 않아 묻지 않았다). 임계값에 못 미친 제스처는 평범한 오버스크롤로 끝난다.

🔴 **임계값 `70px`은 design·PRD 어디에도 없는 신규 값이다.** 시각 피드백이 없어 사용자가 당김의
진행도를 볼 수 없으므로, 우연한 오버스크롤과 의도적인 당김을 가르되 과하지 않은 값으로 잡았다.
**§5 PRD 목록에 「당김 인디케이터 + 임계값」을 시안 요청 후보로 올렸다.**

### 4-8. 🟡 `getDoc`·집계 질의의 캐시 폴백 — **알고 있고, 이번에 고치지 않았다**

W-05 §9 · W-17 항목의 위험이 `stats.ts`에도 그대로 있다. 서버 조회가 실패하면 SDK가 로컬 캐시로
떨어질 수 있어 「실패」가 「성공(옛 값)」으로 보일 수 있다.

**이번 회차에서 고치지 않는다** — 그 폴백이 곧 §8.3.5 오프라인 행의 「마지막 캐시값」이다.
지금은 오히려 규격이 요구하는 동작이다. W-17이 `getDoc` 경로를 정리할 때 같이 봐야 한다.

### 4-9. 세션 캐시를 모듈 수준에 뒀다

§12.3이 「화면 진입 시 1회 조회 후 세션 내 재사용」을 규정하는데, S3는 탭을 옮길 때마다

재진입마다 재조회가 돌아 T-02(「재조회하지 않는다」)를 위반한다.
그래서 `stats.ts` 모듈 수준에 `statsCache`·`deptCache`·`rosterCache`를 뒀다.
**실패는 캐시하지 않는다** — 다음 진입에서 다시 시도해야 한다.

### 4-10. `NeuButton`의 `onClick` 시그니처를 넓혔다

`1-(1-p)³` 대비 최대 오차가 **214(17.3 %)**로 나왔다. 페이지가 완전히 정지한 뒤 T-05로 다시 돌려
재측정하니 **최대 오차 1(0.081 %)**이 됐다. 곡선이 틀린 것이 아니라 **콜드 로드 프레임이 튄 것**이다.
또한 `t0`은 「첫 `0` 표본」이 아니라 **마지막 `0` 표본**을 써야 한다 — 재조회가 즉시 끝나면
스켈레톤 프레임이 한 장도 그려지지 않아 `null`을 기준으로 자를 수 없다.

## 8. W-11 (S4 반 선택 · S5 학생 목록)에 넘길 전제

### 8-1. `classCountByGrade` 읽기 계약 — **재사용할 수 있다. 다시 읽지 마라**

`fetchDepartment()`는 **모듈 수준 캐시(`deptCache`)를 갖는다.** S3에서 이미 읽었으므로
S4가 `fetchDepartment()`를 그대로 부르면 **네트워크로 가지 않는다**(force 없이).

```ts
const dept = await fetchDepartment()
if (dept.kind === 'ok') {
  const lastClass = dept.classCountByGrade[String(grade)]   // 🔴 문자열 키다
}
```

🔴 **맵 키는 문자열이다.** `classCountByGrade[grade]`(숫자)로 읽으면 `undefined`가 되고
부제·반 목록이 조용히 빈다. W-09 §7-3이 지적한 그 함정이다.

⚠ **S4를 URL로 직접 열면(`/grade/2` 새로고침) 캐시가 없다.** 그때는 실제 조회가 돌고
`{ ok | failed }`가 그대로 온다 — S4도 `failed`를 `0`이나 빈 목록으로 읽으면 안 된다.

### 8-2. `maxNumberPerClass = 37`이 S5에서 쓰이는 지점

**S3는 이 값을 읽지 않는다**(지시서 §5.2 지시대로 `fetchDepartment`가 반환하지도 않는다).
S5가 쓰는 곳은 **학생 번호 상한**이다 — DR-03 `number ∈ [1, maxNumberPerClass]`.
`src/lib/studentNo.ts:47`에 그 규칙이 주석으로 이미 적혀 있다.

**S5가 쓰려면 `fetchDepartment`의 반환 타입에 `maxNumberPerClass`를 더해야 한다.**
지금은 `academicYear`와 `classCountByGrade`만 돌려준다 — 지시서 §5.2가 「S5가 쓴다 — 이번 회차에서
읽지 마라」로 못 박아서 일부러 뺐다. **필드를 더하는 것이지 새 조회를 만드는 것이 아니다.**

### 8-3. N-04 파라미터 검증은 **`router.tsx`에 이미 있다 — 다시 만들지 마라**

| 무엇 | 위치 | 무엇을 하나 |

`/grade/1/class/99`로 직접 들어오는 경로는 S5가 막아야 한다.**
