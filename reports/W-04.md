## 5. 판단이 필요했던 지점

### 4-1. `.env.local` 채택과 `.gitignore` 확인 (지시서 §1·§2)

PM이 `.env` 대신 `.env.local`에 6개 값을 채웠다. **그대로 쓴다.** `src/lib/firebase.ts`는
`import.meta.env`를 읽으므로 파일명과 무관하고, Vite는 `.env.local`을 전 모드에서 `.env`보다
우선해 읽는다. W-19에서 배포용 환경 변수를 다룰 때 이 구성이 전제가 된다.

`.env.example`이 **이름 변경으로 사라져 있었다.** 디스크에 파일이 없으면 커밋도 없고 DoD 3이
조용히 깨진다. 원본을 복구하고 콘솔 지시서 6단계에 "복사해서 쓰되 원본을 지우거나 이름을 바꾸지 마라"를 넣었다.

`.gitignore`는 **손대지 않았다.** 이미 순서가 맞다.

```
5: .env
6: .env.*
7: !.env.example      ← 부정 패턴이 .env.* 뒤에 있다
```

실측: `git check-ignore .env.example` → 무출력(exit 1, 무시 안 됨) · `git check-ignore .env.local` →
`.env.local`(exit 0, 무시됨) · `git status`에 `?? .env.example`. **DoD 26·3 동시 충족.**

> `git check-ignore -v`는 부정 패턴에 걸린 파일도 매칭 줄을 출력하므로(`!.env.example`) exit code나
> 무출력 여부로 읽어야 한다. `-v` 출력만 보고 "무시된다"고 읽으면 반대로 판단하게 된다.

### 4-2. 거절 상태가 로그아웃에 덮이고 있었다 (결함 수정, 지시서 §3.1)

지시서가 짚은 그대로였고, 실제로는 **한 겹 더 나빴다.**

`deleteUser` → `signOut` 순서로 가면 `signOut`이 `onAuthStateChanged(null)`을 발화시킨다.
그 콜백은 새 시퀀스 번호를 받으므로, 거절 경로가 `stale()` 가드에 걸려 **`setStatus('domainRejected')`와
`setRejectedEmail()`이 아예 실행되지 않는다.** 덮이는 게 아니라 처음부터 기록되지 않는다.
화면에는 아무 일도 없었던 것처럼 `signedOut`만 남는다 — S1의 거절 배너·거절 계정 칩(T-05)·
`다른 계정으로 로그인` 라벨 교체가 전부 죽는다.

→ 거절을 **인증 상태에서 파생시키지 않는다.** `rejectionRef` 래치를 `deleteUser` 호출 **전에** 세우고,
`resolve(null)`이 래치를 보면 `signedOut` 대신 `domainRejected`를 유지하게 했다.
래치는 `clearRejection()`(T-06)과 **정상 도메인 로그인 성공** 두 경우에만 풀린다.

PM 실측으로 확인: 개인 계정 로그인 → `domainRejected` + `rejectedEmail` 유지 →
`거절 지우기` → `signedOut` + `rejectedEmail -`.

### 4-3. 조회 실패를 `noProfile`로 뭉개지 않는다 (지시서 §3.2, DoD 28)

`users/{uid}` 읽기는 **두 가지 다른 사건**이다.

| 사건 | 판정 | 근거 |
| --- | --- | --- |
| 문서가 없다 (`exists() === false`) | `noProfile` | 최초 로그인 — S2로 보낸다 |
| 읽지 못했다 (`permission-denied`·네트워크·규칙 미게시) | **`loading` + `errorCode`** | 판정을 확정할 수 없다 |

둘을 같게 다루면 오프라인이나 규칙 오류일 때 **활성 부원이 가입 신청 화면으로 튕긴다.**
`status`를 새로 만들지 않고 `loading`에 머무르게 한 이유는 그것이 사실이기 때문이다 —
분기가 확정되지 않았다. 이유는 `errorCode`가 들고 있다.

> **W-06 전제**: `status === 'loading'`이 3초 이상 지속되면 `errorCode`를 근거로 오류 화면을 띄워야
> 한다(§8.1.5 "로딩 최대 3초"). 이 타임아웃은 W-06 몫이며, 지금은 스플래시가 유지된다.

**검증 경위** — 규칙을 `if false`로 막는 재현은 **두 번 다 실패**했다(일반 창·시크릿 창 모두
`noProfile`). 규칙 전파 지연인지 캐시 응답인지 브라우저 밖에서는 가를 수 없어,
**결함 주입**으로 분기 자체를 실측했다: `getDoc` 자리에서 `permission-denied` 코드를 단 에러를
던지게 한 임시 빌드를 PM이 열어 상태판을 확인했다.

```
status        loading
errorCode     permission-denied
parsed        ok 20723 유이준
profile       -
```

`noProfile`이 아니라 `loading` + 코드가 나왔다 — **분기는 성립한다.**
주입 코드(`TEMP-W04-FAULT`)는 측정 직후 제거했고 재빌드로 부재를 확인했다
(W-03A·W-03B의 임시 계측과 같은 방식).

### 4-4. `deleteUser` → `signOut` 순서와 실패 대비 (§5.3)

T-05 문언은 `signOut() + deleteUser()`지만 지시서 §5.3이 **`deleteUser` 먼저**로 못박았고 그게 맞다 —
로그아웃하면 자격 증명이 사라져 자기 계정을 지울 권한이 없어진다. 실패해도 `signOut`은 반드시 하도록
`try/catch`를 나눠 뒀다. **이번 검증에서 `auth/requires-recent-login`은 나오지 않았다**(§6).

### 4-5. 팝업 실패 코드를 로그로 남긴다

폴백이 조용히 일어나면 W-19에서 리다이렉트가 막혔을 때 출발점이 없다.
`console.warn('[auth] 팝업 실패 — 리다이렉트로 폴백한다:', code)` 한 줄을 넣었고,
이 줄 덕분에 이번 실측에서 폴백 원인이 `auth/popup-blocked`임을 코드 수준으로 확정할 수 있었다.

### 4-6. 스토리 페이지에 `AUTH` 상태판을 붙였다

화면이 아니라 **상태 표시판**이다. DoD 14~19·27·28은 실 로그인이 필요한데 자격 증명은 PM만 가지고
있어, 상태와 전이 로그를 그대로 찍어 회신할 수 있는 표면이 필요했다.
버튼 3개(`Google 로그인`·`로그아웃`·`거절 지우기`)는 `AuthContextValue`의 함수를 그대로 부른다.
W-05 라우팅에서 `src/App.tsx`는 통째로 대체된다.

### 4-7. 파싱 실패 시 기존 이름을 지우지 않는다 (DR-12 경계)

`nameSource='parsed'` 계정의 표시 이름이 파싱 불가능한 값으로 바뀌면, `displayNameRaw`만 갱신하고
`name`·`memberStudentNo` 계열은 **건드리지 않는다.** 학교가 표시 이름을 임시로 잘못 바꾼 경우
멀쩡한 이름을 지워 버리면 복구할 방법이 없다. 이름 재입력은 W-06 S2가 다룬다.

### 4-8. 번들이 커졌다

`firebase`가 들어오면서 JS 청크가 500 kB 경고선을 넘었다. 코드 분할은 이번 범위가 아니고
(라우터가 없어 자연스러운 분할 지점이 없다) W-05 라우팅 이후 W-16·W-19에서 다룰 문제다.

## 6. `deleteUser` 실패 경로

**만나지 않았다.** 도메인 거절은 로그인 직후에 판정되므로 `auth/requires-recent-login` 조건이
성립하지 않는다(회신 §3의 예상과 일치). 그래도 코드는 실패를 전제로 짜여 있다.

| 단계 | 처리 |
| --- | --- |
| `deleteUser` 실패 | `console.warn` + `errorCode`에 코드 보존. **거절 판정은 그대로 진행** |
| `signOut` | 삭제 성공·실패와 무관하게 **항상 실행** |
| `signOut`까지 실패 | 다음 `onAuthStateChanged`가 다시 판정한다. 래치가 살아 있어 거절 상태는 유지된다 |

실패가 실제로 나면 **Auth에 계정이 남는다.** 그때는 콘솔에서 수동 삭제가 필요하고,
빈도가 잦아지면 W-15 이후 서버측 정리(블로킹 함수)로 옮겨야 한다.

## 7. 사용자 확인이 필요한 사항

1. **`status === 'loading'` 3초 타임아웃은 W-06이 붙여야 한다**(§4-3). 조회 실패가 영구적이면
   지금은 스플래시가 계속 유지된다. W-06 S1 작업 지시서에 §8.1.5 로딩 3초 규칙을 명시해 달라.
2. **번들 크기**(§4-8). 코드 분할 시점을 W-16으로 볼지 W-19로 볼지 정해 두면 그때 논쟁이 없다.
3. **거절 계정 삭제 실패 시 잔여 계정 처리**(§6). 지금은 콘솔 수동 삭제다. 운영 중 발생 빈도를
   보고 서버측 정리로 옮길지 W-15 이후에 판단하면 된다.
4. PRD v1.3 반영 대기 항목 — DR-10 `[MVP 유보]` 표시, §9.6 요약표 보정(§8·§9). **PM이 한다.**

## 9. W-05(라우팅 + 역할 가드)에 넘길 전제

### 🔴 W-15 주의 — §9.6 요약표 ≠ 부록 B 전문

**자기 갱신 허용 키는 부록 B가 정본이다.** §9.6 요약표만 보고 Rules를 쓰면 **DR-12 동기화가 막힌다.**

- `docs/SunDO_PRD.md:2866` — 부록 B의 `users.update` 허용 키에
  `'name','memberStudentNo','memberGrade','memberClassNo','memberNumber','updatedAt'`가 **이미 들어 있다**(확인함).
- `docs/SunDO_PRD.md:2915` — 그 이유를 적은 주석이 있다: DR-12 자동 갱신 때문이며,
  임의 이름 삽입 위험은 부원 목록·감사 로그 노출로 상쇄된다. 프로파일 B 전환 시 `beforeSignIn`
  블로킹 함수로 서버가 대신 갱신하도록 옮긴다.
- §9.6 요약표는 이 키들을 빠뜨렸다. **요약과 전문이 다르면 전문이 정본이다.** 보정은 PM이 v1.3에서 한다.

### `AuthProvider` 계약

```ts
const { status, profile, parsed, rejectedEmail, errorCode,
        signIn, signOut, clearRejection } = useAuth()
```

- **`AuthProvider`는 화면을 그리지도, 이동하지도 않는다.** 라우팅은 W-05가 `status`를 보고 한다.
- **문구가 없다.** 에러 **코드**만 노출한다. ER-11~ER-14 · TS-17(`로그인이 취소되었습니다`)은 S1이 붙인다.
  취소는 에러가 아니다 — `auth/popup-closed-by-user`가 `errorCode`로 온다.
- `status`가 `loading`인 동안 화면을 그리지 마라(N-05). **`errorCode`가 함께 있으면 판정 실패다** — 3초 뒤 오류 화면.
- `rejectedEmail`은 `clearRejection()`까지 살아 있다(§4-2). T-05 배너·칩·버튼 라벨이 이 값에 달려 있다.
- `AuthProvider`는 **`AppShell` 안쪽**에 둘 필요는 없지만, `ToastProvider`는 오버레이 루트가 필요해
  `AppShell` 안이어야 한다. **둘 다 라우트 루트에 1개씩**만 둔다(W-03C §7-5).

### 그 밖

- `src/App.tsx`는 스토리 페이지다. W-05가 라우터로 대체하면서 `AUTH` 절도 사라진다.
- 환경 변수는 `.env.local`에 있다(커밋 안 됨). 새 개발 환경은 `.env.example`을 복사해 채운다.
- Firebase 콘솔은 `sundo-dev` **임시 규칙** 상태다 — **실제 학생 명부를 넣지 마라.**
  역할·상태 검증이 없다. 시드는 W-15 이후다.
