🔬 **추론하지 않고 저장소 원본 규칙을 에뮬레이터에 그대로 싣고 §3.2가 지시한 질의를 돌렸다.**

| --- | --- |

| `pending` | 🔴 **거부** |

| `rejected`(재신청) | 🔴 **거부** |

⇒ **BR-30 코드가 통째로 무동작이 되고, 「레이트 리밋을 붙였다」는 문장만 남는다.**

⚠ **단건 `get`은 허용된다**(A-6). 그러나 문서 ID가 `{uid}_{Date.now()}`(§11.1 멱등성)라
**나중에 알아낼 수 없다** — 열거가 불가능하다.

**세 갈래를 PM에게 올렸고 ①이 선택됐다.**

| 안 | 대가 |

## 3. 🔴 규칙 변경 — 1줄

### 3.1 무엇을 열었나

```
- allow list: if isVice() || isTeacher();
+ allow list: if isVice() || isTeacher()
+   || (isSignedIn() && resource.data.uid == request.auth.uid);
```

🔴 **넓히는 방향이다.** 옛 앱은 이 질의를 만들지 않으므로 **규칙을 앱보다 먼저 배포해도
깨지는 화면이 없다**(W-21B §1.1의 판정 기준 — 「틀렸을 때 무엇이 깨지느냐」).
⇒ 배포가 **2단계**로 끝난다(W-22A는 좁히기가 있어 3단계였다).

⚠ **PRD §9.6 요약표는 `approvalRequests` read를 「본인 또는 `vice` 이상」으로 규정한다.**
🔴 **이 변경은 조항에서 멀어진 것이 아니라 오히려 가까워진 것이다** — 옛 규칙은 `get`에서만
「본인」을 지키고 `list`에서는 지키지 못했다.

### 3.2 🔬 규칙 주석 하나가 틀렸다

옛 주석: 「「본인」 절이 `resource.data`를 보므로 `list`에서 **증명할 수 없다**」.

🔬 **틀렸다.** Firestore는 `list`를 **결과 문서마다** 평가하고, 질의가 규칙과 어긋나면
**통째로 거부한다**(「rules are not filters」의 정확한 뜻이다). 규칙을 고치지 않고
패치본을 에뮬레이터에 실어 먼저 확인했다.

| 시도 | 결과 |
| --- | --- |
| 본인 uid 등식 질의 | ✅ **허용**(3건) |
| 🔴 `where` 없는 전체 목록 | ✅ **거부** |
| 🔴 남의 uid로 질의 | ✅ **거부** |

⇒ **경계가 양방향으로 확인된 뒤에** 규칙을 고쳤다. 주석도 함께 고쳤다.

### 5.2 판별 유니온 — `ok(n) | unknown`

```ts
export type SignupAttemptCount =
  | { kind: 'ok'; count: number }
  | { kind: 'unknown'; errorCode: string }

export function isSignupBlocked(attempts: SignupAttemptCount): boolean {
  return attempts.kind === 'ok' && attempts.count >= SIGNUP_ATTEMPT_LIMIT
}
```
🔴 **`unknown`을 `0`이나 `3`과 뭉개지 않았다**(`CodeLookup`·`DuplicateVerdict` 선례).
**판정 지점이 `isSignupBlocked` 하나뿐**이라 「실패는 통과」 계약이 한 곳에서만 산다.

### 5.3 세는 시점 — 진입 1회 + 제출 직전 1회 (§3.4)

- **진입** — `useEffect([uid, online])` · 🔴 **`countedUidRef`로 uid당 1회로 못 박았다.**
  React StrictMode는 개발에서 이펙트를 두 번 실행하므로 **그대로 두면 질의가 2회로 보인다.**
- **제출 직전** — `handleSubmit` 안, 코드 조회(①)보다 **앞**.
- 🔴 **오프라인에서는 진입 카운트를 하지 않는다** — S2는 이미 오프라인 제출을 막고 있고
  (W-08 §5-7), 캐시만 보고 「3회 미만」이라 답하면 **그 값이 거짓일 수 있다.** 새 분기를 만들지 않았다.

### 5.4 🔬 `serverTimestamp()`가 아직 확정되지 않은 문서

방금 쓴 본인 문서는 로컬 캐시에서 `createdAt`이 `undefined`다.

빼면 자기 최근 신청을 놓쳐 **한도가 한 칸 헐거워진다.**

### 5.5 화면 — 「비활성」이지 「부재」가 아니다

`disabled = !codeFilled || !online || rateLimited` · 버튼은 `disabled={disabled}`로 **남아 있다.**
🔴 **W-15A §4-4의 「읽기 전용 = 버튼 부재」와 반대인 이유** — 거기는 **권한이 없어 영원히
못 하는 것**이고 여기는 **지금만 못 하는 것**이다. 문구가 그 이유를 말한다.

E-1009는 동의 안내와 **같은 표면**(`Field`의 `.ff-msgwrap`/`.ff-msg`)을 쓴다 — **새 표면을 만들지 않았다.**

## 9. 🔬 측정 함정

### ① 🔴 승계 — node가 Chrome을 spawn하면 조용히 죽는다 (W-18 · W-22A §9 ③)

### ② 🔴 **신규 — 내 측정 두 개가 틀렸고, 결과가 아니라 측정을 고쳤다**

첫 실행에서 이렇게 나왔다.

| 시나리오 | 첫 결과 | 왜 무효였나 |
| --- | --- | --- |
| DoD 8(예외 주입) | 「앱이 뜬다 · 경고 1건」 | 🔴 **사이트 키가 없어 `initializeAppCheck`가 아예 불리지 않았다.** 주입한 예외가 닿을 코드가 실행되지 않았고, 찍힌 경고는 **「키 없음」 경고**였다 — **다른 사실이다** |
| DoD 9(오프라인 첫 실행) | 「앱이 안 뜬다」 | 🔴 **서비스 워커가 설치되기 전에 오프라인으로 열었다.** Chrome의 공룡 페이지가 떴고 그것은 **앱의 결함이 아니라 측정의 오류**다 |

⇒ **8은 가짜 사이트 키를 넣은 번들로 다시 지었고, 9는 워커를 데운 뒤 오프라인 재적재로 바꿨다.**
🔴 **「앱이 안 뜬다」를 그대로 결함으로 적었으면 없는 회귀를 만들 뻔했다.**

⚠ 🔴 **그런데 9는 고친 뒤에도 성립하지 않았다** — 워커가 preview + 헤드리스에서

**그래서 9를 「측정됨」으로 적지 않는다.** 대신 **8b(reCAPTCHA·App Check 도메인 전면 차단)**가
EC-01의 실질(「App Check가 네트워크를 못 타도 앱이 서는가」)을 닫는다.
🔴 **진짜 오프라인 재적재는 배포본·실기기에서 재야 한다** — W-20도 「배포본에서」 쟀다.

### ③ ⚠ 신규 — `try`는 동기 구간만 잡는다

reCAPTCHA가 **키를 거부**하는 실패(HTTP 400)는 `initializeAppCheck` 호출 **뒤** SDK 내부에서
비동기로 일어난다. ⇒ `catch`가 잡지 못하고 `[SunDO]` 경고도 안 난다.
🔴 **「경고가 없으니 App Check가 잘 붙었다」로 읽으면 틀린다.** 붙었는지는
**콘솔 요청 지표**로만 확인된다(`database_ToDo/W-22B.md` §2.2-8).

### ④ ⚠ 신규 — 규칙을 고치면 `mutations.mjs`가 함께 죽는다

역검증 변형은 규칙의 **원문 조각**을 `from`으로 잡는다. 한 줄만 바뀌어도
「원본 조각을 못 찾음」으로 러너가 종료 코드 2로 죽는다.
🔴 **규칙을 고친 회차는 `mutations.mjs`를 같이 고쳐라.** 이번에 1건 갱신 + 2건 신설했다.

### ⑤ ⚠ 신규 — 선언한 `breaks`가 실측과 다를 수 있다

`approvals-list-open`이 A-10도 깨는데 선언에 없었다. **실행 결과를 보고 선언을 고쳤다.**
