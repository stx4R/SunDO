## 9. 🔬 측정 함정

### ① 🔴 **신규 — W-22A §2.1의 관문 명령이 이 저장소에서 항상 거짓 경보를 낸다**

지시서 §2.1이 준 명령:

```bash
git show HEAD:firestore.rules > /tmp/head.rules && diff firestore.rules /tmp/head.rules
```

**실행 결과 — `1,494c1,494`, 즉 494줄 전부 불일치.** 🔴 **규칙이 사라진 것처럼 보인다.**

🔬 **원인**: 이 저장소는 `core.autocrlf=true`다. 작업 트리의 `firestore.rules`는 **CRLF**,
`git show`가 뱉는 blob은 **LF**다. `diff`는 바이트를 보므로 **모든 줄이 다르다고 말한다.**

```bash
diff <(tr -d '\r' < firestore.rules) <(tr -d '\r' < /tmp/head.rules)   # → 완전 일치
git hash-object firestore.rules                                        # → HEAD blob과 동일
```

🔴 **이것이 왜 위험한가 — 이 관문은 W-21C 사고를 잡으라고 세운 그물이다.**
매번 빨갛게 뜨는 경보는 **무시하게 되고**, 무시하는 순간 그물이 없는 것과 같다.
「늑대다」를 494줄씩 외치는 관문은 진짜 늑대가 왔을 때 아무도 안 본다.

⇒ 🔴 **규약 4-3의 확인 수단을 `git diff --numstat`과 `git hash-object`로 바꿔야 한다.**
둘 다 **정규화된 blob**을 보므로 줄 끝 차이에 걸리지 않고, **내용이 진짜 달라졌을 때만** 반응한다.
🔴 **문자열 3건 `grep`은 그대로 유효하다** — 줄 끝과 무관하다.

### ② 🔴 **신규 — 「배포가 성공했다」는 세 개의 다른 사실로 쪼개진다**

W-21C §8 ①은 「명령의 성공은 파일 내용을 보증하지 않는다」를 남겼다. 이번에 재 보니 **층이 셋**이었다.

| 층 | 무엇을 보증하나 | 이번 회차 |
| --- | --- | --- |
| 1 | **배포 명령이 성공했다** | ✅ 3단계 전부 |
| 2 | **배포가 읽은 파일이 이번 변경을 담고 있다** | ✅ SHA 대조(규약 4-3) |
| 3 | 🔴 **게시된 결과물이 그 내용이다** | ⚠ **Hosting은 ✅**(URL에서 받아 확인) · 🔴 **Rules는 미확인** |

🔬 **Hosting은 3층까지 잴 수 있다** — 결과물이 공개 URL에 있어 그냥 받아 보면 된다.
🔴 **Firestore Rules는 못 잰다** — 게시된 규칙을 읽으려면 Rules REST API가 필요하고
그러려면 OAuth 토큰이 필요한데, 이 하네스에는 `gcloud`가 없고 firebase-tools의 자격 증명도
표준 configstore 경로에 없다. ⇒ **그래서 §3.4가 콘솔 육안 확인인 것이다.**

🔴 **다음 회차를 위해**: 규칙 3층을 자동으로 재려면 **서비스 계정 + Rules API**가 필요하고,
그것은 「서비스 계정 키 커밋 금지」와 충돌한다. **W-22B가 판단할 것**으로 넘긴다.

### ③ ⚠ **승계 — 이 하네스에서 node가 Chrome을 spawn하면 조용히 죽는다** (W-18)

W-18이 실측한 것(종료 코드 127 · 예외 0 · 샌드박스 무관)이 이번에도 유효했다.

### ④ ⚠ **신규 — 「캐시 이름이 다르다」는 「갱신된다」가 아니다**

스모크 16의 근거로 SW 캐시 이름(`sundo-shell-v0.16.0-afd174ac` vs 옛 `…v0.14.0-…`)을 확인했다.
