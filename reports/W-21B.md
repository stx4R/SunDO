**버전** `SunDO v0.15.0` · 선행 W-21(`v0.14.0` · `a9eb77e`)

> 🔴 **이 회차의 첫 산출은 「나누기로 한 결정」이다.**
> 지시서는 네 건(기능 3·4·9·12)을 한 회차에 담았고 §0.1이 「들어가지 않으면 코드를 더 쓰지

> 판단해 코드 0줄에서 멈추고 물었다. 사용자가 **2분할**을 골랐다.

> **W-21B**(이번 · `v0.15.0`) = 기능 **9** + **12** — 규칙 회차

## 4. 🔴 규칙 변경 전량

### 4.1 무엇을 넓혔나 — 기능 9

```
    function editsReasonOnly() {
      return request.resource.data.diff(resource.data).affectedKeys()
               .hasOnly(['reasonCode', 'reasonText', 'updatedBy', 'updatedAt'])
        && validReason(request.resource.data)
        && resource.data.status == 'active'
        && request.resource.data.updatedBy == request.auth.uid;
    }

    function softDeletesRecord() {
      return request.resource.data.diff(resource.data).affectedKeys()
               .hasOnly(['status', 'deletedBy', 'deletedAt'])
        && resource.data.status == 'active'
        && request.resource.data.status == 'deleted'
        && request.resource.data.deletedBy == request.auth.uid;
    }

    function canEditRecord() {
      return isActive()
        && (resource.data.createdBy == request.auth.uid || isVice());
    }
```

```
      allow update: if canEditRecord() && (editsReasonOnly() || softDeletesRecord());
      allow delete: if false;
```

🔴 **두 전이는 배타적이다.** 사유 변경은 `status`를 못 건드리고(RU-11), 삭제는
`reasonCode`를 못 건드린다(RX-8). 한 요청이 둘을 겸하면 **양쪽 `hasOnly`가 모두 깨져** 거부된다.

⚠ **넓히기만 한 것이 아니다** — 옛 규칙에서 `occurredAt`·`studentDocId`·`status`가 열려
있던 것을 `hasOnly`가 **닫았다**(§2.2 가). 넓힌 축과 좁힌 축이 한 블록 안에 있다.

### 4.3 🔴 지시서를 이긴 사실 — `inviteCodes update`를 통째로 좁힐 수 없다

§3.4는 「create/update → `isDev()`」다. **그대로 쓰면 부장의 가입 승인이 죽는다.**

🔬 근거 — `src/lib/admin.ts:383`의 승인 배치가 같은 규칙으로 `useCount`를 쓴다.

```js
batch.update(codeRef, { useCount: increment(1) })
```

규칙 테스트 **B-1**(「`head`의 승인 배치 4연산 통째로」)이 정확히 그 자리를 지키고 있었고,
배치는 **부분 성공이 없으므로**(Q-3) 한 연산이 걸리면 **승인 전체가 죽는다.**

⇒ **필드로 갈랐다.** 만료 처리(`isActive`·`revokedAt`)와 생성은 `dev`, **`useCount`만** `head`.
🔴 **C-10이 급소를 지킨다** — 부장이 `useCount`와 `isActive`를 **함께** 써서 승인 문으로
만료를 끼워 넣는 경로. `hasOnly(['useCount'])`가 그것을 막는다.

## 6. 판단과 이탈

### 6.1 🔴 `recordCount` 감소 — **하지 않는다**

W-16 §7이 「v1.1 삭제 회차에 규칙을 넓힌다」로 예약했다. **이 회차가 그 예약을 닫지 않는다.**

**소비자를 세었다** — `recordCount`를 **화면에 그리는 자리가 0곳**이다.

| 자리 | 무엇 |
| --- | --- |
| `AuthProvider.tsx:61` | 타입 필드로 들고만 있다 |
| `signup.ts:171` | 가입 시 `0` |
| `records.ts:358` | 저장 시 `increment(1)` |
| `policy.ts` ×2 | 개인정보 처리방침 **본문에서 이름만 언급** |
| `account.ts` | 탈퇴 시 보존해야 한다는 **주석** |
| 🔴 **화면 렌더** | **0곳** |

**넣지 않는 근거 4가지**

1. 🔴 **삭제자가 작성자가 아닐 수 있다.** 차장이 부원 기록을 지우면 감소 대상은
   `resource.data.createdBy`의 문서인데, 규칙의 자기 갱신 경로(`selfSync`)는 **본인 문서만**
   연다. 차장에게는 `isHead()` 경로도 없다. ⇒ **「남의 카운터를 바꾸는 새 문」을 열어야 한다.**
   🔬 **B-30이 그것을 실측으로 보여 준다** — 그 배치는 지금 통째로 거부된다.
2. 본인이 지워도 「+1만」에 걸려 −1이 거부된다(RC-3 · 🔬 B-31).
3. 감소를 열면 RC-2·RC-3·RC-6이 지키던 「임의 값 차단」이 약해진다. 특히 **`records` 삭제
   없이 단독으로 −1 하는 update를 막을 수 없다**(RC-5가 문서화한 성질 — 규칙은 형제
   연산을 못 본다). 즉 누구나 자기 카운트를 0으로 만들 수 있게 된다.
4. 삭제 배치가 2연산 → 3연산이 되어 「부분 성공 없음」의 표면이 넓어진다.

⇒ 🔴 **`recordCount`는 「작성 횟수」이지 「현재 유효 기록 수」가 아니다.** 그 의미를
§9.3.1에 명시해야 한다 — §8 ③.

### 6.2 🔴 되돌리기(`deleted → active`)를 열지 않았다

design `18`에도 §8.7에도 복구 UI가 없고, BR-08은 「삭제는 소프트 삭제」까지만 규정한다.
여는 순간 「지운 것을 아무 흔적 없이 되살리는」 경로가 생긴다.

⇒ **검증용 복구는 콘솔이 한다.** 절차는 `database_ToDo/W-21B.md` §5다(DoD 15의 근거).
🔴 그때도 **`auditLogs`의 `RECORD_DELETE` 로그는 지우지 않는다** — 감사 로그는 수정·삭제
전면 금지(§14.5 3번)이고, 「지웠다가 되돌렸다」가 남는 것이 옳다.

### 6.3 부장의 재발급 pill — `disabled`가 아니라 **부재**

비활성 버튼은 「지금은 안 되지만 언젠가 된다」를 뜻한다. 부장에게는 **영영 안 된다.**
W-15A §4-4의 「읽기 전용은 부재」와 같은 판단이다.
⚠ **강제 탭 방어는 남겼다** — `doReissue`가 `canIssue`를 실행 직전에 한 번 더 본다.

### 6.4 수정·삭제 실패 문구 — ER-07 재사용

§8.10.3에 이 경로의 실패 코드가 **없다.** 새 문구를 짓지 않고 ER-07
(`저장에 실패했습니다. 다시 시도해 주세요`)을 그대로 썼다 — 사용자에게는 같은 사실
(「쓰기가 실패했다」)이고, §4-6이 「없으면 만들지 말고 물어라」인데 **이미 있는 문구로
덮이는 경우**라 묻지 않았다. §8에 코드 부여 후보로 올렸다.

### 6.5 오프라인에서는 액션 시트를 열지 않는다

§8.7.5가 오프라인 S7을 「배너 + 캐시 목록」으로 규정하고 쓰기 경로가 없다.
🔴 **무반응**으로 처리했다 — §8.10에 「오프라인에서는 수정할 수 없습니다」 문구가 없어
**없는 문구를 지어내지 않았다.** §8.7.2 #7의 「부원은 롱프레스 무반응」과 같은 형태다.

⚠ **부작용** — 오프라인 사용자는 왜 반응이 없는지 알 길이 없다. §8 후보로 올렸다.

### 6.6 아바타는 `DSHSS.png` — 시안을 따르지 않았다

design `18b`·`18c`·`18d`의 요약 카드 아바타는 **그라디언트 + 이름 첫 글자**다.
🔴 **W-21 결정 4가 일반 학생 아바타를 정적 이미지로 통일**했고 S6 기록 작성 카드가 이미
그 형태다. 두 화면이 같은 학생을 다르게 그릴 수 없어 `DSHSS.png`를 썼다.
⇒ **DS-01 이탈이 아니라 결정 4의 적용**이다. W-21 §6 ③이 이미 열어 둔 항목이다.

### 6.7 `admin.ts`의 `Actor`를 import하지 않았다

구조가 같아 값은 그대로 통하지만, import하면 S8 전용 모듈(`fetchMembers` ·
`subscribePendingRequests` · 양도 배치)이 S7 청크로 끌려 들어온다.
**타입이 겹치는 것과 모듈이 겹치는 것은 다른 문제다.** `RecordActor`를 `records.ts`에 뒀다.

### 6.8 `deleteReason`을 허용 키에 넣지 않았다

§9.3.5가 `deleteReason`(0~100자)을 소프트 삭제 필드로 정의하지만 **MD-04에 입력란이 없다.**
길이 검증 없이 키만 열면 임의 길이 문자열이 들어온다. v1.1이 입력란을 만들 때
**키와 길이 조건을 함께** 연다 — W-16 §7이 `recordCount`에 쓴 것과 같은 형태다.

## 7. 🔬 측정 함정

**승계** — 시크릿 창은 세션 격리 · `MSYS_NO_PATHCONV=1` · `vite preview`는 `localhost` ·
인증 뒤 화면은 구조 주입으로 잰다 · `heredoc`이 백슬래시를 먹는다 · **`git checkout`은
커밋 전 회차에서 원복 수단이 아니다**.

**신규 4건**

### ① 🔴 「이 조건이 무엇을 막는가」를 두 번 틀렸다 — 역검증이 고쳤다

`softDeletesRecord()`의 출발지 조건(`resource.data.status == 'active'`)에 대해
**「빼면 되돌리기(RX-10)가 열린다」**로 적고 변형을 돌렸다.
🔴 **아무것도 빨개지지 않았다.**

원인 — RX-10을 막고 있는 것은 출발지 조건이 아니라 **목적지 조건**
(`request.resource.data.status == 'deleted'`)이었다. `status: 'active'`로 쓰는 요청은
거기서 먼저 걸린다.

⇒ 출발지 조건이 **실제로** 막는 것을 다시 찾아 **RX-11**로 잠갔다:
**이미 삭제된 기록의 `deletedBy`를 다른 사람 것으로 덮어쓰는 경로**다.
`status`가 `deleted → deleted`라 **값이 안 바뀌어 `affectedKeys()`에 들어가지 않고**
(B-20이 문서화한 성질), 나머지 조건이 전부 통과한다.

### ② 🔴 그리고 다시 틀렸다 — RX-10은 **세 겹**이었다

「두 status 조건을 **함께** 빼면 RX-10이 열린다」로 고쳐 적었다. **또 초록이었다.**

세 번째 벽이 **`deletedBy == request.auth.uid`**다. 되돌리는 요청은 `deletedBy`를 `null`로
비우는데(그것이 되돌리기의 정의다) `null == auth.uid`가 거짓이라 거기서 선다.

⇒ 🔴 **어느 하나만 벗겨도 RX-10은 열리지 않는다.** 세 조건이 각자 다른 것을 막고
(RX-9 · RX-11 · RX-7), 되돌리기는 **그 셋이 겹치는 자리**에서 막힌다.
**단일 변형에 대응하는 테스트가 없는 케이스**이고, 그 사실 자체를 테스트 주석에 남겼다.

⚠ **교훈** — 「이 조건은 X를 막는다」는 **가설이지 사실이 아니다.** W-16 Q-5의
`no-dollar-anchor`가 같은 종류였고, 이번에는 **두 번 연속** 같은 함정에 빠졌다.
🔴 **`breaks` 목록은 먼저 적고 실측으로 고치는 것이지, 실측을 보고 맞춰 적는 것이 아니다.**

### ③ 🔴 지시서의 규칙 변경 지시가 다른 배치를 죽일 수 있다

§3.4의 「`inviteCodes` create/update → `isDev()`」가 그것이다(§4.3).
🔴 **규칙 한 줄을 좁히기 전에 「이 규칙을 쓰는 배치가 또 있는가」를 코드에서 세어라.**
`grep`으로 `codeRef`·`inviteCodes`를 훑는 데 1분이면 됐고, 안 했으면 부장의 가입 승인이
배포 후에 죽었을 것이다.

### ④ ⚠ 작업 트리는 CRLF, index는 LF다

W-18 §6.4는 「`firestore.rules`는 CRLF, `src/**`는 LF」로 적었는데 **작업 트리 기준으로는
둘 다 CRLF**다(`core.autocrlf`). `git ls-files --eol`이 `i/lf w/crlf`를 보여 준다.
⇒ 스크립트로 파일을 고칠 때는 **읽은 개행을 그대로 되돌려 주면 된다.**
「LF여야 한다」로 단정하고 강제 변환하면 diff가 파일 전체로 부푼다.
🔬 실측 — `firestore.rules` `+103 −8`, `src/index.css` **`+122 −0`**(추가만).
