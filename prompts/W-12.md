### 2.3 오프라인 쓰기 계약 — 실측으로 확정한다

🔴 **W-08에서 실제로 터진 자리다.** `batch.commit()`이 오프라인에서 resolve되지 않아 스피너가 영원히 돌았다.
`db`는 `persistentLocalCache`로 초기화돼 있으므로 `setDoc()`의 Promise는 **서버 확인까지 resolve되지 않는다.**

아래 3가지를 실측하고 표로 보고한다.

1. 온라인에서 `setDoc()` Promise가 resolve되기까지의 대략적 시간
2. **오프라인에서 `setDoc()` Promise가 resolve되지 않는다는 사실** (N초 대기 후 pending 확인)
3. 오프라인에서도 **로컬 반영은 동기적으로 끝난다**는 사실 (같은 문서를 즉시 다시 읽어 확인)

→ 이 결과가 §3.7의 저장 파이프라인 근거가 된다. **`await setDoc(...)`으로 UI를 막는 코드를 쓰지 마라.**

### 2.4 30분 중복 검사 질의 형태

BR-01은 클라이언트 1차 검사이고, 이를 위한 IX-06(`studentDocId, reasonCode, occurredAt DESC`)은 **아직 생성돼 있지 않다.**
인덱스가 없으면 `failed-precondition`이 떨어지고, W-11 DoD 18의 교훈대로 **그 실패를 「중복 없음」으로 읽으면 안 된다.**

**그래서 이번 회차는 인덱스가 필요 없는 형태를 쓴다.**

```
query(records,
  where('studentDocId', '==', student.id),
  where('dateKey', 'in', [어제, 오늘]))       // 등식(in 포함)만 — 복합 인덱스 불필요
```

- 등식만 있는 질의는 자동 단일 필드 인덱스 병합으로 동작한다. **W-11이 IX-09에서 이미 실측한 성질이다.**
- 나머지 판정(30분 창 · `reasonCode` · `reasonText` · `status`)은 **전부 클라이언트**에서 한다. 한 학생의 하루치는 많아야 몇 건이다.
- 🔴 **어제를 함께 읽는 이유**: 00:10에 작성하면 30분 창이 전날 23:40까지 걸친다. **분기하지 말고 항상 2일치를 읽어라** — 등식 `in`이라 비용 차이가 없고 경계 버그가 사라진다.
- §8.6.3의 「30분 초과 + 같은 날 같은 사유 → MD-05 모달」도 **같은 결과 집합으로 판정된다. 추가 질의 0회.**

이 형태가 실제로 인덱스 없이 도는지 **질의 로그와 함께 실측**하고, 위 서술과 다르면 코드를 쓰기 전에 보고한다.

   우측 배지 `자동 입력` `11/700 #2E6B4C` · 배경 `rgba(31,81,56,0.10)` · `padding 4px 9px` · `radius 999`
7. **20px** 아래 주 버튼 가로 100% `기록 저장` (`.btnp` + `shine`)
8. **12px** 아래 중앙 안내 — 초록 점(`pulseDot`) + `11/500 rgba(20,53,38,0.70)` `저장 즉시 모든 부원에게 반영됩니다`

**리터럴 승격 판단**: 일시 텍스트 `14px`는 §7.2 타입 스케일에 없는 값이다(가장 가까운 것이 `Row title 14.5px`).
W-03B §3 기준(서로 다른 컴포넌트 2개 이상)에 걸리는지 판단해 승격하거나, 걸리지 않으면 **리터럴로 두고 보고서에 근거를 남긴다.**
임의로 `14.5px`로 맞추지 마라 — 원문은 `14`다.

### 3.2 사유 세그먼트 — `Segmented` 공용 컴포넌트

컨테이너 `radius 16` · `padding 5` · `gap 6` · 배경 `rgba(255,255,255,0.6)` · 테두리 `1px rgba(255,255,255,0.85)` ·
`inset 0 1px 3px rgba(20,53,38,0.05)`.
항목 3등분(각 `flex: 1`) · `radius 12` · 높이 **46** · 중앙 정렬 · `13/500` · 비선택 글자 `rgba(20,53,38,0.70)`.
선택 항목 = `linear-gradient(160deg,#2E6B4C,#1F5138)` + 흰 글자 `700` + 그림자 `0 6px 14px rgba(31,81,56,0.3)`.

- 좌 `복장 불량`(기본 선택) / 중 `실내화 미착용` / 우 `기타`
- 🔴 **선택 배경은 항목마다 켜고 끄는 것이 아니라 절대 위치 인디케이터 1개가 갖는다.** 독의 활성 알약과 같은 이유다 —
  항목마다 배경을 토글하면 가로 슬라이드가 불가능하다. 전이 `0.22s cubic-bezier(.2,.8,.25,1)`
- 탭 시 **선택된 쪽에 흰색 sparkle** (§3.4)
- `role="radiogroup"` + 각 항목 `role="radio"` `aria-checked` (§15.3). 항목은 `<button type="button">`이다
- 🔴 **200% 확대에서만 2행 그리드(2 + 1)로 접는다**(AC-11 · §8.6.2). 평소에는 반드시 1행 3분할이고,
  **라벨 텍스트는 어떤 경우에도 축약하지 않는다.** 높이 46은 두 경우 모두 유지한다
- `inset 0 1px 3px rgba(20,53,38,0.05)`는 W-09 승격 대기 목록의 `--shadow-inset-soft` 후보다. 두 번째 사용처가 생기면 승격을 판단하라

**`Segmented`는 사유를 모른다.** `items: { value, label }[]` · `value` · `onChange(value, event)`만 받는다.
사유 코드(`DRESS`/`SLIPPER`/`ETC`)와 라벨의 대응은 `RecordSheet`가 갖는다.

`Field` 규격 그대로. Floating Label `기타 사유`, 포커스 중에만 placeholder `예: 명찰 미착용`.

| 항목 | 값 |
| --- | --- |
| 글자 수 카운터 | 우측 안쪽 **16px**, `0/20` `11/500 rgba(20,53,38,0.70)` `tabular-nums`. **18자를 넘기면 `#C0392B`** |
| 힌트 | 입력 아래 **6px**, `11/500 rgba(20,53,38,0.70)` — `사실만 짧게 적어 주세요. 학생에 대한 평가나 별명은 쓰지 않습니다` |

⚠ **W-08 §5-1의 선례를 그대로 따른다** — 버튼 활성 조건은 「저장 가능한 최소 조건」이지 「검증 성공」이 아니다.

### 3.5 오픈·닫힘 상태 기계 — 여기서 실수가 나온다

**히스토리(결정 2)**

```tsx
// 열기
navigate(location.pathname, { state: { sheet: true }, preventScrollReset: true })
// 닫기 요청 (저장 성공 · 딤 탭 · 아래 스와이프 · ESC 전부 이 경로)
if (location.state?.sheet) navigate(-1)
// 실제 닫힘: location.state.sheet가 사라진 것을 보고 닫는다 (제스처 뒤로가기도 같은 지점으로 들어온다)
```

- `pathname`이 같으므로 `ScreenTransition`(`key={pathname}`)은 **재마운트되지 않는다.** S5의 명부·스크롤 위치가 살아 있다
- **닫는 경로는 단 하나다.** 「닫기 요청 → 히스토리 뒤로 → state 소멸 감지 → 닫힘」. 세 갈래로 각각 닫지 마라
- 새로고침으로 `state`가 사라지면 시트는 닫힌 상태로 시작한다. 정상이다

**마운트 (값 폐기의 실제 구현)**

S5가 `{ student, key }`와 `open`을 따로 들고 있는다.

- 열기: `key`를 증가시켜 **`RecordSheet`를 새로 마운트**한 뒤 `open=true`
- 닫기: `open=false`만 한다. **`student`를 즉시 비우지 마라** — 닫힘 애니메이션 0.38s 동안 내용이 사라진다

이렇게 하면 `occurredAt` · `clientRecordId` · 사유 초기화 · 기타 입력값 폐기가 **한 곳(마운트)에서 자동으로** 일어난다.
`open`이 false→true로 바뀌는 것을 `useEffect`로 감지해 상태를 되돌리는 방식을 쓰지 마라 — 초기화 누락이 반드시 하나 생긴다.


| 단계 | 처리 |
| --- | --- |

| 사전 검증 | ① `student`가 없으면 시트를 닫고 토스트 `학생 정보를 확인할 수 없습니다` ② `role`이 `member`·`vice`·`head`·`dev`가 아니거나 `status`가 `active`가 아니면 시트를 닫고 토스트 `기록 작성 권한이 없습니다` ③ `기타`인데 트림 후 2자 미만이면 **시트를 유지**하고 인라인 에러 + shake |

| 로컬 쓰기 | `setDoc(doc(db,'records',clientRecordId), payload)` — 🔴 **`await`하지 마라.** `.catch()`로 오류만 삼키고(로그만) 즉시 다음 단계로 간다 |
| 캐시 무효화 | `stats.ts`의 홈 캐시를 비운다. 🔴 **`clearRosterCache()`는 부르지 마라** — 명부까지 버린다(W-11 §4-5) |
| 닫기 | §3.5의 닫기 요청 |
| 토스트 | 온라인 `기록 저장됨`(TS-01) / 오프라인 `기록 저장됨 · 연결되면 자동 전송`(TS-02). 판정은 `navigator.onLine` |

🔴 **왜 `await`하지 않는가**(§2.3 실측 근거): 오프라인 지속성이 켜져 있으면 `setDoc`의 Promise는 서버 확인까지 resolve되지 않는다.
기다리면 **음영 구간에서 스피너가 영원히 돈다** — 정확히 W-08에서 터졌던 실패다.
Firestore가 로컬에 커밋한 시점에 데이터는 이미 안전하고(BR-38 「저장은 로컬 우선」), 전송은 SDK가 책임진다.

**그래서 T-07(저장 실패 → 시트 유지 + 인라인 배너 + 롤백)은 사전 검증 실패에만 적용된다.**
서버 거부(규칙 위반·시각 위조)는 이 계층에서 관측되지 않는다. **그 사실을 보고서와 `database_ToDo/W-12.md`에 명시하고 W-17로 넘긴다.**

**낙관적 로컬 반영(T-05)은 별도 코드가 필요 없다.** Firestore 로컬 캐시가 그 자체다.
S7이 아직 없으므로 화면에 즉시 반영할 목록도 없다. **가짜 낙관적 상태를 만들지 마라.**

### 3.9 `dateKeys.ts` — `toMonthKey`

`toDateKey`·`toWeekKey`와 **같은 KST 규칙**으로 `YYYY-MM`을 만든다(§9.3.5 · DR-05).
🔴 **기존 두 함수의 KST 변환을 복사하지 말고 공유하라.** 세 함수가 서로 다른 경로로 KST를 계산하면

경계 3케이스를 단위 실측한다 — `00:05` / `23:55` / **월요일 `00:00`**(주 경계, DR-06 ISO 주차).

새로 만들면 멱등성(BR-02)이 깨져 같은 기록이 2건 남는다.

### 3.12 접근성 (§15.3 · §15.4)

- 시트 `role="dialog"` `aria-modal="true"` · 포커스 트랩 · **닫을 때 트리거였던 학생 행으로 포커스 복귀**
- 세그먼트 `radiogroup`/`radio`/`aria-checked`, 기타 입력 `aria-expanded`

## 5. `database_ToDo/W-12.md`가 담아야 할 것

2. **IX-06** — 이번 회차는 쓰지 않는다(§2.4의 등식 `in`으로 대체). 서버 중복 검사로 전환하거나 S7의 학생별 이력을 붙일 때 필요해진다. 요청 시점과 근거
3. 🔴 **`recordCount` 규칙 개정 요청** (결정 1) — §9.6 `users` update의 자기 갱신 허용 키에 `recordCount`를 넣을지,
   아니면 프로파일 B(`beforeCreate`/Callable)로 미룰지. **지금은 아무도 올리지 않아 값이 영원히 `0`이며 버그가 아니다**를 명시

## 6. 검증 환경

W-07~W-11과 같은 방식이다. **새로 필요한 것 3가지**만 적는다.

1. 스텁 `firestore`가 **`where(..., 'in', [...])`** 를 해석해야 한다. 질의 키를 기록해 §2.4의 「인덱스 불필요」 근거로 삼는다
2. 스텁이 **`setDoc`을 오프라인 모드로 흉내** 낼 수 있어야 한다 — 로컬 반영은 즉시, Promise는 pending 유지(§2.3)
3. 시각 고정 — `occurredAt`·`dateKey`·경계 3케이스를 재현하려면 기기 시각을 주입할 수 있어야 한다.
   **화면 코드에 시각 주입 훅을 만들지 마라.** 하네스에서 `Date`를 덮는다

**W-11이 남긴 측정 함정 2건을 그대로 적용한다.**
① `delayMs`는 인증 `getDoc`에도 걸린다 — 화면의 로딩 구간은 `delayMs` 경과 **뒤**에 시작한다
② 스크롤·경계 검증은 조건이 실제로 성립해야 한다 — 조건을 못 만들었으면 통과가 아니라 **미측정**이다
