### 0.3 사용자 확정 결정 3건

**결정 1 — 초과 승인은 A안이다. 승인 시점에 한도를 검사하지 않는다.**
`useCount >= maxUses` 여부와 무관하게 승인은 성공하고 `useCount`는 그대로 +1 된다.
근거: **BR-14의 실질 게이트는 신청 시점(S2)이다.** 승인은 부장의 명시적 판단이라 사람이 이미 게이트이고,
초과분은 「이미 신청을 통과한 사람」으로 상한이 묶인다. 🔴 **한도 초과 경고 UI를 만들지 마라** — §8.10에 문구가 없다.
**§7에 「BR-14는 신청 시점 검사임을 각주로 명시」를 신규 항목으로 올려라.**

**결정 2 — 규칙 회차를 S8 직후(W-16)로 당긴다.** (§0.1)

**결정 3 — S8을 2분할한다.** 이번은 **③ 가입 승인 + ① 부서 가입 코드**다.
🔴 **② 부원 목록 · 권한 양도는 만들지 마라.** 섹션 자체를 렌더하지 않는다.

## 3. 구현 지시

### 3.1 화면 골격과 역할별 노출

- 제목 `관리`(H1) + **역할 배지**(그라디언트) — `부장` / `차장` / `교사` / `Dev`. 🔴 **`Dev`는 §8.10.6 고정 영문**이다
- 섹션 순서는 §8.8.2 그대로 — **① 부서 가입 코드 → ③ 가입 승인 대기**. ②는 그 사이에 **자리를 비운다**(빈 div도 만들지 마라)
- 🔴 **역할별 노출을 §8.8.2 표 그대로 지킨다**

| 섹션 | 부원 | 차장 | 부장 | 교사 | Dev |

| 헤더 | — | ✔ | ✔ | ✔ | ✔ |

- 하단 힌트 `기록 수정·삭제는 부장·차장만 가능합니다`(§8.10.5)
- 🔴 **한 섹션의 실패가 다른 섹션을 막지 않는다**(§8.8.6). 조회도 렌더도 섹션 단위로 독립이어야 한다

### 3.5 🔴 쓰기 3종 — 배치 계약

**세 가지 모두 「부분 성공이 없다」가 요구다.** `writeBatch`로 묶는다.

**(a) 승인 — OP-09**

```
writeBatch:
  users/{uid}          .status = 'active',  approvedBy, approvedAt, updatedAt
  approvalRequests/{id}.status = 'approved', decidedBy, decidedAt
  inviteCodes/{codeId} .useCount = increment(1)        ← W-08 §0.2 안 2
  auditLogs/{newId}    action: 'USER_APPROVE'
```

- 🔴 **한도를 검사하지 않는다**(결정 1)
- `inviteCodes/{codeId}`는 신청자의 `users.inviteCodeId`(= 코드 문자열)에서 온다.
  🔴 **그 값이 없거나 코드 문서가 사라졌으면 `useCount` 갱신만 건너뛰고 승인은 진행한다** —
  코드 문서 때문에 사람의 가입이 막히면 안 된다. 이 분기를 보고서에 남겨라
- 확인 모달 **없음**. 즉시 처리(T-05) → 행 페이드아웃 `0.2s` + 배지 감소 + 토스트 **TS-07**

**(b) 거절 — OP-09**

```
writeBatch:
  users/{uid}          .status = 'rejected', rejectReason: null, updatedAt
  approvalRequests/{id}.status = 'rejected', decidedBy, decidedAt
  auditLogs/{newId}    action: 'USER_REJECT'
```

- 확인 모달 **MD-03** → 토스트 **TS-08** `가입을 거절했습니다`. 🔴 **`useCount`를 건드리지 않는다**

**(c) 코드 재발급 — OP-10**

```
writeBatch:
  (기존 코드가 있으면) inviteCodes/{old}.isActive = false, revokedAt
  inviteCodes/{newCode}  전체 필드 생성          ← 🔴 문서 ID = 코드 문자열 (W-08 안 1)
  departments/{id}      .activeInviteCodeId = {newCode}, updatedAt
  auditLogs/{newId}      action: 'CODE_ISSUE'
```

- 확인 모달 **MD-01** → 새 코드 표시(`blurIn`) + 토스트 **TS-05**
- 🔴 **`code` 필드도 문서 ID와 같은 값으로 넣는다**(규칙이 `data.code == codeId`를 강제한다 — `database_ToDo/W-08.md` §2-1)
- 신규 문서의 필드는 §9.3.3 전부 — `code`·`issuedBy`·`issuedAt`·`expiresAt`(발급 + 14일, BR-13)·`isActive: true`·`revokedAt: null`·`useCount: 0`·`maxUses: 30`
- **레이트 리밋**(BR-16 · §11.5) — `inviteCodes`에서 `issuedAt >= 1시간 전`을 세어 **5회 이상이면 버튼 비활성** +
  탭 시 **E-3002** `잠시 후 다시 시도해 주세요 (시간당 5회 제한)`

**🔴 오프라인 계약**

§8.8.6이 「오프라인: **전 액션 버튼 비활성** + 배너 `오프라인 상태에서는 관리 기능을 사용할 수 없습니다`」로 규정한다.

## 6. 검증 환경

W-14와 같은 스텁 하네스다. **새로 필요한 것 4가지**만 적는다.

1. 🔴 **`writeBatch` 스텁** — `set`·`update`·`delete`를 큐에 쌓고 `commit()`에서 **원자적으로** 반영한다.
   **부분 성공을 재현할 수 있어야 한다**(중간 연산에서 던져 전체가 롤백되는지) · `commit()`을 **영원히 pending**으로 두는 모드
2. **`increment` 센티널** — `useCount`가 실제로 +1 되는지 관측 가능해야 한다
3. **`onSnapshot` + `getDoc` 혼용** — W-13·W-14의 스텁을 합친다. 🔴 **`getDoc`은 캐시 미스에서 `unavailable`로 throw**해야 한다(W-14 P1)
4. **역할 주입 5종** — `member`·`vice`·`head`·`teacher`·`dev`. 섹션 노출 매트릭스를 전수로 잰다

**측정 함정 — 앞선 회차가 남긴 것을 그대로 적용한다.** 특히
② `__WRITES__`는 경로별로 세어라 — 이번엔 **한 배치에 4개 컬렉션**이 들어간다
⑤ **StrictMode 이중 마운트**가 구독·질의 횟수를 2배로 찍는다
③ 전이는 끝난 뒤에 읽어라 / **조건을 못 만든 검증은 미측정이다**
