## 3. `AuthProvider`에 `refresh()`를 추가한다 — **A안 확정**

W-06 §9가 올린 A·B·C 중 **A를 택한다.**

| 안 | 판정 | 이유 |
| --- | --- | --- |
| **A `refresh()` 추가** | **채택** | 가장 작다. `resolve()`를 재사용하므로 **W-17이 `getDoc` 경로를 고치면 `refresh()`가 자동으로 함께 고쳐진다** — A의 약점으로 지목된 캐시 폴백은 A가 새로 만드는 위험이 아니라 기존 위험을 물려받는 것뿐이고, 물려받은 만큼 함께 해소된다. `AuthProvider`가 판정을 독점한다는 W-04 계약도 유지된다 |
| B `onSnapshot` | 기각 | W-12를 앞당긴다. **규칙이 아직 임시인 상태**에서 모든 인증 읽기의 형태를 바꾸는 것은, W-17이 다시 볼 예정인 지점 위에 큰 베팅을 하는 것이다 |
| C 화면이 직접 `getDoc` | 기각 | 판정 로직이 화면으로 샌다. 같은 판정이 두 곳에 생기면 반드시 갈라진다 |

**BR-27과의 관계**: BR-27은 `실시간 구독`이라 적었고 §8.2.6은 `30초 간격 폴링 **또는** 실시간 구독`을 허용한다. 화면 상세 명세가 더 구체적인 계층이므로 폴링은 규격 위반이 아니다. **BR-27 문구를 §8.2.6에 맞춰 개정할지는 st4R 결정 사항이므로 보고서 "PRD 반영 필요"에 올려라.**

### 3.1 시그니처

```ts
refresh: () => Promise<void>
```

`useAuth()` 반환값에 **8번째 항목으로 추가**한다. 다른 7개(`status`·`profile`·`parsed`·`rejectedEmail`·`errorCode`·`signIn`·`signOut`·`clearRejection`)는 이름·타입·거동 전부 그대로다.

### 3.2 거동 규칙 — 전부 DoD로 검증한다

| # | 규칙 | 이유 |
| --- | --- | --- |
| 1 | 현재 로그인된 사용자로 `resolve()`를 **다시 돌린다**. 판정 로직을 새로 쓰지 마라 | 판정은 한 곳에만 있어야 한다 |
| 2 | **`status`를 `loading`으로 되돌리지 않는다** | 되돌리면 `AuthGate`가 스플래시를 띄워 S2-1이 30초마다 사라진다 |
| 3 | **실패하면 현재 `status`를 그대로 둔다.** 실패를 `noProfile`·`signedOut`으로 떨어뜨리지 마라 | 폴링 1회 실패에 사용자가 가입 신청 화면으로 튕기면 안 된다. W-05 §9 위험의 최악 시나리오가 바로 이것이다 |
| 4 | 재진입 방지 — **동시 호출은 1회만 돈다.** `useState`가 아니라 **동기 ref 빗장**을 써라 | §0.2 말미의 확정 규칙 |
| 5 | 미인증 상태(`signedOut`·`domainRejected`)에서 호출되면 **아무 것도 하지 않고 즉시 반환**한다 | 재인증을 유발하지 마라 |
| 6 | `throw`하지 않는다 | `signIn`과 같은 계약(W-06 §2.2) |
| 7 | 감사 로그·DR-12 동기화를 **매 호출마다 반복하지 않는다** | §2.2 마지막 항목. 반복된다면 멈추고 물어라 |

`resolve()`에 `{ silent?: boolean }` 정도의 최소 매개변수를 더해 규칙 2·3을 만족시키는 것은 **허용한다.** 그 이상으로 `AuthProvider`를 고치지 마라.

## 4. `/signup`에 `rejected`를 허용한다

BR-28이 `rejected` 계정의 재신청을 허용하고 §8.2.6이 거절 변형에 `가입 코드 다시 입력` → S2 이동을 규정한다. 그런데 지금 `/signup`의 `allow`는 `noProfile`·`withdrawn`뿐이라 **거절 계정이 그 버튼을 눌러도 `/pending`으로 되튕긴다.**

| 항목 | 처리 |
| --- | --- |
| 변경 | `/signup`의 `allow`에 **`rejected` 1개만** 추가한다 |
| 착지 표는 그대로 | `rejected`의 기본 착지는 여전히 `/pending`이다(§3.1). `allow` 확장은 "직접 이동이 허용된다"는 뜻이지 착지 화면을 바꾸는 것이 아니다 |
| 다른 라우트 | **건드리지 마라.** 이 1칸 외에 매트릭스가 바뀌면 실패다 |
| 도착지 | S2는 아직 자리표시자다. **정상이다.** W-08이 채운다 |
| PRD | §6.1 S2 진입 경로가 `신규·탈퇴 계정`만 적고 있다. BR-28과 어긋나므로 보고서 "PRD 반영 필요"에 올려라 |

### 5.3 문구 — 이 문자열만 쓴다 (§8.2.6)

| 위치 | A 승인 대기 | B 거절됨 |
| --- | --- | --- |

| 주 버튼 | `승인 확인` | `가입 코드 다시 입력` |

## 6. 자동 감지와 쿨다운

### 6.1 폴링

| 항목 | 규격 |
| --- | --- |
| 주기 | **30초** (§8.2.6) |
| 조건 | `status === 'pending'`일 때만. `rejected`에서는 돌지 않는다 |
| 가시성 | `document.visibilityState === 'visible'`일 때만. 백그라운드에서는 멈추고, 복귀 시 **즉시 1회** 돈 뒤 주기를 재개한다 |
| 중복 | 진행 중인 `refresh()`가 있으면 건너뛴다 |
| 정리 | 언마운트·`status` 변화 시 타이머를 반드시 해제한다 |
| 소유 | **폴링 주기는 화면이 소유한다.** `AuthProvider`에 넣지 마라 — 화면마다 정책이 다르다 |

지수 백오프·재시도 횟수 제한을 넣지 마라. 요구되지 않았다.

### 6.2 쿨다운

| 항목 | 규격 |
| --- | --- |
| 길이 | **10초** (§8.2.6) |
| 표현 | 버튼 `disabled` + `aria-disabled="true"`. **남은 초를 표시하는 문구·카운트다운을 만들지 마라** — §8.2.6에 규격이 없다 |
| 시작 | `refresh()` 완료 시점(성공·실패 무관) |
| 언마운트 | 타이머 해제 |

쿨다운 중 시각 피드백이 없는 것이 불친절하다고 판단되면 **구현하지 말고 보고서에 W-18 후보로 올려라.**
