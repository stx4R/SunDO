## 3. 구현 지시

### 3.1 🔴 기능 3 — 중식/석식은 **데이터 모델 결정**이다

**설계안을 표로 내고 사용자 확인을 받은 뒤에 코드를 써라.** 최소 두 갈래가 있다.

| 안 | 형태 | 장점 | 대가 |
| --- | --- | --- | --- |
| **A. 한 문서 안에서 나눈다** | `assignments.lunch.mon` / `assignments.dinner.mon` | 문서 1개 유지 · 주차 키 그대로 | 🔴 **기존 2건 마이그레이션** · 중첩이 깊어진다 |
| **B. 문서를 나눈다** | `2026-W35_lunch` / `2026-W35_dinner` | 스키마가 평평하다 | 🔴 **문서 ID 규약이 바뀐다** · 읽기가 2배 · S9가 두 번 읽는다 |

🔴 **어느 쪽이든 기존 2건(`2026-W34`·`W35`)을 옮겨야 한다.**

**마이그레이션 규약**

- 🔴 **`--dry-run`이 기본값이고 `--commit`이 있어야 쓴다**(W-16D §2.3 그대로)
- 🔴 **기존 문서를 지우지 마라.** 새 형태로 **쓰고**, 옛 형태는 남긴 채 앱이 새 것을 읽게 하라.
  되돌릴 수 있어야 한다
- 실행 전 요약(대상 건수 · 변환 결과) → 사용자 확인 → `--commit`
- 🔴 **앱보다 먼저 돌려라.** 새 앱이 옛 문서를 읽으면 S9가 죽는다

**화면**

- S9 조회와 편집 **양쪽**에서 중식/석식을 가른다. 🔴 **탭인지 섹션인지는 design `19`가 정한다**
- 편집은 **부장만**. 🔴 차장·부원·교사에게는 편집 진입점을 **렌더하지 마라**(W-15A §4-4의 「읽기 전용은 부재」)
- 담당자 검색 팝오버는 `users` 목록을 쓴다 — **`list`는 이미 열려 있다**(M-1)
- 🔴 **감사 로그** — `DUTY_UPDATE`가 §9.3.8에 있다. 남길지 판단하고 근거를 적어라.
  남긴다면 배치가 2연산이 되고 **부분 성공 없음**이 걸린다

### 3.2 기능 4 — 학생 검색

**§2.3의 조사 결과로 방식을 정하고 근거를 적어라.**

| 후보 | 판단 재료 |
| --- | --- |
| **전량 로드 + 클라이언트 필터** | 1,033건. 🔴 **이름 중간 일치가 된다.** 첫 로드 비용과 캐시 재사용을 실측하라 |
| **prefix 질의** | 읽기가 적다. 🔴 **「준」으로 「김준서」를 못 찾는다** — 사용자가 원하는 것인지 확인 |
| **혼합** | 학번은 prefix · 이름은 클라이언트 |

- 🔴 **학번과 이름 둘 다** 받는다(사용자 요구). 입력이 숫자면 학번, 아니면 이름 — 판정 규칙을 적어라
- 결과를 탭하면 **바로 기록 작성**(S6 시트). 🔴 **기존 경로를 재사용하라** — `ClassStudents`가
  시트를 여는 방식(W-12)을 복제하지 마라
- 진입점은 **홈**. 🔴 **`AppShell`·`Dock`을 고쳐야 한다면 §9로 물어라**
- ⚠ **`isActive: false` 학생을 결과에서 걸러라**(클라이언트 필터 — W-11 §3 B안)

### 3.3 🔴 기능 9 — 기록 수정·삭제

**권한 — 셋뿐이다**

```
작성자 본인(createdBy == uid)  또는  head  또는  dev
```

🔴 **규칙과 화면이 같은 문장이어야 한다.** 헬퍼를 재사용해 `vice`가 섞이지 않게 하라
(W-17F의 결함 1이 정확히 그 형태였다 — 화면이 규칙보다 넓거나 좁으면 사용자가 혼란스럽다).

**삭제 — 소프트 삭제다**

- `status: 'active' → 'deleted'`. 🔴 **문서를 지우지 마라**
- S7 목록이 `status == 'active'`로 질의하므로 **자동으로 빠진다**(W-13)
- 🔴 **`recordCount` 감소를 할 것인가 — 판단하고 근거를 적어라.**
  - W-16 §7이 「v1.1 삭제 회차에 규칙을 넓힌다」로 예약했다
  - ⚠ **감소를 넣으면 배치가 커지고 규칙이 「+1만」에서 「±1」로 넓어진다**
  - ⚠ **넣지 않으면 `recordCount`가 실제 건수보다 커진다** — 그 값의 소비자가 지표(M-02)뿐이라면
    감수할 수 있다. 🔴 **소비자를 세어 보고 결정하라**

**수정 — 사유 변경**

- 🔴 **`validReason()`을 그대로 통과해야 한다** — `ETC`면 `reasonText` 2~20자, 아니면 `reasonText` 없음
- 🔴 **바꿀 수 있는 필드를 `hasOnly`로 못 박아라.** `createdBy`·`studentDocId`·`occurredAt`을
  바꿀 수 있게 열지 마라
- ⚠ **`affectedKeys()`는 「값이 바뀐 키」다**(W-17 §4.6). 테스트를 쓸 때 같은 값을 다시 쓰면
  통과한다 — `B-20`이 그 성질을 문서화했다

**감사 로그** — `RECORD_UPDATE`·`RECORD_DELETE`가 §9.3.8에 있다.
🔴 **남긴다면 `before`/`after`에 학생 이름을 담지 마라**(W-18 §2.1① · 익명화와 양립).

### 3.4 기능 12 — 코드 발급 권한

- `inviteCodes` create/update → **`isDev()`**
- 🔴 **`departments` update가 문제다** — 재발급(`activeInviteCodeId`)은 dev만, 양도(`headUid`)는
  head·dev 둘 다여야 한다. **같은 규칙 블록이 둘을 다 받는다.**
  → **필드별로 가를 수 있는지 판단하고, 못 가르면 §9로 물어라.**
  ⚠ 🔴 **넓은 쪽으로 두면 통제가 성립하지 않는다**(부장이 여전히 `activeInviteCodeId`를 바꿀 수 있다)
- S8 화면 — 부장에게 **복사만**. 재발급 pill은 `dev`에게만
- 🔴 **문구** — 「부장은 재발급할 수 없다」를 알리는 안내가 §8.10에 있는가. 없으면 §9

## 5. 🔴 배포 순서 — 이 회차의 급소

### 5.1 §18.4의 전제

「Rules·인덱스 배포는 앱 배포보다 **먼저**」 — **앱이 먼저 나가면 아직 없는 권한을 두드린다.**

### 5.2 넓히는 규칙(3·4·9)은 §18.4 그대로

규칙을 **먼저** 배포해도 옛 앱은 그 권한을 쓰지 않으므로 **아무것도 깨지지 않는다.**

### 5.3 🔴 좁히는 규칙(12)은 반대로 선다

`inviteCodes`를 `isHead()` → `isDev()`로 좁히면, **규칙을 먼저 배포한 순간 옛 앱의
부장 재발급이 즉시 죽는다.** 화면에는 여전히 pill이 보이는데 누르면 실패한다.

**그래서 이렇게 한다.**

| 순서 | 무엇 |
| --- | --- |
| ① | **넓히는 규칙(3·4·9) + 인덱스**를 먼저 배포 |
| ② | 앱 배포 |
| ③ | 🔴 **좁히는 규칙(12)을 그 직후에** |
| ④ | 스모크 |

⚠ **③과 ②의 간격을 짧게 하라.**
🔴 **지금은 실사용자가 3명(전부 테스트 계정)이고 URL이 공유되지 않았으므로 그 창이 무해하다** —
**그 사실을 근거로 적고, 실사용이 시작된 뒤에는 이 순서를 다시 판단해야 함을 §7에 남겨라.**

⚠ 🔴 **W-20 §3.2가 「같은 논리가 반대로 서는」 예를 이미 남겼다.** 같은 형태다 —
규칙이 무엇을 하느냐가 아니라 **틀렸을 때 무엇이 깨지느냐**가 순서를 정한다.

### 5.4 롤백

- 🔴 **규칙 롤백은 이제 Git 이력에서 이전 버전 재배포가 가능하다**(W-16 이후 파일이 있다)
- 마이그레이션은 🔴 **옛 문서를 남겨 두었으므로** 앱만 되돌리면 된다
- 서비스 워커는 건드리지 않는다 — 건드렸다면 `database_ToDo/W-20.md` §1.4
