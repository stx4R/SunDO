### 2.3 🔴 주차 규격의 공백 — 코드를 쓰기 전에 정한다

| 물음 | 근거와 공백 |
| --- | --- |
| `weekId`는 무엇인가 | §9.3.6 — `YYYY-Www` **KST ISO 주차**. `toWeekKey`가 이미 만든다. **새로 계산하지 마라** |
| 화면의 `{M}월 {n}주차`는? | BR-47 표기 · **BR-48 「해당 월의 첫 월요일이 속한 주를 1주차로 센다」** |
| 🔴 **공백** | BR-48은 **첫 월요일 이전 날짜가 몇 주차인지 말하지 않는다.** 예: 2026-08-01(토)은 8월 1주차인가, 7월 마지막 주차인가 |

**해석을 이렇게 고정한다** — **그 주의 월요일이 속한 달을 기준 달로 삼고, 그 달의 첫 월요일이 1주차다.**
이러면 모든 주가 정확히 하나의 `(월, n주차)`에 대응하고 중복·공백이 없다.
🔴 **이것은 신규 확정값이다. §7에 올려라.** 다른 해석이 더 낫다고 판단되면 **코드를 쓰기 전에 물어라.**

경계 4케이스를 순수 함수로 실측한다 — 월 첫날이 월요일인 달 / 화요일인 달 / 일요일인 달 / 월 마지막 주.

## 3. 구현 지시

### 3.1 화면 골격 (design `1j` 순서)

위 → 아래: 제목 `선도 일정`(H1) + 주차 표기 → 오늘 순찰 카드 → 요일 행 5개 → 하단 힌트.
색·간격·크기는 `1j` 원문 그대로이되, **`舊 version.` 3종 이탈(OV-02·OV-03·OV-04)은 적용하지 않는다.**

- 우측 상단 `일정 편집` 버튼 자리는 **비워 둔다**(§0.5). 제목이 그 자리를 차지해도 좋다 — **대조표에 이탈로 적어라**
- 하단 힌트 `다음 주 일정은 부장·차장이 등록합니다` — **문구 그대로**(§8.10.5)

### 3.2 주차 표기

- `weekId`는 **`toWeekKey(now)`** 그대로. 🔴 **직접 계산하지 마라**
- 화면 표기는 `{M}월 {n}주차` — §2.3에서 고정한 해석으로 `dateKeys.ts`에 순수 함수를 추가한다
- 🔴 **`formatDateKeyLabel`이 `dateKey` 문자열을 받는 것과 같은 이유로**, 주차 표기 함수도
  **`weekId` 문자열 또는 `Date` 중 하나로 인자를 고정**하고 호출부가 다시 계산할 여지를 주지 마라. 선택 근거를 적어라

### 3.3 오늘 순찰 카드

주 그라디언트 카드. 상단 `오늘 순찰 · {요일}요일` → 담당자 칩 N개 → 하단 `{순찰 시간} · {장소}`.

- 요일 판정은 **KST 기준**이다. `dateKeys.ts`의 KST 변환을 통과시켜라
- 담당자 칩은 `assigneeNames`의 이름을 그대로 쓴다 (§3.5)
- 🔴 **주말(토·일)에는 이 카드 대신 §3.7의 블록이 온다**

### 3.4 요일 행 5개

월~금 고정(§8.9.3 · D-10 기본값). 각 행 = 요일 배지 + 담당자 이름을 **` · `로 연결**.

- 오늘 강조 `drow.today` — 배경 틴트 + 배지 그라디언트 + `오늘` 칩. **주말에는 강조 행이 0개다**
- 담당자가 0명인 요일은 문서가 규정하지 않는다(편집 검증이 1명 이상을 강제하지만 그것은 v1.1이다).
  **시딩 실수로 빈 요일이 올 수 있다** — 빈 배열을 안전하게 그리고, 화면이 죽지 않는지 실측하라
- `patrolTime`·`patrolPlace`는 **문서의 값을 쓴다.** 문서에 없으면 `fetchDepartment()`의 부서 기본값으로 떨어진다(§9.3.6 「부서 기본값」)

### 3.5 🔴 담당자 이름은 `assigneeNames` 스냅샷이다 — `users`를 읽지 마라

§9.3.6이 `assigneeNames`를 **표시용 이름 스냅샷**으로 따로 두는 이유가 이것이다.

- **`users` 질의 0건**이어야 한다. DoD로 잠근다
- 🔴 **탈퇴 작성자 취소선(BR-58)을 여기에 적용하지 마라.** BR-59가 「**이미 편성된 과거 주차의 담당자 이름은 그대로 남긴다**」로
  명시한다. S7과 S9는 **다르게 동작하는 것이 정상**이다
- 결정 3(§0.3)의 클라이언트 규율이 여기서 지켜진다 — S9는 `users`를 아예 읽지 않으므로 규율 위반 여지가 없다

### 3.6 🔴 실시간 구독을 켜지 않는다

W-13 §8-1의 구독 계약은 **목록형 화면**을 위한 것이다. S9는 문서 **1~2건**이고, 편집이 v1.1이라
**MVP에서 이 문서를 바꾸는 주체가 앱 안에 없다.**

- `getDoc` 단발 조회 + `usePullToRefresh` + N-06(백그라운드 복귀 재조회)로 충분하다
- 🔴 **`onSnapshot` 호출 0건**을 `grep`과 런타임 양쪽으로 확인한다 (DoD)
- §8.9.4 T-03의 「전 사용자 실시간 반영」은 **편집 저장 시점의 요구**이고 v1.1이다

### 3.7 주말 처리 (T-04)

토·일에 진입하면 오늘 카드 자리에 **`이번 주 순찰이 종료되었습니다`** + **다음 주 일정 미리보기**.

- 🔴 **다음 주 문서는 주말에만 읽는다.** 평일 질의 **1건**, 주말 질의 **2건** — 질의 로그로 잠근다
- 다음 주 문서가 없으면 미리보기 자리에 **EM-06과 같은 문구를 재사용하지 말고**,
  「다음 주 일정이 아직 등록되지 않았습니다」류의 새 문구가 필요한지 판단하라.
  🔴 **§8.10.2에 그 문구가 없다.** 새로 지어내지 말고 **§7 신규 항목으로 올리고**, 이번에는
  **미리보기 블록 자체를 그리지 않는 쪽**으로 처리한다(문구를 만들지 않는다)
- `이번 주 순찰이 종료되었습니다`는 §8.9.4 T-04 원문이다. **§8.10.2 사전에는 없다** — 이것도 §7 신규 항목이다

## 6. 검증 환경

W-13과 같은 스텁 하네스다. **새로 필요한 것 3가지**만 적는다.

1. **`getDoc` 스텁의 문서 부재·에러 주입** — `exists() === false`와 3코드(`permission-denied`·`unavailable`·`failed-precondition`)를 가른다

3. **`dutySchedules` 픽스처** — 평일/주말, 문서 있음/없음, 빈 요일 포함

**측정 함정 — W-12·W-13이 남긴 8건을 그대로 적용한다.** 특히
③ **픽스처 시각이 실행 시각보다 미래일 수 있다**(W-13 ③) — 요일 판정이 걸린 이번 회차에 특히 위험하다.
