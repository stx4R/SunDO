### 0.3 🔴 사용자 확정 결정 3건

**결정 1 — `departments.memberCount`를 폐기한다.**
증가·감소 어느 경로도 없고 `src/` 전체에 참조가 0건인 **죽은 필드**임이 W-16D에서 실측으로 확정됐다.

- 🔴 **S10에 부원 수를 그리지 마라.** PRD §8.11이 요구하지 않는다면 만들지 않는다
- ⚠ **§8.11이 부원 수 표시를 요구한다면** 필드를 읽지 말고 **`users` count 질의**로 구한다.
  그 경우 §7에 「§8.11이 요구하므로 실시간 count로 구현했다」를 근거와 함께 남겨라
- 🔴 **탈퇴 배치에 `memberCount` 감소를 넣지 마라.** 넣으면 `departments` update가 `isHead()`에
  막혀 **배치 전체가 죽는다**(탈퇴하는 본인은 `head`가 아니다 — `reports/W-16.md` §8-3)
- PRD §9.3.2 필드 제거와 BR-57 정리는 **PM 소유**다. §7 항목으로 올려라

**결정 2 — `dev` 계정의 탈퇴를 막지 않는다.**
규칙 `selfWithdraw()`는 `resource.data.role != 'head'`만 본다. Dev는 통과한다.

- 🔴 **규칙을 넓히지 마라.** Dev는 운영자 본인이고 실수로 누를 위험이 낮다
- §9.6 각주에 「Dev 탈퇴는 막지 않는다 — 의도된 상태다」를 명시할 것을 §7에 올려라
- 🔴 **S10에서 Dev에게 탈퇴 버튼을 숨기지도 마라.** 규칙과 화면이 어긋나면 다음 사람이 혼란스럽다

**결정 3 — 부장 탈퇴 차단 문구를 확정한다.**

### 2.2 🔴 `selfWithdraw()` 규칙 전문을 읽고 표로

`firestore.rules`에서 그대로 읽어 **허용 키와 조건을 표로 보고**한 뒤 코드를 써라.
`reports/W-16.md` §8-1이 예고한 형태다.

```
resource.data.status == 'active'
resource.data.role != 'head'                                   // BR-56 · R-07
request.resource.data.status == 'withdrawn'
affectedKeys().hasOnly(['status','withdrawnAt','updatedAt'])   // 🔴 정확히 3개
```

🔴 **하나라도 더 쓰면 탈퇴가 통째로 거부된다.** `withdrawReason`·`anonymizedAt`·`name` 등을
같이 쓰지 마라. `SEC-9c`가 이미 그 케이스를 잡고 있다(탈퇴하면서 `role`을 함께 바꾸면 거부).

### 3.2 🔴 계정 탈퇴 — 규칙에 코드를 맞춘다

| 항목 | 규정 |
| --- | --- |
| 쓰는 키 | 🔴 **정확히 3개** — `status: 'withdrawn'` · `withdrawnAt` · `updatedAt` |
| 전이 | `active → withdrawn` **한 방향만**. 되돌리는 UI를 만들지 마라 |
| 확인 | **ConfirmModal 필수.** 되돌릴 수 없는 조작이다(양도와 같은 급) |
| 🔴 `destructive` | §8.10.4가 위험색을 **MD-07에만** 준다. 탈퇴 모달이 MD-07인지 확인하고, 아니면 켜지 마라(W-15B §3.9) |
| 성공 후 | `signOut` → S1로. 🔴 **`refresh()`를 부르지 마라** — 프로필이 사라진 상태에서 역할 판정이 도는 경로가 TS-12를 부른다(W-15B §4-2) |
| 오프라인 | 🔴 **`await`하지 마라.** 오프라인에서 promise가 resolve되지 않는다(W-08 §5-7 · W-12 §1-3). 기존 쓰기 경로가 어떻게 하는지 `records.ts`에서 확인하고 같은 형태를 써라 |

⚠ **`update`는 대상 문서가 없으면 실패한다**(W-15A §4-2). `users/{본인}`은 로그인 상태라
항상 존재한다 — **그 전제를 주석에 남겨라.**

### 3.3 🔴 부장 탈퇴 차단 — 이중 방어

| **클라이언트** | 탈퇴 버튼을 🔴 **비활성**으로 그리고, 바로 아래에 결정 3의 문구를 둔다 |

## 6. 검증 환경

### 6.1 🔴 에뮬레이터를 **먼저** 돌린다

W-16이 만든 `npm run rules:test`가 회귀 그물이다. 🔴 **실기기에 가기 전에** 코드가 내는
`update` 형태를 에뮬레이터 케이스로 먼저 통과시켜라.

- `SEC-9a`(부장 거부) · `SEC-9b`(탈퇴 계정의 읽기·쓰기 거부) · `SEC-9c`(허용 키 밖 거부)
- 🔴 **코드가 실제로 쓰는 키 집합**을 케이스에 그대로 옮겨라. 한 글자라도 다르면 무의미하다
- 🔴 **테스트를 깨뜨리지 말고 늘려라**(`reports/W-16.md` §8-5). 새 조건을 넣으면
  `mutations.mjs`에 역검증 변형도 함께 넣어라

| 창 | 🔴 **시크릿 창.** `persistentLocalCache`가 규칙 거부를 가린다(W-16D의 5-1 교훈) |

### 6.3 스텁 하네스

W-15B와 같다. **새로 필요한 것 3가지**만 적는다.

   `vice` · `teacher`
