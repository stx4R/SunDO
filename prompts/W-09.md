## 0. 시작 전 전제

### 0.1 W-08 보고서 §7 확인 요청 6건 회신

| # | 항목 | 결정 |
| --- | --- | --- |
| 1 | `Field` 확장 2건 (`transform` prop + `FieldHandle.reset()`) | **승인.** prop 1개는 §2.2가 허용한 폭 안이고, `reset()`의 근거가 특히 정확하다 — `validate`가 `string \| null` 2값이라 "판정 없음"을 표현할 수 없어 조회 실패를 성공(거짓말)이나 실패(정상 코드에 오탐)로밖에 못 그린다. **다만 진짜 결함은 `reset()`이 없었다는 것이 아니라 비동기 판정이 들어올 선언적 통로가 `Field`에 없다는 것이다.** `reset()`은 그 구멍을 명령형으로 메운 것이고, 화면이 늘면 화면마다 다른 escape hatch가 생긴다. **지금 고치지 않는다** — 실사용 소비자가 S2 하나뿐이라 설계할 근거가 부족하다. **S6 기록 작성 시트 회차에 소비자 2개를 놓고 `Field` 계약을 정리한다.** 열린 질문이 아니라 **예약된 결정**으로 PROGRESS에 기록하라 |
| 2 | `PrimaryButton`에 `aria-disabled` 1줄 | **승인.** W-07 §5-7의 `NeuButton`과 같은 건이다 |
| 3 | 오프라인 처리 추가 | **승인. 지시서의 누락이다.** PRD §8.2.5에 확정 문안이 있는데 §6에 옮기지 않았다. 근거도 맞다 — Firestore는 오프라인 쓰기를 로컬 큐에 넣고 `commit()`을 서버 ack까지 붙들기 때문에, 막지 않으면 변형 E가 취소 수단 없이 영원히 돈다 |
| 4 | 제출 버튼 활성 = 9자 완성 | **승인. 이것도 지시서가 틀렸다.** §8.2.2 #9의 기준은 `코드 미입력 시`, 즉 **비어 있는가**이지 검증 통과 여부가 아니다. design `13b`/`13d`도 같은 쪽이고, 내 §6.1이 "C에서 활성"이라 적으면서 그 둘과 어긋났다. 지적한 막다른 길(다 치고 바로 탭 → 버튼이 죽어 있어 blur조차 안 걸림)은 실제로 발생하는 동선이다 |
| 5 | 검증 중 성공 테두리 선점 (`settleY` 0.2s 조기 재생) | **현행 유지 · W-18 후보 확정.** 대안이 규격에서 더 멀어진다는 분석이 맞다 |
| 6 | 오프라인 배너 겹침 유예 | **이번 회차가 그 답이다.** §0.2 |

**§5-1·§5-5·§5-8·§5-12·§5-13·§5-14의 판단도 전부 유지한다.** 특히 §5-5(확정된 이름이 있으면 폴백을 열지 않는다)와 §5-14(늦게 끝난 조회가 새 값을 덮지 않게 `lookupSeq`)는 지시서가 요구하지 않았는데도 맞게 간 것이다. §5-5는 §8.2.3의 "본인은 변경할 수 없다"를 지켰고, §5-14가 없었으면 사용자가 값을 고치는 순간 옛 판정이 새 값에 붙었다.

### 0.2 🔴 이번 회차의 결정 — 오프라인 배너를 **밀어내기**로 바꾼다

| 출처 | 규정 |
| --- | --- |
| PRD §6.4 | `상단 고정` · `z-index 70` |
| design `12d` | 흐름 안에서 **콘텐츠를 밀어냄**(컨테이너 `padding:54px 0 0` + 배너 `flex:none`) |
| W-06 §5-3 | 충돌 해소 순서 1번으로 **PRD(오버레이)** 를 택하고, "독이 있는 화면에서 겹치면 재판단"으로 유예 |
| W-08 §5-7 | **독이 없는 S2에서 이미 겹쳤다.** 배너 `safe-area+16`~`+56`, 제목 `safe-area+26` |

**design 쪽으로 뒤집는다.** 근거는 세 가지다.

1. **겹침이 두 화면에서 실증됐다.** S2는 독이 없는데도 겹쳤고, 상단 정렬인 S3·S7·S8·S9·S10은 전부 겹친다. 유예 조건이 이미 충족됐다.
2. **오버레이는 정보를 가린다.** 배너가 알리려는 것은 "지금 오프라인"인데, 그 대가로 화면 제목을 가리면 순손실이다.
3. **PRD의 `상단 고정`은 위치 규정이지 겹침 규정이 아니다.** design이 같은 요소를 흐름 안에 그렸다는 것은 손실 없는 이형이 아니라 **더 구체적인 명세**다. `z-index 70`은 그대로 지킨다 — §0.3의 딤 관계 때문이다.

**PRD §6.4의 `상단 고정`을 `상단 고정(콘텐츠를 밀어냄)`으로 개정**해야 정합이 맞는다. st4R 반영 목록에 올려라.

### 0.4 충돌 해소 순서 (불변)

1. PRD가 명시한 값이 있고 design이 손실 없는 이형이 아니면 → **PRD**
2. PRD가 침묵하고 design에 값이 있으면 → **design**
3. 둘 다 있고 서로 다르며 어느 쪽이 손실인지 판단이 서지 않으면 → **멈추고 물어라**

### 1.1 왜 S3와 함께 하지 않는가

W-08 §5-7이 "**전 화면의 상단 여백 계약을 바꾸는 일**"이라고 정확히 진단했다. 그 변경을 새 화면과 같은 회차에 섞으면, 회귀가 났을 때 원인이 배너인지 S3인지 갈라내는 데 회차 하나를 더 쓴다. **여백 계약은 단독으로 검증하고, S3는 그 위에 올라선다.**

W-03A/B/C가 화면 없이 부품만 만든 선례가 있다. 다만 그때와 달리 **이번에는 소비자가 이미 6개**(Splash · S1 · S2 · S2-1 · 정책 3종 · 독 자리표시자 5종)라 통합 검증이 가능하다.

## 2. 사전 조사 — 코드를 쓰기 전에 하고, 보고서에 표로 남겨라

### 2.1 design `12d`의 밀어내기 구조 원문

`padding: 54px 0 0`의 `54px`이 무엇으로 이루어졌는지 분해하라.

| 확인 | 내용 |
| --- | --- |
| 목업 상태 표시줄 높이 | 다른 프레임(`12a`·`13a`)의 상단 값 `88px`과 대조하면 표시줄 몫이 나온다 |
| 배너 상단 오프셋 | W-06이 `safe-area + 16px`로 확정했다(독 `bottom 16px`의 거울상). design에서 이 값이 유도되는지 |
| **배너 하단 ↔ 콘텐츠 간격** | 이번에 새로 필요한 값이다. design에서 유도되면 그 값을 쓴다 |

**유도되지 않으면 §3.2의 규칙을 쓴다.** 값을 지어내지 마라.

### 2.2 `AppShell`의 현재 여백 소유 구조

| 확인 항목 | 왜 |
| --- | --- |
| 상단 패딩이 어디서 계산되는가 (`safe-area + 26px` / 독 화면 `+34px`) | 배너 높이를 여기에 더할지, 별도 형제로 둘지가 갈린다 |
| 스테이지 직계 자식의 순서와 각각의 `position`·`z-index` | 스크롤 영역 · 독 슬롯 · 오버레이 루트 |
| 스테이지가 flex 컬럼인가 | 밀어내기가 성립하려면 배너가 **형제**여야 한다 |
| `hasDock`·`bottomGap` prop이 상단에도 영향을 주는가 | 없어야 정상이다 |

### 2.3 `.ofb`의 현재 마운트 경로

W-06이 `OverlayRootContext`로 포털했다. **그 루트가 `pointer-events: none`이라는 사실 외에 배너가 오버레이 루트에 의존하는 것이 있는지** 확인하라. 없으면 §3.1에서 끊는다.

### 2.4 배너와 딤의 z 관계

시트가 열린 상태(딤 `z-40`)에서 배너(`z-70`)가 **딤 위에 보여야** 한다. 현재 구조에서 두 요소가 **같은 스택 컨텍스트에 있는지** 확인하라. 부모가 달라 `z-index`가 비교되지 않으면 §3.1의 배치가 그것을 고쳐야 한다.

## 3. 배너 슬롯

### 3.1 소유와 배치 — **`AppShell`이 직접 렌더한다**

컨텍스트 3번째(`BannerRootContext`)를 만들지 마라. 포털도 쓰지 마라.

| 판단 | 근거 |
| --- | --- |
| 왜 포털이 아닌가 | 포털은 "다른 곳에서 만든 것을 여기 꽂는다"는 문제를 푼다. 배너는 **만드는 쪽이 없다** — 전역 1개이고 조건이 `useOnline()` 하나뿐이다 |
| 왜 `AppShell`인가 | `AppShell`은 **여백 단독 소유자**다(W-06 §1). 배너가 여백을 바꾸므로 소유가 일치한다 |
| 대가 | `AppShell`이 `useOnline()`을 부르게 된다. 훅 하나이고 라우팅·인증을 아는 것이 아니다 |

**배치**: 스테이지의 **직계 자식**으로, 스크롤 영역의 **형제이자 바로 앞**에 둔다.

```
스테이지 (flex column)
 ├─ OfflineBanner        ← 신규 위치. z-70. 오프라인일 때만 렌더
 ├─ 스크롤 영역
 ├─ 독 슬롯 (DockRootContext)
 └─ 오버레이 루트 (OverlayRootContext, pointer-events: none)
```

스크롤 영역·오버레이 루트와 **같은 스택 컨텍스트**에 놓이므로 `z-index: 70`이 딤(`z-40`)을 이긴다(§2.4). 실측으로 확인하라.

`OfflineBanner`에서 `OverlayRootContext` 의존과 포털 코드를 **제거**한다. 시각 규격(높이 40 · `radius 14` · `rgba(20,53,38,0.88)` · `blur 12` · 좌우 18 · 아이콘 14 · `12px/700`)은 **한 값도 바꾸지 마라.**

### 3.2 밀어내는 양

design에서 유도되지 않으면(§2.1) 아래 규칙을 쓴다.

| 항목 | 규칙 |
| --- | --- |
| 배너가 차지하는 세로 | 상단 오프셋 `16px` + 배너 높이 `40px` = **`56px`** |
| 콘텐츠 시작 | 배너가 있을 때 = 배너가 없을 때 + `56px`. 즉 일반 화면 `safe-area + 26 + 56`, 독 화면 `safe-area + 34 + 56` |
| 배너 하단 ↔ 콘텐츠 간격 | **기존 상단 패딩을 그대로 유지한다**(26px / 34px). 새 간격 값을 만들지 마라 |
| 배너가 없을 때 | **기존 값과 바이트 단위로 같아야 한다.** 조건부 패딩이 항상 붙지 않도록 하라 |

`env(safe-area-inset-top)`을 두 번 더하지 마라. 배너와 콘텐츠가 각각 safe-area를 계산하면 2배가 된다.

### 3.3 스크롤과의 관계

배너는 **스크롤되지 않는다**(스크롤 영역 밖의 형제다). 콘텐츠를 스크롤해도 배너는 제자리다. 이것이 `상단 고정`(§6.4)의 의미다.

## 4. 화면별 영향과 회귀

**배너가 없을 때 6화면의 computed 값이 한 칸도 바뀌지 않는 것이 이번 회차의 핵심 증명이다.**

| 화면 | 배너 없음 | 배너 있음 |
| --- | --- | --- |
| **Splash** | 불변 | 스플래시가 `z-100`이라 배너를 덮는다. **그대로 둔다** — 배너를 조건부로 끄지 마라. 판정 중에는 화면 자체가 없으므로 가릴 콘텐츠도 없다 |
| **S1** | 불변 | 세로 중앙 정렬이 `56px`만큼 아래로 밀린다. Footer가 최하단에 남는지 확인 |
| **S2** | 불변 | **W-08 §5-7의 유예가 해소된다.** 뒤로 버튼·제목이 배너 아래로 내려간다 |
| **S2-1** | 불변 | 중앙 정렬이 밀린다. 하단 고정 영역·Footer는 그대로 |
| **정책 3종** | 불변 | `loading`을 건너뛰므로(W-06 §0.1-3) 배너가 보인다. 정상이다 |
| **독 자리표시자 5종** | 불변 | 상단 패딩이 `+34` → `+34+56`. **독은 하단이라 영향 없다** |

### 4.1 S2의 오프라인 처리는 그대로 둔다

W-08 §5-6이 넣은 **힌트 교체 + 버튼 비활성**을 배너가 대체하지 않는다. 셋을 함께 쓴다.

- PRD §8.2.5가 힌트와 버튼 비활성을 **명시**한다. 배너가 생겼다고 지울 근거가 없다.
- S1도 같은 구조다(배너 + 힌트 교체 + 버튼 비활성). **일관을 깨지 마라.**
- 배너는 "지금 오프라인"을, 힌트는 "그래서 이 화면에서 무엇을 할 수 없는지"를 말한다. 중복이 아니다.
