#### 결정 2 — 🔴 이번에 새로 드러난 충돌: 본인의 재신청 전이가 §9.6에 막혀 있다

| 출처 | 규정 |
| --- | --- |

### 2.2 🔴 `Field`가 캐럿 위치를 지킬 수 있는가 — 이번 회차의 최대 위험

`가입 코드` 입력은 타이핑 중 값을 **변형**한다(대문자화 + `-` 삽입). 제어 컴포넌트에서 값을 바꿔 다시 내려보내면 브라우저가 캐럿을 **문자열 끝으로 밀어 버린다.** 중간을 고치던 사용자는 커서가 튀는 것을 본다.

`src/components/Field.tsx`를 읽고 보고하라.

| 확인 항목 | 왜 |
| --- | --- |
| `onChange`가 넘기는 것이 값인가 이벤트인가 | 캐럿 보정에는 `input` 요소 접근이 필요하다 |
| `FieldHandle`(ref)이 무엇을 노출하는가 | `setSelectionRange`를 부를 수 있는 통로가 이미 있을 수 있다 |
| 값이 외부에서 바뀔 때 캐럿을 어떻게 다루는가 | 아무 처리도 없으면 끝으로 밀린다 |

| 결과 | 조치 |
| --- | --- |
| 통로가 **이미 있다** | 화면에서 보정한다. `Field`를 고치지 마라 |
| 통로가 **없다** | **`Field`를 최소한으로 확장하는 것을 허용한다.** `Field`는 앱의 유일한 텍스트 입력 수단(DS-06)이고 값 변형이 필요한 입력은 앞으로도 나온다(S6 기타 사유·S9 검색). **W-07 §1의 API 표 4번을 갱신해 재수록하고**, 확장 이유를 보고서 §"판단이 필요했던 지점"에 적어라 |
| 확장 폭이 prop **2개를 넘어간다** | **멈추고 물어라** |

### 2.3 진입 3상태의 실제 값

`/signup`은 W-07 §4 이후 `noProfile` · `withdrawn` · `rejected` 3가지로 들어온다. 각 상태에서 `useAuth()`의 `profile` · `parsed`가 실제로 무엇을 들고 있는지 확인해 표로 보고하라.

| 상태 | `profile` | `parsed` | 화면이 이름·이메일을 어디서 얻는가 |
| --- | --- | --- | --- |
| `noProfile` | ? | ? | `users` 문서가 없다 |
| `withdrawn` | ? | ? | 문서가 있다 |
| `rejected` | ? | ? | 문서가 있다 |

**`noProfile`에서 `profile`이 `null`이면 신원 카드는 `parsed`와 `auth.currentUser`에서 값을 얻어야 한다.** 세 상태가 같은 코드 경로를 타도록 만들되, 값의 출처가 갈리는 지점을 명시하라.

### 2.4 현재 Firebase 규칙 상태

콘솔을 볼 수 없으므로 **코드에서 확인 가능한 것만** 보고하라 — 프로젝트에 규칙 파일(`firestore.rules` 등)이 있는지, `firebase.json`이 규칙을 참조하는지. **없으면 "저장소에 규칙 파일 없음"이라고 적어라.** §10의 요청서가 그 사실 위에서 쓰인다.

### 3.1 코드 조회 (안 1)

```
getDoc(doc(db, 'departments', 'dshs-jayul', 'inviteCodes', <입력값>))
```

`departmentId`는 §9.3.1이 `'dshs-jayul'` 고정값으로 규정한다. **`where` 쿼리를 쓰지 마라** — `list`는 여전히 막혀 있고, 안 1이 연 것은 **단건 `get` 하나뿐**이다.

판정 순서와 결과:

| # | 조건 | 결과 | 코드 |
| --- | --- | --- | --- |
| 1 | 문서 없음 | `존재하지 않는 코드입니다` | E-1001 |
| 2 | `isActive !== true` | `만료된 코드입니다. 부장에게 새 코드를 요청해 주세요` | E-1002 |
| 3 | `expiresAt` 경과 | 〃 | E-1002 |
| 4 | `useCount >= maxUses` | 〃 | E-1002 (BR-14) |
| 5 | 통과 | 성공 | — |

**🔴 조회 자체가 실패한 것을 "없는 코드"로 읽지 마라.** 네트워크 오류·권한 거부·타임아웃은 **1번이 아니다.** 이것들은 인라인 에러가 아니라 **상단 배너 ER-01 `네트워크에 연결할 수 없습니다`**로 보내고 코드 필드는 검증 이전 상태로 둔다. W-05 §9가 지적한 것과 같은 종류의 거짓말이다 — 조회 실패를 "문서 없음"으로 읽으면 정상 코드를 가진 사용자에게 존재하지 않는다고 말하게 된다.

반환 타입은 **판별 가능한 유니온**으로 만들어라. `null`로 "없음"과 "실패"를 뭉개지 마라.

### 3.2 OP-01 배치 (안 2 적용 후 **2건**)

```
writeBatch:
  ① users/{uid}              — 진입 상태에 따라 setDoc 또는 updateDoc
  ② approvalRequests/{reqId} — setDoc
```

**`inviteCodes` 갱신은 없다.** 안 2가 OP-09로 옮겼다.

#### ① `users/{uid}`

| 진입 상태 | 연산 | 쓰는 필드 |
| --- | --- | --- |
| `noProfile` | `setDoc` | §11.2 OP-01 요청 JSON 전체 + **`updatedAt: serverTimestamp()`**(§9.3.1이 필수로 규정하는데 OP-01 예시에 빠져 있다) |
| `withdrawn` · `rejected` | `updateDoc` | §0.2 결정 2의 조건 6 부분집합만. **`createdAt`·`recordCount`·`email`·`uid`를 다시 쓰지 마라** |

재신청 시 반드시 함께 쓰는 값: `status: 'pending'` · `role: 'member'`(BR-62) · `withdrawnAt: null` · `rejectReason: null` · `inviteCodeId` · `updatedAt`.

#### ② `approvalRequests/{reqId}`

| 항목 | 규격 |
| --- | --- |
| 문서 ID | **`{uid}_{제출 시각 밀리초}`.** 제출을 시작할 때 **1회 생성해 ref에 담고 재시도에도 그대로 재사용**한다(§11.1 멱등성). 매번 새로 만들면 재시도가 문서를 늘린다 |
| 필드 | §9.3.7 전체 — `uid` · `email` · `name` · `inviteCodeId` · `status: 'pending'` · `createdAt: serverTimestamp()` |
| BR-28 | 재신청은 **새 문서**다. 기존 문서를 덮어쓰거나 지우지 마라 |

| --- | --- |
| 배치 실패 | 상단 배너 `가입 신청에 실패했습니다. 잠시 후 다시 시도해 주세요`(T-06). **부분 생성 문서를 남기지 않는다** — `writeBatch`가 원자적이므로 자동으로 만족한다. 별도 롤백 코드를 쓰지 마라 |
| 성공 후 이동 | **화면이 `navigate()`를 부르지 마라.** `status`가 `pending`이 되면 라우터가 `/pending`으로 옮긴다. `refresh()`를 호출해 판정을 갱신하는 것까지가 화면의 일이다 |

**`이미 신청이 접수되었습니다`(`already-exists`)는 만들지 마라.** 신청이 접수된 계정은 `pending`이 되어 라우터가 S2에 머물게 하지 않는다 — 도달 불가 경로다. 도달 불가라는 판정을 보고서에 근거와 함께 적어라.

## 5. 가입 코드 입력의 거동

### 5.1 형식과 변형

| 항목 | 규격 |
| --- | --- |
| 형식 | `^[A-Z]{4}-[0-9]{4}$`, **9자 고정** |
| 대문자화 | 입력 즉시 `toUpperCase()` |
| `-` 삽입 | 문자 4개가 차면 자동 삽입 |
| 캐럿 | **위치를 유지한다**(§2.2). 중간 편집·삭제에서도 끝으로 밀리지 않아야 한다 |
| 붙여넣기 | 같은 규칙을 적용한다. 소문자·공백이 섞인 붙여넣기도 정규화된다 |
| 초과 입력 | 9자를 넘는 입력은 버린다 |

`src/lib/inviteCode.ts`의 **순수 함수**로 만들어라 — 입력 문자열과 캐럿 위치를 받아 정규화된 문자열과 새 캐럿 위치를 돌려준다. 화면 없이 실측할 수 있어야 한다.

### 5.2 검증 시점 (§7.3 `field` 규격 + §8.2.4 T-03)

| 시점 | 처리 |
| --- | --- |
| 입력 중 | 검증하지 않는다. 변형만 한다 |
| **blur** | ① 형식 검사 → 실패 시 즉시 인라인 에러 + shake ② 통과 시 **서버 조회**(우측 스피너 16px) → 성공 체크 / 실패 shake |
| 제출 | **코드를 다시 조회한다**(EC-07 — 입력 도중 만료될 수 있다). 캐시된 결과를 믿지 마라 |
| 재검사 | 한 번 에러가 뜬 필드는 **값이 바뀔 때마다 즉시 재검사**한다(§7.3) |

에러 문구 — **이 4개만 쓴다**(§8.2.3):

`가입 코드를 입력해 주세요` / `코드 형식이 올바르지 않습니다 (예: DJSN-2691)` / `존재하지 않는 코드입니다` / `만료된 코드입니다. 부장에게 새 코드를 요청해 주세요`

### 5.3 이름 폴백 (EC-32 · DR-11)

| 상황 | 처리 |
| --- | --- |
| 파싱 성공 | 신원 카드에 파싱된 이름만. **이름 입력 필드를 렌더링하지 않는다.** `nameSource='parsed'` |
| 파싱 실패 | 신원 카드 아래에 이름 입력 1개 추가 + 안내 `Google 계정 이름을 확인할 수 없습니다. 이름을 직접 입력해 주세요`(ER-14). `nameSource='manual'` |

이름 검증(§8.2.3): `^[가-힣a-zA-Z\s]+$`, **2~10자**, blur 시점. 문구는 `이름을 입력해 주세요` / `이름은 2자 이상 10자 이하로 입력해 주세요` / `이름에는 한글 또는 영문만 사용할 수 있습니다` **3개만**.

**파싱 판정을 화면에서 다시 하지 마라.** `useAuth()`의 `parsed`가 이미 들고 있다.
