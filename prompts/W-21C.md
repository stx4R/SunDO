## 3. 구현 지시

### 3.1 기능 3 — 순찰 일정 편집

- design `19a`~`19e`의 **시각 규격을 그대로** 쓴다. 🔴 **팝오버 좌표·크기·색을 실측으로 대조**하라
- **부장만**(결정 2). 🔴 차장·부원·교사에게는 편집 진입점을 **렌더하지 마라**(부재로 처리)
- 담당자 검색 팝오버는 `users` 목록 — `list`는 이미 열려 있다(M-1)
- 🔴 **감사 로그 `DUTY_UPDATE`를 남길지 판단하고 근거를 적어라.** 남기면 배치가 2연산이 되고
  「부분 성공 없음」이 걸린다. W-21B §4.6이 그 형태의 선례다
- 🔴 **`hasOnly`로 바꿀 수 있는 필드를 못 박아라.** `weekId`·`startDate`·`endDate`·`createdBy`를
  열지 마라 — W-21B §4.1이 `records`에서 한 것과 같은 형태다
- ⚠ **`19c`의 에러 상태**(장소 미입력)를 구현하라. 문구는 §2.2의 DS-05 판정에 따른다

## 5. 🔴 마이그레이션 — 이 회차의 급소

### 5.1 문제

`reports/W-21B.md` §9.1이 확정한 형태는 `patrolTime`·`patrolPlace`를 **`string → map`**으로 바꾼다.

🔴 **같은 이름의 타입을 바꾸면 옛 앱과 새 앱이 공존할 수 없다.**

| 순서 | 옛 앱 | 새 앱 |
| --- | --- | --- |
| 마이그레이션을 **먼저** | 🔴 **map을 string 자리에서 읽어 깨진다** | 정상 |
| 앱을 **먼저** | 정상 | 🔴 **string을 map 자리에서 읽어 깨진다** |

⚠ **§9.1이 「옛 필드를 남긴 채 새 형태를 함께 쓴다」로 적었지만, 같은 이름으로는 그것이 불가능하다.**
남기려면 **새 이름이 필요하다.**

### 5.2 🔴 설계안을 표로 내고 확인을 받아라

**코드를 쓰기 전에.**

| 안 | 형태 | 공존 | 대가 |
| --- | --- | --- | --- |
| **A. 새 이름 병기** | `patrolTime`(string · 유지) + `patrol`(map · 신설) | ✅ **둘 다 산다** | 필드가 늘고, 언젠가 옛 필드를 지우는 회차가 필요하다 |
| **B. 같은 이름 교체** | `patrolTime`이 map이 된다 | 🔴 **불가** | 배포 창에 반드시 깨진다 |
| **C. 문서 분리** | `2026-W35_v2` | ✅ | 문서 ID 규약이 바뀐다 · 읽기가 갈린다 |

🔴 **`assignments`·`assigneeNames`도 같은 문제다.** `{mon: [uid]}` → `{mon: {lunch, dinner}}`는
**타입 변경**이다. 같은 판단이 필요하다.

**어느 안이든 지킬 것**

- 🔴 **`--dry-run`이 기본값이고 `--commit`이 있어야 쓴다**
- 🔴 **옛 문서를 지우지 마라**
- 실행 전 요약(대상 건수 · 변환 결과) → 사용자 확인 → `--commit`
- 🔴 **되돌리는 절차를 `database_ToDo/W-21C.md`에 먼저 적어라**(규약 4-3의 정신)

### 5.3 배포 순서

| 순서 | 무엇 | 왜 |
| --- | --- | --- |
| ① | **마이그레이션**(새 필드 추가만 · 옛 필드 유지) | 옛 앱이 옛 필드를 계속 읽는다 — 안 깨진다 |
| ② | **인덱스**(기능 4가 요구하면) | §18.4 |
| ③ | **규칙**(`dutySchedules` 좁히기) | 🔴 **좁히는 변경이지만 옛 앱에 편집 경로가 없어 무해하다** — 그 사실을 확인하고 적어라 |
| ④ | **앱** | |
| ⑤ | 🔴 **스모크** — 이번 것 + **W-21B의 8건**(§0.4-1) | |

⚠ **③의 무해함은 「옛 앱이 `dutySchedules`에 쓰지 않는다」에 달려 있다.** §2.1에서 **직접 세어라.**
🔴 **세지 않고 「무해할 것이다」로 넘어가지 마라** — W-21B §7 ③이 정확히 그 함정이었다.
