### 0.3 🔴 이 회차를 막고 있던 결정 — **확정한다**

#### 결정 1 — BR-30은 **클라이언트 카운터**다. Rules로 세려 하지 마라

🔴 **D-2의 교훈을 그대로 적용했다 — PRD를 먼저 찾았고, 이미 정해져 있었다.**

> **PRD §11.5 원문**
> | 대상 | 한도 | 강제 위치 |
> | 가입 신청 | 계정·IP당 24시간 3회 | **클라이언트 + Firebase App Check** |
>
> 각주: *클라이언트 전용 제한은 새로고침·시크릿 탭으로 우회 가능하다. 실사용 규모(약 40명)에서는
> 허용 위험이지만, 외부 유출 정황이 발생하면 프로파일 B로 즉시 전환한다.
> Firebase App Check(reCAPTCHA v3)를 MVP부터 활성화해 자동화 요청을 1차 차단한다.*

**여기서 읽어야 하는 것 3가지**

| # | 사실 | 따라오는 지시 |
| --- | --- | --- |
| 1 | 강제 위치가 **「클라이언트 + App Check」**이지 Rules가 아니다 | 🔴 **`firestore.rules`를 이 회차에 한 줄도 고치지 마라.** Rules는 집합을 셀 수 없다(W-16 §6에서 이미 실측된 한계다) |
| 2 | **「계정·IP당」** — 🔴 **클라이언트는 자기 IP를 모른다** | **계정당만 센다.** IP 몫은 **App Check가 대신한다** — 그것이 「짝이다」의 실제 의미다 |
| 3 | 각주가 **우회 가능성을 이미 인정하고 받아들였다** | 🔴 **완벽한 카운터를 설계하려 들지 마라.** 시크릿 탭 우회를 막는 것은 이 회차의 목표가 아니다. **목표는 「자동화가 아닌 사람의 반복을 늦추는 것」이고, 자동화는 App Check가 막는다** |

⇒ 🔴 **하나만 배포하면 반쪽이 된다**(W-16 §7). §2와 §3은 **같은 커밋·같은 배포로 나간다.**

#### 결정 2 — App Check **시행(enforce)은 이 회차에서 켜지 않는다**

| 단계 | 무엇 | 이 회차 |
| --- | --- | --- |
| ① | SDK 부착 + 사이트 키 배선 (코드) | ✅ **한다**(§2.2) |
| ② | 콘솔 앱 등록 + **모니터링 모드** (PM) | ✅ **한다**(§2.3) |
| ③ | **시행 켜기** | 🔴 **하지 않는다.** PM이 지표를 보고 별도로 켠다(§2.4) |

🔴 **왜 ③을 미루나 — 시행은 「토큰이 없는 요청을 전부 거부」다.**
reCAPTCHA v3 토큰이 실제로 발급되고 있는지는 **콘솔 「요청 지표」에 검증된 요청이 쌓여야만** 알 수 있다.
지표 없이 켜면 실패했을 때 **앱 전체가 죽고, 사용자 3명이 전부 막히며, 원인이 규칙인지 App Check인지
구별되지 않는다.** ⇒ **①②를 배포하고, 지표가 「검증됨」으로 차면 그때 켠다.**

⚠ **이것은 「하나만 배포하지 마라」와 충돌하지 않는다.** 그 규정은 **App Check와 BR-30을 갈라
배포하지 마라**는 뜻이고, 시행 시점은 별개의 축이다. **§2와 §3은 이번에 함께 나간다.**

#### 결정 3 — 신규 오류 코드 **E-1009**를 만든다

§11.4 표에 가입 신청 레이트 리밋 문구가 **없다.** 만들지 않으면 사용자는 버튼이 왜 안 눌리는지 알 수 없다.

| 코드 | 조건 | HTTP | 문구 | 오퍼레이션 |
| --- | --- | --- | --- | --- |
| **`E-1009`** | 가입 신청 24시간 3회 초과 | 429 | **`가입 신청은 24시간에 3회까지 가능합니다`** | OP-01 |

- 🔴 **E-3002(`잠시 후 다시 시도해 주세요 (시간당 5회 제한)`)의 형태를 본떴다** — 한도를 문구에 드러낸다.
  W-07 §7-5의 「쿨다운 중 남은 초 미표시」가 W-18까지 끌려간 이유가 **왜 안 눌리는지 알 수 없다**였다
- 🔴 **남은 시간을 표시하지 마라.** §11.4에 그 형태의 문구가 하나도 없고, 24시간 카운트다운은 새 규격이다
- **st4R 반영 항목**이다(§8 신규 ㉕)

#### 결정 4 — 커스텀 도메인(`D-19`)·Hosting 채널은 **PM 판단으로 남긴다**

🔴 **개발이 임의로 정하지 않는다.** 학교·교육청 도메인 보유 여부는 코드가 알 수 없는 사실이다.
다만 **판단 재료는 §4-5에 적어 둔다.** 🔴 **결정 2(`sundo-dev-8ef38`이 그대로 운영)로
§18.1의 dev/prod 분리 조항이 이미 사실과 어긋났다** — 그 개정(§6-7)은 도메인 결정과 **무관하게** 한다.

## 2. App Check — **3단계로 나눈다**

### 2.1 왜 나누나

| 층 | 무엇이 보증되나 | 실패하면 |
| --- | --- | --- |
| ① SDK | 앱이 토큰을 **요청한다** | 콘솔 경고 1건. 앱은 정상 동작한다 |
| ② 등록·모니터링 | 콘솔이 토큰을 **집계한다** | 지표가 안 찬다. 앱은 정상 동작한다 |
| ③ 시행 | 토큰 없는 요청이 **거부된다** | 🔴 **앱 전체가 죽는다** |

🔴 **①②는 되돌리기 비용이 0에 가깝고 ③만 비싸다.** 그래서 ③을 뗐다.

### 2.2 ① SDK 부착 — 코드

```
initializeApp(config)
  ↓
initializeAppCheck(app, {
  provider: new ReCaptchaV3Provider(siteKey),
  isTokenAutoRefreshEnabled: true,
})
  ↓
getAuth(app) · initializeFirestore(app, …)
```

- 🔴 **순서를 지켜라**(§1.1-2). `initializeApp` **직후**, 다른 서비스보다 **먼저**
- 🔴 **사이트 키가 비어 있으면 App Check를 건너뛰고 `console.warn` 1건만 남긴다. 앱을 멈추지 마라.**
  ⚠ **이것은 W-04 §6의 「6개 중 하나라도 비면 멈춘다」 계약을 일부러 따르지 않는 것이다.**
  근거 — **`VITE_FIREBASE_*` 6개는 없으면 앱이 아무것도 못 한다(기능). 사이트 키는 없어도

## 3. BR-30 — 가입 신청 레이트 리밋

### 3.1 규정

**계정당 24시간 3회.** 근거 §11.5 · BR-30. IP 몫은 App Check가 맡는다(결정 1).

### 3.2 어디를 세나 — **`approvalRequests`. 새 컬렉션을 만들지 마라**

- 🔴 **이미 만들어지는 데이터다.** 신청 1회 = 문서 1건이고, 재신청도 새 문서 1건이다(W-08 §4-4 실측)
- 질의: **본인 uid 등식 1개** + **`createdAt >= 24시간 전`은 클라이언트 필터**
  🔴 **`where`에 범위 조건을 넣지 마라** — 등식+범위는 복합 인덱스를 요구한다(§1.2-4)
- 🔴 **새 필드도 만들지 마라.** `users`에 `signupAttempts` 같은 것을 더하면
  §9.6 자기 갱신 허용 키를 넓혀야 하고, 그러면 **`firestore.rules`가 열린다**(§0.4 위반)

### 3.3 판정과 화면

| 상태 | 처리 |
| --- | --- |
| 24시간 내 3건 미만 | 평소대로 |
| **3건 이상** | 🔴 **제출 버튼 비활성** + 인라인 **E-1009** `가입 신청은 24시간에 3회까지 가능합니다` |
| 조회 실패 | 🔴 **§3.5** |
| 오프라인 | 🔴 **기존 계약 그대로** — S2는 이미 오프라인에서 제출을 막는다(W-08 §5-7). **새 분기를 만들지 마라** |

- 🔴 **「비활성」은 `disabled`다. 부재가 아니다.** W-15A §4-4의 「읽기 전용 = 버튼 부재」와 **반대**인 이유:
  거기는 **권한이 없어 영원히 못 하는 것**이고 여기는 **지금만 못 하는 것**이다. 문구가 이유를 말한다
- 🔴 **남은 시간을 계산해 보여 주지 마라**(결정 3)

### 3.4 세는 시점

**S2 진입 시 1회** + **제출 직전 1회.** 진입 시만 세면 화면을 열어 둔 채 3회를 채울 수 있고,
제출 직전만 세면 다 입력한 뒤에야 막혀 §8.2의 동선이 깨진다.

### 3.5 🔴 조회 실패를 「초과」로 읽지 마라

**실패하면 통과시킨다.** W-12 §3.8(중복 조회 실패 → 저장 진행)과 **같은 규칙**이다.

> **가입을 잘못 막는 것이 한 번 더 신청받는 것보다 비싸다.**
> 신입 부원이 아무 설명 없이 가입 불가가 되면 복구할 방법이 앱 안에 없다.

`permission-denied`·`unavailable`·`failed-precondition` 전부 **통과**시키고 `console.warn` 1건만 남긴다.
🔴 **판별 유니온을 써라** — `ok(n) | unknown`. `unknown`을 `0`이나 `3`과 뭉개지 마라(W-12 `DuplicateVerdict` 선례).

### 3.6 만들지 마라

새 컬렉션 · `users` 신규 필드 · IP 카운트 · Rules 변경 · 남은 시간 표시 · 관리자용 리셋 UI ·
